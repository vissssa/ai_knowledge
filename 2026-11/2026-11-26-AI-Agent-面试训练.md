## B01 标称 1 Gbps 却只跑到 8 Mbps：cwnd、BDP 与拥塞控制

**题目 ID**：Q-20261126-B01 ｜ 一级类型：操作系统与网络 ｜ 二级主题：TCP 拥塞控制与带宽时延积（BDP）｜ 标签：TCP、拥塞控制、CUBIC、BDP

### 题目

面试官给出一组观测：上海到弗吉尼亚的专线标称 1 Gbps，往返时延 200 ms，链路丢包率约 0.01%。运维用 `iperf` 单条 TCP 连接测试，稳定吞吐只有 8 Mbps 左右，而 `iftop` 显示链路利用率不到 1%。同一条链路上开 8 条并发连接，总吞吐涨到约 60 Mbps，但仍然远低于标称值。请解释单流吞吐受什么约束、8 Mbps 这个数量级是怎么来的，以及在不改变链路的前提下有哪些工程手段能提升吞吐。

### 先思考

1. 先算一笔账：1 Gbps × 200 ms 等于多少字节"在途"？这个量叫带宽时延积，它和"窗口"是什么关系？
2. 稳态吞吐的近似公式是 `cwnd / RTT`。如果观测到 8 Mbps、RTT 200 ms，反推在途数据量是多少个 MSS？
3. 0.01% 的丢包在局域网上可以忽略，在长肥管道上意味着什么？丢包型的拥塞控制会把丢包解释成什么信号？

### 参考答案

**定义**：TCP 发送方任意时刻"已发送未确认"的数据量不得超过 `min(cwnd, rwnd)`（RFC 5681 §2、§3.1 原文为 "The minimum of cwnd and rwnd governs data transmission."）。`cwnd` 是拥塞窗口，由拥塞控制算法依据 ACK 与丢包反馈调整；`rwnd` 是接收方通告的窗口，由接收缓冲与内核自动调优决定。稳态下吞吐约等于 `窗口 / RTT`，因此**决定吞吐的不是链路带宽，而是窗口能否填满带宽时延积（BDP = 带宽 × RTT）**。

**适用边界**：`吞吐 ≈ 窗口 / RTT` 只在窗口是瓶颈时成立。窗口足够大而链路成为瓶颈时，吞吐由带宽决定；出现随机丢包时，丢包型算法（Reno、CUBIC）会把丢包解释为拥塞信号并收缩窗口，吞吐转而由丢包率与 RTT 共同决定，与带宽脱钩。这也是"带宽买够了、吞吐还是上不去"的典型成因。反向的边界是：短 RTT、低带宽的局域网里 BDP 很小，默认窗口就能填满，公式的实用价值不高。

**示例（把 8 Mbps 算出来）**：BDP = 1 Gbps × 0.2 s = 200 Mbit = **25 MB**。8 Mbps 在 200 ms RTT 下对应在途约 `8e6 × 0.2 / 8 = 200 KB`，按 MSS 1460 B 计约 **137 个段**——说明 cwnd 长期在 140 段量级振荡。再用 Mathis 近似 `BW ≈ (MSS/RTT) × 1.22/√p`：MSS/RTT ≈ 58.4 kbps，p = 1e-4 时 √p = 0.01，得 **约 5.8 Mbps**，与观测的 8 Mbps 同量级。结论很直接：**这条链路的吞吐被丢包率和 RTT 锁死在个位数 Mbps，1 Gbps 的标称能力在这个丢包率下几乎不可能被单流利用**。

**相近概念区别**：
- `cwnd` vs `rwnd`：前者是发送方对网络的估计（会因丢包收缩），后者是接收方的容量承诺（不会因网络丢包变化）；两者取小。
- 带宽 vs 吞吐 vs goodput：带宽是链路能力上限；吞吐是实际传输速率；goodput 扣除重传与协议开销，长肥管道上重传多时三者差距显著。
- 拥塞控制 vs 流量控制：前者保护网络（怕中间节点排队溢出），后者保护接收方（怕缓冲溢出），二者是不同层的问题。
- 丢包型（Reno/CUBIC）vs 模型型（BBR）：前者把丢包当拥塞证据；后者估计瓶颈带宽与最小 RTT，不把随机丢包当拥塞，因此在有随机丢包的长链路上优势明显。
- socket 缓冲 vs 窗口：应用层 `send()` 返回只代表写进了内核发送缓冲，`SO_SNDBUF` 上限会直接给单流吞吐设一个天花板。

**典型应用（通用工程）**：跨地域数据迁移、备份复制、大文件分发、跨云同步的设计都不能假设"单流能吃满带宽"。可行手段按性价比排序：① **并发多流**（每条流各自有独立 cwnd，8 条流把总在途量放大 8 倍，这也是本题 60 Mbps 的来源；上限受接收端 CPU、磁盘与链路公平性约束）；② **放大 socket 缓冲**（发送与接收缓冲都要 ≥ BDP/并发流数，否则窗口被本机内存卡死，而不是被网络卡死）；③ **换拥塞控制算法**（两端可控时上 BBR 类模型型算法，绕开"丢包即拥塞"的误判）；④ **缩短 RTT**（就近接入、边缘中转、CDN 回源收敛）；⑤ 应用层分块并行 + 断点续传，把"单连接可靠性"降级为"分块可重试"，这是工程上最稳的一条。

**面试现场回答**：单流吞吐的约束不是带宽，而是窗口能否填满 BDP，以及丢包型算法如何解释丢包。这条链路 BDP 是 25 MB，8 Mbps 对应在途只有 200 KB、约 137 个段，而 0.01% 的丢包按 Mathis 近似就足以把单流压在 6-8 Mbps，与带宽无关。工程解是并发多流 + 放大 socket 缓冲 + 需要时换 BBR + 缩短 RTT，并且用"分块可重试"替代"单连接硬扛"。

### 关键点

1. 有效窗口是 `min(cwnd, rwnd)`，吞吐约等于 `窗口 / RTT`；要跑满带宽就必须让窗口 ≥ BDP。
2. 长肥管道上丢包率是吞吐的主导变量：0.01% 的丢包在 200 ms RTT 下把单流压到个位数 Mbps，Mathis 近似可用来做数量级校验。
3. CUBIC 仍是丢包驱动（RFC 9438：β=0.7、C=0.4，Linux/Windows/Apple 默认），它对长距离更友好但不会改变"丢包即收缩"的范式。
4. 单流有本机天花板：`SO_SNDBUF`/`SO_RCVBUF` 与接收窗口自动调优的上限可能远小于 BDP，此时瓶颈在内存配置而非网络。
5. 并发多流的收益是乘性的（各自独立 cwnd），但受接收端处理能力、磁盘与链路公平性约束，不是越多越好。

### 常见误区

1. 认为"带宽买够了吞吐自然上去"——带宽只是上限，BDP 与丢包率才决定单流能达到多少，这是本题最核心的错判。
2. 把 `cwnd` 和 `rwnd` 混为一谈——丢包后 cwnd 会掉，rwnd 不会；如果排查时只调接收缓冲，发送侧的丢包收缩完全不受影响。
3. 用 `iperf` 单流结果给链路定性——单流测出的是"这条路径上单条 TCP 的命运"，多流、UDP、应用层分块并行会给出完全不同的结论。

### 延伸学习

1. RFC 5681 *TCP Congestion Control*（cwnd/rwnd、慢启动、拥塞避免、快速重传与快速恢复的规范文本，本轮已核验 §2/§3）：https://www.rfc-editor.org/rfc/rfc5681
2. RFC 9438 *CUBIC for Fast and Long-Distance Networks*（现行标准，明确 CUBIC 为 Linux/Windows/Apple 默认并更新 RFC 5681，本轮已核验摘要）：https://www.rfc-editor.org/rfc/rfc9438

### 追问

那是不是把拥塞控制换成 BBR 就解决问题了？——回答要点：BBR 绕开"丢包即拥塞"的误判，在随机丢包的长链路上确有大收益，但它需要两端可控、依赖 pacing 与足够的发送缓冲，且与 CUBIC 流共存时公平性存在争议；另外它解决的是"算法如何解释丢包"，不解决"本机 socket 缓冲小于 BDP"这一层天花板。正确说法是分层排查：先看窗口是否被本机缓冲卡住，再看算法如何解释丢包，最后才是链路本身。

## B02 什么时候该停：Agent 循环的终止条件与无进展检测

**题目 ID**：Q-20261126-B02 ｜ 一级类型：AI Agent 核心 ｜ 二级主题：Agent 状态、规划、执行和反馈——循环终止与无进展检测 ｜ 标签：Agent 循环、终止条件、无进展检测、预算

### 题目

面试官问：一个 ReAct 风格的 Agent 在循环里执行"思考 → 调工具 → 观察"。请说明这个循环有哪几类终止方式，每一类的判定责任应该落在哪一层；为什么"让模型自己说完成了"不能作为唯一的完成判据；以及在工程上如何识别"看起来在推进、实际在原地打转"。

### 先思考

1. 一个 while 循环必须有退出条件。Agent 循环的退出条件能分成哪几类：达成了、花完了、卡住了、需要人？
2. 模型输出 "DONE" 或 "任务已完成" 时，它提供的是"事实"还是"主张"？这两者对编排层意味着什么不同处理？
3. 如果只看步数上限，会发生什么：设 100 步，绕圈的 Agent 花 100 步的钱再失败；设 5 步，正常任务被腰斩。有没有比步数更接近"进展"的量？

### 参考答案

**定义**：Agent 循环是一台状态机，每轮由"模型提议下一步动作"与"运行时执行并回填观察"两部分组成。终止条件分五类：**达成**（任务目标被验证满足）、**预算耗尽**（步数 / token / 时长 / 成本）、**无进展**（动作或状态重复、目标集合不再缩小）、**阻塞**（缺权限、缺人工输入、外部依赖不可用）、**不可恢复错误**（结构性失败，重试无意义）。这五类必须映射到**互不相同的终态**，因为它们的下游处置完全不同：达成要交付、预算耗尽要降级或转人工、无进展要带诊断上报、阻塞要挂起等待、错误要告警。

**适用边界**：终止判定属于**编排层**，不属于模型。模型能做的是提议动作、给出自评；它无法可靠判定"目标是否真的被满足"，因为判定需要外部事实（工具返回的业务状态、断言结果），而模型只看到自己上下文里的文本。反过来，纯确定性的编排层也无法独立判断"语义上是否完成"——开放式任务（写一份竞品分析）没有可断言的成功条件，这类任务只能退化为"人工验收"或"结构化自评 + 抽样复核"。**边界由此划出：可断言的任务用验证器终止，不可断言的任务用人工或抽样终止，两者都不能只靠模型自述。**

**示例**：检索类子任务中，Agent 因为结果排序抖动对同一查询连续调用三次 `search_docs`，参数完全一致。第一次返回 10 条、第二次返回 10 条但顺序不同、第三次相同。模型把"结果不同"理解为"还有新信息"，继续换措辞检索。若编排层维护**动作指纹**（工具名 + 归一化参数）并统计重复率，第二轮就能判定"同一指纹重复 3 次且新增证据 id 为 0"，直接以 `no_progress` 终止并附上已收集的证据清单——这比让它跑到 40 步再报"未能完成"有价值得多。

**相近概念区别**：
- **超时 vs 终止条件**：超时是时间维度的外部切断，终止条件是任务维度的判定；只有超时的系统无法区分"慢"与"卡住"。
- **单步重试 vs 循环终止**：重试作用在一次工具调用上（同一动作再试），终止作用在整条轨迹上（不再继续这个方向）。
- **预算耗尽 vs 无进展**：预算耗尽是被动花完，无进展是主动识别；前者是最后防线，后者是主要机制。把 max_steps 当唯一机制，等价于用"钱花完了"代替"发现走错了"。
- **模型自评 vs 验证器**：自评是概率性主张，验证器是对外部状态的确定性断言；前者可用于生成候选终态，不能用于签发终态。

**典型应用（Agent 系统）**：编排层维护三样确定性状态——预算账本（步数 / token / 时长 / 成本四本账，任一触顶即进 `budget_exhausted`）、动作指纹表（工具 + 归一化参数 + 结果摘要哈希）、目标集合（把任务分解为可勾选的子目标，每轮标记关闭了哪些）。模型只负责"下一步做什么"与"建议终止"，编排层负责"是否允许终止"。终态是**一等输出**：`succeeded / partial / needs_input / no_progress / failed`，每个终态都必须带结构化诊断（已完成子目标、未完成原因、可复用产物引用），否则下游只能笼统报"Agent 失败了"。

**面试现场回答**：Agent 循环有五类终止——达成、预算耗尽、无进展、阻塞、不可恢复错误，它们必须是五种不同终态。完成判定不能交给模型自述，因为模型只看得见上下文文本，看不到外部世界是否真的变了；可断言任务用验证器（业务状态查询、断言、schema 校验）签发成功，不可断言任务用人工或抽样。识别原地打转靠三个确定性信号：动作指纹重复率、目标集合是否还在缩小、新增证据数是否为零。max_steps 只是最后防线，不是策略。

### 关键点

1. 终止有五类且必须映射为不同终态：达成 / 预算耗尽 / 无进展 / 阻塞 / 不可恢复错误，混成一个 `failed` 就丢失了全部处置信息。
2. 完成判据必须是外部可验证的事实（工具返回的业务状态、断言、schema），模型自述只能作为"申请终止"的提议。
3. 无进展检测的三个信号：动作指纹重复、状态哈希不变、目标集合不再缩小；步数不是进展的度量。
4. 预算要分账（步数 / token / 时长 / 成本），任一项触顶即终止，且预算传导到每一步的工具超时。
5. 终态必须携带可复用产物与诊断，否则转人工的成本等于重新做一遍。

### 常见误区

1. 用"如果任务完成请输出 DONE"作为主要终止机制——提示词是指引层，模型对"是否真的完成"的判断是概率性的，且极易被"我调用了工具"误当成"工具达成了目标"。
2. 把 `max_steps` 设成 100 当作兜底——真实效果是"绕圈的 Agent 花满预算再失败"，成本与时延都按最坏情况计费，而正常任务仍在被腰斩的边缘。
3. 把"无进展"和"失败"合并成一个终态——前者意味着"方向错了、证据还在"，后者意味着"确实做不到"；合并后既无法做自动重规划，也无法给人工一个有价值的交接包。

### 追问

怎么区分"还在推进但很慢"和"原地打转"？——回答要点：用进展量而不是步数。可用的进展量包括：新增证据 id 数、已关闭子目标数、状态机所处阶段是否前移、连续两个检查点之间的状态哈希是否变化。慢但推进的轨迹里这些量单调改善；打转的轨迹里它们长期为零而动作指纹重复率上升。两个信号同时出现才降级为 `no_progress`，只出现一个时给"减速提示"而不是终止，避免误杀长尾任务。

## S01 第三方后台改版后成功率从 96% 掉到 41%：浏览器 Agent 的定位、断言与幂等

**题目 ID**：Q-20261126-S01 ｜ 一级类型：工具与互操作协议（兼属 AI Agent 核心）｜ 二级主题：工具执行的可验证性——浏览器自动化的定位、断言与写操作幂等 ｜ 标签：浏览器自动化、可访问性树、断言、写操作幂等

### 题目

一家 SaaS 公司让 Agent 代客在 30 个第三方后台（供应商门户、物流系统、政务申报）执行任务：查运单、改收货地址、提交工单。这些系统都没有 API，只能用浏览器自动化。当前架构是 Playwright + 视觉模型兜底：模型看页面快照决定点哪里，用 CSS 选择器定位元素，找不到就交给视觉模型按坐标点击。

系统规模：日均 4.2 万次任务、30 个站点、单任务平均 12 步、每步 P95 延迟 2.3 秒、视觉兜底占比 9%。

最近一周出现三类问题：

1. **某供应商改版**：class 名全部哈希化、按钮从 `<a>` 改成 `<div>` 加 `role="button"`，该站点成功率从 96% 掉到 41%，失败几乎全部是"找不到元素"。
2. **静默未提交**：另一个站点成功率没掉，但客户投诉"Agent 说提交成功，后台没有记录"。抽查发现表单有必填校验未通过，页面停在原地，Agent 因为"点击后页面有变化（出现了红色提示）"而判定成功。
3. **重复提交**：网络抖动导致一次提交超时，Agent 重试后同一工单提交了两次，产生两条重复工单。

约束：不能要求第三方提供 API；每步延迟预算 P95 ≤ 3 秒；视觉模型每步成本约为 DOM 解析的 40 倍；合规要求所有写操作可追溯到具体页面状态与参数。

请给出改造方案：定位策略怎么分层、如何判定"操作真的生效"、写操作如何做到不重复，并说明哪些能力属于模型、哪些属于编排层、哪些属于确定性系统。

### 先思考

1. 三个故障分别对应哪一层缺失：定位的稳定性（绑定 DOM 结构）、完成的判定（把"有变化"当"成功"）、副作用的边界（超时即重试）？
2. 改版后"元素还在、只是换了标签"，说明定位应该绑定什么——DOM 结构、文本、还是用户与辅助技术感知到的角色与名称？
3. "点击成功"与"业务成功"之间隔着什么？如果一个页面没有明确的成功提示，你还能用什么外部事实来判定？

### 参考答案

**结论**：这一类系统失败的核心不是"模型不够聪明"，而是**把概率性的动作提议当成了确定性的执行结果**。改造方向是把三层职责切开：模型只负责"在语义层面决定做什么"；编排层负责"分层定位、状态等待、结果断言、幂等与重试策略"；确定性系统（浏览器协议层、断言查询、幂等台账、审计日志）负责"动作真的发生、结果真的生效、副作用真的只发生一次"。

**问题拆解**：① 41% 的失败是定位脆弱——CSS 长链绑定 DOM 结构与实现细节，改版必然断；② 静默未提交是**完成判据错**——把"页面有变化"当作成功证据，而真正的判据是业务状态；③ 重复提交是**副作用边界缺失**——超时是未知态，未知态下重试等于重复写。

**核心方案**：
1. **定位分层**：第一层用可访问性语义（role + accessible name，如 `getByRole('button', { name: '提交工单' })`），Playwright 官方文档明确建议优先 role 定位器，因为"这是最接近用户与辅助技术感知页面的方式"，并指出 CSS/XPath 会随 DOM 结构变化而失效；第二层用 label / placeholder / text / test-id；第三层才是视觉定位，且必须限流并强制"点击后状态验证"。
2. **就绪判定**：把固定 `sleep` 换成可观测状态——元素可见且可交互、网络空闲、可访问性树快照在连续两次采样中稳定。Playwright 的 locator 每次操作都重新定位最新 DOM，这解决了陈旧元素问题，但解决不了"页面还在异步渲染"的问题，所以需要显式的稳定判定。
3. **结果断言**：写操作必须以**外部事实**作为完成判据，按可靠性排序——后端数据核对（查工单是否真的存在）> 网络响应（提交请求的 2xx 与响应体）> 明确的成功态 DOM（成功页 URL、订单号出现）> 一般性的"页面有变化"（不可用）。断言失败时终态是 `unknown` 而非 `failed`。
4. **写操作幂等**：提交前生成业务幂等键（会话 + 操作指纹），写入本地幂等台账；超时后**只允许查询不允许重发**，查询确认未提交才允许重发一次；页面上无幂等能力时，靠"提交后按业务主键查询 + 台账标记"补位。重试预算按会话计，不允许无限重试。
5. **失败分类**：`locator_failed / precondition_unmet / business_rejected / unknown`，四类对应不同处置：重定位、修正前置状态、上报业务原因、查询确认。

**执行流程**：任务进入 → 编排层加载站点画像（该站点的选择器优先级、成功判据、幂等键来源）→ 每步：语义定位（role/name）→ 就绪判定 → 执行动作 → 断言（读操作断言数据出现；写操作断言业务状态）→ 失败则按四类分流 → 写操作完成后落台账与审计（页面快照哈希 + 归一化参数 + 断言结果）→ 终态回传。

**技术选型与依据**：定位首选可访问性语义（依据：Playwright 官方推荐 role 优先，且改版时角色与名称的稳定性显著高于 class；备选：test-id——最稳但要求站点配合，第三方系统不具备；备选：视觉坐标——兼容性最好但不可复现、成本 40 倍、无法解释失败）。就绪判定选显式状态等待（依据：固定 sleep 在高方差站点上既慢又不可靠）。断言选"业务侧查询优先"（依据：只有业务状态能回答"是否生效"；备选：网络响应监听——快但要求能识别提交请求，且被前端拦截时不可靠）。

**方案取舍**：核心权衡是**覆盖率与稳定性**——纯语义定位覆盖不了无语义的自绘组件（canvas、复杂表格），必须保留视觉兜底，但兜底比例越高，成功率越不可预测、成本越高；因此按站点画像配置兜底限额（如单任务视觉步数 ≤ 2），并把它作为可观测指标。第二个权衡是**自动化程度与安全性**——写操作越自动，重复与越权风险越高，因此写路径默认"断言 + 台账 + 单次重发"，高风险站点（政务申报）降级为"填表到提交前，人工点最后一下"。

**失败路径与边界条件**：定位失败——先降级到下一层定位策略，仍失败则截图 + 可访问性树快照入库（这是唯一能让改版修复变成"看图改选择器"的资产）；前置状态不符（如账户被锁）——立即终止为 `precondition_unmet`，不要反复重试；业务拒绝（校验提示）——解析提示文本回传，不重试；超时——进 `unknown`，只查询不重发。**超时**：每步独立超时 + 任务级 deadline，deadline 剩余时间成为该步超时上限。**重试**：读操作指数退避 + 抖动 + 上限 3 次；写操作只在"确认未提交"后重发一次。**幂等**：幂等键 = 会话 ID + 操作指纹（站点 + 动作 + 归一化参数），台账唯一约束保证同一键只落一条。**恢复**：任务中断后凭台账续跑，已完成的子步骤直接返回既有结果，不重复点击。

**安全、成本、延迟与可靠性**：安全——所有写操作审计记录"页面快照哈希 + 归一化参数 + 断言依据"，凭证按站点隔离存储且不进入模型上下文；表单内容做敏感字段白名单，避免把客户身份证号写进轨迹。成本——视觉兜底从 9% 压到 3% 以下可省约三成推理成本（视觉单步成本约 40 倍）。延迟——语义定位单步 200 ms 量级，视觉兜底单步 2 秒量级，兜底比例直接决定 P95。可靠性——把"断言通过率"与"静默错误率"分开监控，后者只能靠人工抽检 + 客户投诉回流。

**验证指标与观测**：按站点 × 步骤的失败率（定位失败、断言失败分开）、断言通过率、**静默错误率**（人工抽检中"Agent 报成功但业务未生效"的比例，目标 0）、重复提交率（业务侧按主键去重计数）、视觉兜底比例、单任务 P95 延迟、每站点"改版检测时延"（从上版到选择器修复的小时数）。

**能力归属**：模型承担"看语义快照决定下一步做什么、从自然语言指令映射到页面元素意图"（概率性）；编排层承担定位策略分层、就绪判定、断言选择、幂等键生成、重试与预算（Agent 编排能力）；浏览器协议层的 auto-wait、可访问性树、网络响应监听，以及幂等台账的唯一约束与审计日志，是传统确定性系统——**"只提交一次"这件事的最终防线是唯一约束，不是提示模型"小心不要重复"**。

### 关键点

1. 定位绑定"用户与辅助技术感知到的角色与名称"，而不是 DOM 结构；CSS 长链与坐标点击都是脆弱的最后一层。
2. "点击成功""页面有变化"都不是完成判据；写操作的完成判据必须是外部事实（业务状态查询或提交响应），失败时终态是 `unknown` 而非 `failed`。
3. 超时是未知态：写操作在未知态下只查询不重发，重发前必须确认未提交，且只允许一次。
4. 幂等的最终防线是台账唯一约束 + 业务主键核对，页面的"防重复点击"只是 UX 层面的缓解。
5. 视觉兜底是覆盖率工具不是稳定性工具：必须限额、必须带"点击后状态验证"、必须计入成本与可观测指标。

### 常见误区

1. 用"页面有变化"作为成功证据——校验失败的红色提示同样是"页面有变化"，这正是静默错误的来源；判据必须区分"变化"与"目标状态成立"。
2. 认为改版是不可抗力、只能靠视觉兜底硬扛——语义定位 + 改版检测 + 快照资产可以把修复从"重新调 prompt"变成"改一行选择器"，41% 这类断崖是定位策略的单点依赖造成的。
3. 用重试解决提交超时——超时不等于未提交，无幂等键的重试就是重复写；对第三方系统尤其危险，因为重复工单往往无法撤回。

1. Playwright 官方文档 *Locators*（role 优先、CSS/XPath 不推荐的理由、auto-waiting 与 strictness，本轮已核验）：https://playwright.dev/docs/locators
2. Playwright 官方文档 *Auto-waiting / Actionability*（元素可交互判定的具体条件，是"就绪判定"的确定性依据）：https://playwright.dev/docs/actionability （本轮未逐字核验正文）

### 追问

1. 为什么不干脆全用视觉模型，人怎么做它就怎么做？——要点：视觉坐标不可复现（分辨率、滚动位置、动态内容都会改变命中点），单步成本约 40 倍，失败无法归因（说不清是"没看见"还是"点错了"）；更关键的是它绕过了可访问性语义这一层确定性信息，等于把"元素身份"也交给了概率模型。正确做法是语义优先、视觉兜底并限额。
2. 第三方站点完全没有语义标注（`div` 满屏、无 label），怎么办？——要点：先看可访问性树的退化形态（很多"无语义"页面仍有文本与层级），用文本 + 结构 + 相对锚点组合定位；仍不行则用视觉定位但必须"点击后状态验证 + 单步限额 + 快照留档"，并把该站点标记为高风险（写操作转人工确认）。这属于覆盖率换稳定性的显式取舍，不能默认它能自动收敛。
3. 客户说"Agent 报成功但没生效"，你怎么在 10 分钟内定位？——要点：取该任务的审计记录，按三步排：① 断言依据是什么（若为"页面有变化"则判据本身不合格）；② 提交请求是否真的发出（网络日志/前端拦截）；③ 业务侧按主键查询是否存在。三步能区分"没提交""提交被业务拒绝""提交成功但下游异步失败"，第三种必须靠业务侧对账而不是页面。

### 小型实践

用 30-60 分钟搭一个最小对照实验：本地起一个含必填校验的提交表单页，写两个执行器——A 用 CSS 长链 + 固定 `sleep(1)` + "页面有变化即成功"；B 用 role/name 定位 + 状态等待 + "提交后查询列表确认新记录"作为断言。然后人为改版（把按钮从 `<button>` 换成带 `role="button"` 的 `<div>`、给容器加一层 wrapper），对比两版在 20 次提交中的成功率、静默错误率（页面无变化但报成功 / 有变化但未落库）与耗时。最后加一次"提交接口延迟 3 秒"的注入，观察两版在超时下的行为差异——B 版应当只查询不重发。

## S02 limit 2Gi、监控 1.2Gi，Pod 却反复 OOMKilled：容器内存计量与观测错位

**题目 ID**：Q-20261126-S02 ｜ 一级类型：操作系统与网络（兼属软件工程与平台工程）｜ 二级主题：容器资源限制与进程隔离——cgroup 内存计量、OOM 判定与观测口径 ｜ 标签：cgroup v2、OOMKilled、page cache、working set

### 题目

一个文档处理服务跑在 Kubernetes 上，职责是接收 PDF、抽取文本、分块后写入检索库。容器 `resources.limits.memory = 2Gi`，副本数 12，日均处理 8 万份文档，单份 PDF 平均 6 MB、最大 300 MB。

现象：过去两周该服务每天有 3-8 个 Pod 被 `OOMKilled`（exit code 137）。但 Grafana 上的容器内存面板（取自 `container_memory_working_set_bytes`，15 秒采样）显示这些 Pod 被杀前一直稳定在 1.1-1.3 Gi，从未接近 2 Gi。同期同节点上的其他服务出现过一次 `MemoryPressure` 驱逐，运维怀疑"内存泄漏"，但 `tracemalloc` 与运行时堆指标都正常。

已知额外信息：解析并发数配置为 8；服务会先把上传文件落到临时目录再读取；临时目录位于挂载的 `emptyDir` 且 `medium: Memory`；团队为了"省 IO"把 Node 的 `--max-old-space-size` 设成了 1.5 Gi。

请给出根因分析路径、止血方案与根治方案，并说明为什么监控看到的数字与 OOM 判定依据会不一致。

### 先思考

1. 先分清三个量：进程 RSS、cgroup 的 `memory.current`、监控面板的 working set。它们各自统计什么、谁包含 page cache、谁是派生量？
2. OOM killer 的触发条件是"某个数字超过上限"还是"内存无法再回收"？`memory.high` 与 `memory.max` 的行为差在哪？
3. 8 路并发 × 单份最大 300 MB 的全量读入，和 2 Gi 的限制之间是什么关系？15 秒采样能看见多长的尖峰？

### 参考答案

**结论**：根因不是内存泄漏，而是**计量对象与观测对象错位**。OOM 判定依据是 cgroup 的 `memory.max` 与"不可回收内存"，而监控面板上的 working set 是一个派生量（且被 15 秒采样平滑掉）；同时服务的真实峰值内存由"并发数 × 单文件全量读入 + 堆外缓冲 + tmpfs"决定，瞬时越过 2 Gi 后由内核直接杀进程。四件事叠加：堆内指标正常（堆外涨）、page cache 与 tmpfs 计入 cgroup（RSS 不含或归属不同）、峰值是秒级尖峰（采样错过）、`--max-old-space-size` 只约束堆（不约束 Buffer 与外部内存）。

**问题拆解**：
1. **观测层**：15 秒采样对齐不上秒级尖峰；`working_set` 是 `usage - inactive_file` 的估算，用于驱逐与调度决策，不是 OOM 的判定输入；面板看的是容器维度，而 OOM 计数在 `memory.events`。
2. **计量层**：cgroup v2 的 `memory.current` 统计"该 cgroup 及其后代当前使用的内存总量"，内核文档明确指出追踪对象包括**页缓存与匿名内存**（"Userland memory - page cache and anonymous memory."）；`memory.max` 达到且无法回收时在 cgroup 内触发 OOM killer，`memory.high` 只是节流加重回收压力、**永不触发 OOM**。
3. **应用层**：8 路并发、单份最大 300 MB 全量读入，加上解析中间表示与堆外 Buffer，峰值可达数 GB；`--max-old-space-size=1.5Gi` 只限制 V8 堆，Buffer 分配在堆外，堆指标看起来很健康。
4. **节点层**：kubelet 的 `memory.available` 定义为 `node.status.capacity[memory] - node.stats.memory.workingSet`，并**显式排除 inactive_file**，因为假设这部分在压力下可回收；这意味着 tmpfs 与大量 page cache 会把节点层面推向 `MemoryPressure`，触发与容器 OOM 不同的第二套机制。

**核心方案**：
- **止血**：① 把解析并发从 8 降到 2-3，并对单文件大小设上限（例如 > 50 MB 走异步队列），直接压掉峰值；② 把 `emptyDir` 的 `medium: Memory` 改为磁盘（或改用 `ephemeral-storage` 配额），消除 tmpfs 计入 cgroup 的这部分；③ 临时把 limit 提到 4Gi 并确认节点可分配余量，同时补上 `memory.high = 3Gi` 做软闸门（超限先节流、给回收与告警留时间，而不是直接被杀）；④ 对已 OOM 的 Pod 关闭无意义的重启风暴：把任务做成可重入，重启后按任务幂等键续跑。
- **定位**：在容器内高频采集 `memory.current`、`memory.stat`（`anon` / `file` / `inactive_file` / `active_file`）、`memory.events`（`oom` 与 `oom_kill` 计数），与业务指标（并发数、单文件大小、解析阶段）对齐时间轴；同时打开内核 OOM 日志，确认被杀进程与当时的 `anon`/`file` 构成。判据是：若 `oom_kill` 增长与"并发峰值"同步而 `anon` 无单调上升趋势，则不是泄漏，是峰值超限。
- **根治**：① 改为**流式解析**（分页读取、边解析边落盘/落块），把"单文件全量在内存"改为"有界缓冲"；② 加**背压**：并发由队列深度与内存水位共同控制，水位高时拒绝新任务而不是继续堆积；③ 显式设置堆外内存预算（单任务缓冲上限 × 并发数 ≤ limit 的 60%），把"内存模型"写进配置而不是靠默认值；④ 把重解析任务与在线服务拆成两个工作负载（不同 limit、不同节点池），避免批处理峰值影响在线 SLA。

**执行流程**：告警（`oom_kill` 增长）→ 取该 Pod 的 `memory.stat` 快照与业务时间轴对齐 → 判定"峰值超限"还是"单调增长" → 峰值超限走并发与流式改造，单调增长走堆外/句柄排查（`smaps`、`memory.stat` 的 `anon` 增长）→ 灰度一个副本验证峰值 → 全量 + 补 `memory.high` 闸门与 OOM 告警。

**技术选型与依据**：软闸门选 `memory.high`（依据：官方文档明确 "Going over the high limit never invokes the OOM killer"，适合做节流与告警；备选：仅靠 `memory.max`——只有杀与不杀两态，没有缓冲带）；观测选 cgroup 原生文件 + 高频旁路采集（依据：`memory.events` 是 OOM 的唯一权威计数，面板派生量会失真；备选：仅用 `container_memory_working_set_bytes`——采样与派生双重失真）；临时文件选磁盘（依据：tmpfs 占的是内存且计入 cgroup，等于把磁盘问题转成内存问题）。

**方案取舍**：核心权衡是**吞吐与内存安全**——并发 8 换成 2 会让单副本吞吐下降约 4 倍，需要靠增加副本或异步队列补回；另一组权衡是**延迟与内存峰值**——流式解析把峰值压到常数级，但引入更多 IO 与更长的单任务时延，对交互式接口需要另设通道。还有**限制强度与故障形态**的权衡：`memory.max` 硬杀干净但丢任务，`memory.high` 节流温和但会拖慢请求，生产上应两者并用（high 做闸门、max 做兜底）。

**失败路径、边界条件、超时、重试、幂等与恢复**：OOM 后重启会导致在途任务丢失——任务必须落库并有幂等键（文档 ID + 解析版本），重启后按未完成状态续跑，避免重复入库；`OOMKilled` 期间的请求要快速失败而不是排队（否则重启后瞬间被压垮，形成重启风暴）；`emptyDir` 上的临时文件在 Pod 重建后消失，续跑逻辑必须能重新拉取源文件；若节点同时触发 `MemoryPressure` 驱逐，kubelet 不遵守 PDB 与 `terminationGracePeriodSeconds`，需要在应用侧保证"任何时刻被杀都不损坏数据"（写入先临时文件再原子 rename）。**超时**：解析单任务超时与背压联动，超时任务进重试队列但带次数上限。**重试**：仅对可重试错误（IO 抖动、下游 5xx）退避重试，解析失败（损坏 PDF）不重试。

**安全、成本、延迟与可靠性**：安全——对上传文件做大小/页数/嵌套对象上限校验（防 zip bomb 与超深结构），临时文件按任务隔离并在完成后清理；成本——把 tmpfs 换成磁盘会带来 IO 成本，但省下的内存 allow 更高副本密度；延迟——流式解析单任务时延上升，但 P99 更可预测；可靠性——`memory.high` 节流让系统在压力下"变慢"而不是"变死"，配合 OOM 告警形成两级保护。

**验证指标与观测**：每容器 `memory.current` 的 P99 与峰值（不是均值）、`memory.events` 的 `oom_kill` 计数（目标 0）、`memory.stat` 中 `anon` 与 `file` 的比例趋势、任务成功率与重试率、单任务峰值内存分布（按文件大小分桶）、节点 `memory.available` 与 `MemoryPressure` 事件数。

**能力归属**：本题不涉及模型能力；内核的 cgroup 计量与 OOM 判定、kubelet 的驱逐判定是确定性系统行为，编排层（K8s 配置、并发与背压策略）决定的是"峰值会不会越过那条线"。把"监控显示没超"当作"不会 OOM"，本质是把派生指标当成了权威判据。

### 关键点

1. `memory.current` 包含 page cache 与 tmpfs；RSS 与 working set 都是不同口径的视角，`memory.events.oom_kill` 才是 OOM 的权威计数。
2. OOM 的触发条件是"达到 `memory.max` 且无法回收"，不是"某个指标超过阈值"；`memory.high` 只节流不杀。
3. working set 是派生量（usage 减 inactive_file），15 秒采样会错过秒级尖峰——"面板没超"与"没超"是两件事。
4. `--max-old-space-size` 只约束堆；Buffer/外部内存/解析中间表示在堆外，堆指标健康不代表进程健康。
5. tmpfs 用的是内存且计入 cgroup，`emptyDir medium: Memory` 等于把磁盘压力转成内存压力。

### 常见误区

1. 认定"监控没到 limit 就是泄漏排查问题"，于是去查堆——真正该查的是峰值与堆外；堆指标正常恰恰是这类故障最典型的误导信号。
2. 直接调大 limit 了事——峰值来自"并发 × 单文件全量"，调大只是把阈值推后，下一次文件更大、并发更高时照样触发；且挤占节点可分配内存，把容器 OOM 换成节点驱逐。
3. 只设 `memory.max` 不设 `memory.high`——系统只有"正常运行"和"被杀"两态，缺少节流与告警的缓冲带，故障总是以最剧烈的方式出现。

### 延伸学习

2. Kubernetes 文档 *Node-pressure Eviction*（`memory.available` 的定义、working set 与 inactive_file 的排除规则、硬/软驱逐阈值，本轮已核验）：https://kubernetes.io/docs/concepts/scheduling-eviction/node-pressure-eviction/

### 追问

1. 为什么 `working_set` 不能作为 OOM 判据？——要点：它是为调度与驱逐决策设计的派生估算（usage 减 inactive_file），假设 inactive_file 在压力下可回收；但"可回收"不等于"已被回收"，在回收跟不上分配的瞬间，cgroup 仍会按 `memory.max` 杀进程。判据与观测是两个不同的问题，混用就会得出"没超限却被杀"的悖论。
2. `memory.high` 和 `memory.max` 应该怎么分工？——要点：high 是主控手段，超限即节流并加重回收压力，用来把"内存紧张"变成"变慢 + 告警"；max 是兜底，达到且无法回收才杀。生产上 high 设在 max 的 80-90%，让系统在触底前有可观测的缓冲带，同时 high 的持续超标要作为独立的告警信号。
3. 同一时刻容器 OOM 与节点驱逐可能同时发生，怎么区分责任？——要点：容器 OOM 由该 cgroup 的 `memory.max` 触发，只杀本 cgroup 内的进程，证据是 `memory.events.oom_kill` 与容器 exit 137；节点驱逐由 kubelet 按 `memory.available`（capacity 减 working set）判定，证据是 Node condition `MemoryPressure` 与 Pod 的 `Evicted` 状态。两者可以并存：容器把节点内存吃紧，节点又驱逐其他 Pod——所以既要给容器设 limit，也要给节点留出系统预留（`system-reserved` / `kube-reserved`）。

## L01 LeetCode 304. 二维区域和检索 - 矩阵不可变

**题目 ID**：Q-20261126-L01 ｜ LeetCode 题号：304 ｜ 中文名：二维区域和检索 - 矩阵不可变 ｜ 英文名：Range Sum Query 2D - Immutable ｜ 难度：medium ｜ 一级类型：二维前缀和 + 容斥 ｜ 标签：前缀和、容斥原理、设计题

### 题目

**官方链接（已核验）**：https://leetcode.cn/problems/range-sum-query-2d-immutable/ （题面、示例与提示于本轮从官方页面核验；页面难度标签未渲染，medium 按官方分类记录）

给定二维矩阵 `matrix`，需要支持多次查询：计算左上角为 `(row1, col1)`、右下角为 `(row2, col2)` 的子矩阵元素总和。

实现 `NumMatrix` 类：

- `NumMatrix(int[][] matrix)`：用整数矩阵初始化；
- `int sumRegion(int row1, int col1, int row2, int col2)`：返回该子矩阵的元素总和。

**输入**：构造时给定 `matrix`；查询给定四个下标。**输出**：子矩阵元素和（整数）。

**约束（官方提示，页面渲染时上标丢失，此处按 10 的幂还原）**：`m == matrix.length`，`n == matrix[i].length`，`1 <= m, n <= 200`，`-10^5 <= matrix[i][j] <= 10^5`，`0 <= row1 <= row2 < m`，`0 <= col1 <= col2 < n`，最多调用 `10^4` 次 `sumRegion`。

**示例（官方，已核验）**：

```
matrix = [[3,0,1,4,2],
          [5,6,3,2,1],
          [1,2,0,1,5],
          [4,1,0,1,7],
          [1,0,3,0,5]]
sumRegion(2,1,4,3) -> 8
sumRegion(1,1,2,2) -> 11
sumRegion(1,2,2,4) -> 12
```

### 先思考

1. 一维前缀和能 O(1) 求区间和，二维能不能类比？先想清楚 `P[i][j]` 应该定义成"哪个矩形"的和。
2. 用 `P` 表达任意子矩形时，会多算哪块、少算哪块？画四个角，看它们如何组合成"整块减两条带再加回重叠角"。
3. 如果 `P` 只开 `m × n`，查询和构造时要不要处处判 `i-1 >= 0`？有没有一种写法让边界判断彻底消失？

### 参考答案

**解题思路（推荐解法：多开一行一列的二维前缀和 + 容斥）**：定义 `P` 为 `(m+1) × (n+1)`，`P[i][j]` 表示原矩阵中前 `i` 行、前 `j` 列（即左上角 `(0,0)` 到 `(i-1,j-1)`）的元素和，第 0 行与第 0 列全为 0。构造递推 `P[i][j] = P[i-1][j] + P[i][j-1] - P[i-1][j-1] + matrix[i-1][j-1]`；查询 `sumRegion(r1,c1,r2,c2) = P[r2+1][c2+1] - P[r1][c2+1] - P[r2+1][c1] + P[r1][c1]`。多出的那一行一列把"下标可能越界"变成"下标自然落到 0"，边界判断因此消失——这是本题真正的工程价值，而不是背公式。

**正确性说明**：设 `S(r1,c1,r2,c2)` 为闭区间子矩阵和。`P[r2+1][c2+1]` 是 `S(0,0,r2,c2)`；减去上方的 `S(0,0,r1-1,c2)` 与左方的 `S(0,0,r2,c1-1)` 后，左上角的 `S(0,0,r1-1,c1-1)` 被减了两次，因此加回一次，得到 `S(r1,c1,r2,c2)`。当 `r1 = 0` 或 `c1 = 0` 时，被减项落在第 0 行/列，值为 0，公式依然成立——这正是 padding 的作用。构造递推同理：`P[i-1][j] + P[i][j-1] - P[i-1][j-1]` 是"上方块 + 左方块 - 重叠块"，再加当前元素。

**复杂度**：构造 O(m·n) 时间、O(m·n) 空间；单次查询 O(1)；总时间 O(m·n + q)，空间 O(m·n)。

**Python 参考代码**：

```python
class NumMatrix:
    def __init__(self, matrix: list[list[int]]):
        m = len(matrix)
        n = len(matrix[0]) if m else 0
        # P[i][j] = 前 i 行、前 j 列的元素和；第 0 行/列全 0，消除边界判断
        self.P = [[0] * (n + 1) for _ in range(m + 1)]
        for i in range(1, m + 1):
            row_acc = 0
            for j in range(1, n + 1):
                row_acc += matrix[i - 1][j - 1]
                self.P[i][j] = self.P[i - 1][j] + row_acc

    def sumRegion(self, row1: int, col1: int, row2: int, col2: int) -> int:
        P = self.P
        return (
            P[row2 + 1][col2 + 1]
            - P[row1][col2 + 1]
            - P[row2 + 1][col1]
            + P[row1][col1]
        )
```

构造里用 `row_acc` 累加当前行前缀，等价于 `P[i-1][j] + P[i][j-1] - P[i-1][j-1] + matrix[i-1][j-1]`（因为 `P[i][j-1] - P[i-1][j-1]` 恰是上一列为止的本行前缀和），少一次二维下标读写，且不改变复杂度。

**关键边界情况**：`m = n = 1` 的单元素矩阵（`sumRegion(0,0,0,0)` 必须等于该元素，包括负数）；全负数矩阵（前缀和不再是单调量，任何"用单调性推断"的直觉都失效）；单行或单列矩阵（`r1 == r2` 或 `c1 == c2`，容斥仍然成立）；最大规模 `200 × 200` 且元素全为 `10^5` 时总和为 `4 × 10^9`，**超出 32 位有符号整数范围**，Python 无虞，但用 C++/Java 实现时前缀和必须用 `long`/`long long`，这是本题最容易在真实工程里翻车的点（面试官常以此为追问）；官方历史用例中存在空矩阵输入，`matrix = []` 需返回 0 而非抛异常。

**测试用例（3 个）**：

1. 官方示例矩阵：`sumRegion(2,1,4,3) = 8`，`sumRegion(1,1,2,2) = 11`，`sumRegion(1,2,2,4) = 12`（三个不同形状，覆盖整块/中方块/横条）。
2. `matrix = [[-1]]`：`sumRegion(0,0,0,0) = -1`（单元素 + 负数，检查 padding 与符号）。
3. `matrix = [[1,-2],[3,4]]`：`sumRegion(0,0,1,1) = 6`，`sumRegion(1,1,1,1) = 4`，`sumRegion(0,1,0,1) = -2`（含负数的全矩阵/右下角/负单格）。

**可迁移解题能力**：把"区间查询"从"每次重算"转成"预计算 + O(1) 组合"，是一类通用优化范式；容斥的四个项对应"整块减两条带加回重叠"，可用二维文氏图记忆；而"多开一行一列消除边界判断"是设计题里最值得带走的实现技巧——它把正确性从"每个分支都写对"降级为"公式写对一次"。

### 关键点

1. `P[i][j]` 的定义是"前 i 行前 j 列"，不是"包含 `(i,j)`"；定义错一位，后面四个下标全错。
2. 查询是"整块 − 上带 − 左带 + 重叠角"，四项的符号固定为 `+ - - +`，加回的那一项最容易漏。
3. 多开一行一列让 `r1 = 0` 或 `c1 = 0` 自然退化为 0，边界判断消失，这是实现层的核心技巧。
4. `200 × 200 × 10^5 = 4 × 10^9` 超过 int32，前缀和数组必须用 64 位整数。
5. 构造 O(mn)、查询 O(1)，一共 `10^4` 次调用时预计算是压倒性优势；若查询次数远小于 `mn`，暴力反而更省。

### 常见误区

1. 用 `m × n` 的前缀和数组并在四处写 `max(i-1, 0)` 之类的边界补丁——能过但极易在某个分支写错符号，且读代码的人无法验证正确性；padding 写法把这类错误从"分散在四处"收敛到"集中在一处"。
2. 把 `P[i][j]` 定义成"以 `(i,j)` 结尾的矩形和"——定义偏差导致查询公式必须整体改写，是本题最常见的思路性错误。
3. 认为"元素都是正数所以前缀和单调"——约束允许负数，任何基于单调性的剪枝或提前返回都是错的。

### 追问

如果矩阵会更新（单点修改 + 区域查询），这套方案还成立吗？——回答要点：不成立，`O(mn)` 的重建让每次更新都不可接受。此时应换二维树状数组（BIT）或二维线段树，单点更新与区域查询都是 `O(log m · log n)`；也可以按行做一维 BIT 的嵌套。判断依据是"更新次数 × 查询次数"的量级对比，而不是哪个数据结构更高级——这正是本题"预计算 vs 在线计算"取舍的延伸。

## 当日重点

1. **吞吐由"窗口能否填满 BDP"与"丢包如何被解释"决定，不是带宽**——1 Gbps × 200 ms 的 BDP 是 25 MB，8 Mbps 只对应约 137 个段在途；0.01% 的丢包在 Mathis 近似下就把单流压在个位数 Mbps。工程解是并发多流、放大缓冲、必要时换 BBR、缩短 RTT。
2. **Agent 循环的终止必须是五种终态，而不是一个 `failed`**——达成、预算耗尽、无进展、阻塞、不可恢复错误对应完全不同的处置；完成判据要靠外部可验证事实，模型自述只能作为申请。
3. **"点击成功"不是"业务成功"**——浏览器 Agent 的完成判据必须是外部事实（业务查询 > 提交响应 > 成功态 DOM），超时是未知态、只查询不重发；幂等的最终防线是台账唯一约束。
4. **OOM 判定依据与监控指标是两个口径**——`memory.current` 含 page cache 与 tmpfs，working set 是派生量、15 秒采样会错过峰值，`memory.events.oom_kill` 才是权威计数；`--max-old-space-size` 管不到堆外。
5. **预计算 + 容斥把区间查询降到 O(1)，代价是定义必须精确**——"前 i 行前 j 列"的定义、`+ - - +` 的符号、多开一行一列消除边界、以及 `4 × 10^9` 必须用 64 位，这四点任一错位都会让"看起来对"的代码在边界上崩掉。
