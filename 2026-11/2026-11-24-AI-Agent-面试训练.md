## B01 · 非 Agent 基础题

**题目 ID**：Q-20261124-B01　**一级类型**：数据库与存储　**二级主题**：Redis 持久化与恢复（RDB / AOF）　**难度**：基础题（中高）　**标签**：Redis、持久化、fsync、fork、COW

### 题目

团队有一个 Redis 单实例，既做缓存，也存放少量业务状态：任务执行进度、分布式锁键、幂等去重集合。一次机器重启后，业务方发现任务进度回退了约十分钟，部分锁键消失，但没有出现数据损坏。请回答：

1. RDB 与 AOF 两种持久化机制分别是什么原理，各自的丢失窗口由什么决定？
2. `appendfsync` 的三种取值（always / everysec / no）各自的持久化判定点和代价是什么？
3. 为什么官方建议即使开启 AOF，也要保留 RDB？开启 AOF + RDB 后重启时用哪个恢复？

### 先思考

1. "写入成功返回"和"数据已在磁盘上"之间隔了什么？Redis 的持久化判定点是哪条命令或哪个动作？
2. RDB 是快照：快照之间发生了什么？快照生成时主进程为什么还能继续写（fork + COW 解决什么）？
3. AOF 是命令日志：日志先写到哪里，什么时刻才真正落盘？丢失窗口和 `appendfsync` 的哪一档绑定？
4. AOF 为什么会越来越大？rewrite 解决什么？Redis 7 的 Multi Part AOF 改了文件组织方式，为什么？
5. 这家公司把"缓存"和"业务状态"混在一个实例里——持久化策略应该按什么维度分级？

### 参考答案

**结论：RDB 的丢失窗口由快照触发间隔决定（分钟级），AOF 的丢失窗口由 fsync 策略决定（everysec 默认下最坏约丢 1 秒）；持久化策略应按数据的可重建性分级，而不是全实例一刀切。**

RDB 是时点快照：Redis 按 `save <秒> <变更数>` 配置的触发点（如 `save 60 1000` 表示 60 秒内至少 1000 个键变更则触发），或手动 `SAVE` / `BGSAVE` 生成 `dump.rdb`。触发时 Redis **fork 出子进程**，由子进程把内存数据集写入临时 RDB 文件，写完后原子替换旧文件；主进程借**写时复制（COW）**继续服务写请求。因此丢失窗口 = 两次快照之间未被快照覆盖的写入，通常是"最近几分钟"；官方明确说明若按常见间隔配置，应准备好在异常停止时**丢失最近数分钟的数据**。fork 本身有代价：数据集很大且 CPU 不强时，fork 可能造成几毫秒到一秒的服务停顿。

AOF 是追加写命令日志：每条改变数据集的命令按 Redis 协议格式追加到 AOF，重启时重放重建状态。落盘时机由 `appendfsync` 决定：`always` 每次追加命令后 fsync（批量/流水线会合并为一次 fsync，"很慢很安全"）；`everysec` 每秒 fsync（默认建议值，快且相对安全，灾难时**最多丢约 1 秒写入**）；`no` 从不主动 fsync，交给操作系统（Linux 通常每 30 秒刷一次，具体取决于内核调优，丢失窗口不可控）。AOF 追加写无寻址、断电后即使结尾有半条命令也可用 `redis-check-aof` 修复。

AOF 只增不减（计数器加 100 次在数据集里只有 1 个键，日志里却有 100 条），所以需要 rewrite：后台按当前数据集生成"重建所需的最小命令集"。Redis 7.0 起使用 **Multi Part AOF**：单个 AOF 文件拆为 base 文件（rewrite 时刻的快照）+ 增量文件，由 manifest 文件登记，rewrite 失败重试有降速限制，manifest 原子替换生效。

边界与选型：同时开启 AOF + RDB 时，**重启用 AOF 重建**（官方注明它保证最完整）；官方建议两者都用，理由是 RDB 利于备份、更快重启和 AOF 引擎出 bug 时兜底，达到"与 PostgreSQL 可比的数据安全等级"；只在乎缓存可接受分钟级丢失的可以只用 RDB，纯缓存甚至可关闭持久化。本题的工程判断是：锁键、幂等集合这类业务状态要么移到同步复制的持久化存储（与 2026-11-12 S02 结论一致），要么接受 AOF everysec 的有界丢失窗口并把正确性锚点放到资源侧——不应靠"调大 fsync 频率"把 Redis 变成强持久存储。

**面试现场回答**：RDB 是 fork + COW 的时点快照，丢失窗口是快照间隔，分钟级；AOF 是命令日志，丢失窗口由 appendfsync 决定，everysec 最坏丢约 1 秒，no 交给内核不可控；AOF 靠后台 rewrite 控制体积，Redis 7 用 base + increment + manifest 的多部分组织；AOF+RDB 同开重启走 AOF。选型上按数据可重建性分级：缓存可不持久化，业务状态要么接受有界丢失并做资源侧兜底，要么换同步复制的存储——Redis 持久化给的是"有界窗口"而不是"不丢"。

### 关键点

1. 持久化的判定点是 fsync（AOF）或快照文件替换完成（RDB），不是 `SET` 命令返回成功——两者之间就是丢失窗口。
2. fork + COW 是快照服务连续性的前提，代价是 fork 停顿（大数据集毫秒到秒级）和写时的内存页复制放大。
3. `appendfsync everysec` 是默认与建议值：丢 1 秒是有界承诺；`no` 把窗口交给内核，不可作为正确性依据。
4. AOF rewrite 与 RDB 都依赖 COW；官方避免 BGSAVE 与 AOF rewrite 同时进行，防止两路重磁盘 I/O。
5. AOF + RDB 同开时重启用 AOF 重建（保证最完整）；RDB 的价值在备份、快速重启与 AOF 引擎兜底。

### 常见误区

1. **认为 everysec 等于不丢数据**：everysec 的承诺是"最坏约丢 1 秒"，磁盘写入变慢时窗口还会拉长；把强一致的写路径建立在 Redis AOF 上是错误设计。
2. **认为 fork 零成本**：快照和 rewrite 都要 fork，大实例上 fork 会造成毫秒到秒级停顿，且写高峰期 COW 复制放大内存占用——把 BGSAVE 排在流量高峰是常见事故源。
3. **只开 AOF 不留 RDB**：官方明确不鼓励——RDB 是备份、快速重启和 AOF 引擎故障时的最后手段。

## B02 · AI Agent 基础题

**题目 ID**：Q-20261124-B02　**一级类型**：上下文工程与能力封装　**二级主题**：子 Agent 结果回传与上下文污染控制　**难度**：基础题（中高）　**标签**：子Agent、结果回传、上下文污染、编排器-工作者

### 题目

什么是"子 Agent 结果回传契约"？编排器把任务分派给多个子 Agent 后，子 Agent 在自己的上下文里完成了大量工具调用与中间推理。请说明：回传给编排器的内容应该是什么、不应是什么，失败与部分完成怎么表达，以及为什么"回传的体积本身就是工程约束"。

### 先思考

1. 子 Agent 的上下文窗口是独立的：中间过程留在子 Agent 里和全部带回父上下文，对父上下文的注意力预算分别意味着什么？
2. 编排器拿到结果后要做什么决策（合并、排序、决定下一步）？这些决策需要的信息形态是"叙述"还是"结构化结论 + 引用"？
3. 子 Agent 失败了、只完成了一半，父层怎么知道？"空结果"和"失败"是一回事吗？
4. 回传内容的体积如果不设上限，几个并行子 Agent 会对主上下文造成什么？
5. 回传契约与"子 Agent 上下文隔离"是同一件事吗？隔离决定什么，回传决定什么？

### 参考答案

**定义：子 Agent 结果回传契约是编排器与子 Agent 之间关于"回传内容形态、体积上界与失败语义"的约定——回传的是蒸馏后的结构化结论、引用锚点与显式的完成状态，而不是全量轨迹。**

适用边界：适用于编排器-工作者、并行探索、Map-Reduce 式汇总等子 Agent 深度工作的架构；不适用于子 Agent 结果本身就需要人审全过程的合规场景。Anthropic 的上下文工程文章（已核验）给出的量化锚点：每个子 Agent 探索可能消耗数万 token，但只回传 **1,000–2,000 token 的浓缩摘要**；详尽的搜索上下文隔离在子 Agent 内部，主 Agent 负责综合分析——这正是对"上下文污染"（context pollution）的结构性应对。

简洁示例：深度研究任务拆给 3 个子 Agent 各读 100 页文档。回传契约要求每个子 Agent 返回：结论段（不超过 800 token）、关键引用列表（来源 ID + 段落锚点）、状态字段（completed / partial / failed + 失败原因类别）。父上下文收到约 3×1,500 token，而不是 3×80,000 token 的轨迹。

与相近概念的区别：与**子 Agent 上下文隔离**（2026-10-10 B03）不同——隔离决定"谁能看到什么"（边界划分），回传契约决定"边界上传回什么"（内容形态与体积）；与**函数返回值**不同——函数返回是确定性单值，回传内容包含概率性结论，必须带引用与不确定性标注才能被下游验证；与 **RAG 检索注入**不同——RAG 注入的是外部知识片段，回传的是子 Agent 的执行产出。

Agent 系统中的应用：它是编排器-工作者架构的核心接口设计。典型应用：(1) 并行研究/分析任务的汇总；(2) 工具密集型子任务的报告（如代码审查子 Agent 只回传问题清单与位置）；(3) 长任务的阶段性汇报。工程上通常落实为：结构化 schema（结论 / 引用 / 状态 / 统计信息）、体积硬上限（超限由子 Agent 自行蒸馏而非父层截断）、失败三态显式表达、引用锚点让父层可下钻验证。

**面试现场回答**：回传契约约定三件事——内容形态（蒸馏后的结构化结论 + 引用锚点，不是轨迹）、体积上界（子 Agent 侧自行蒸馏，Anthropic 的实践锚点是 1–2 千 token 级摘要）、失败语义（completed / partial / failed 三态显式，失败不得折叠成空结果）。隔离决定谁看到什么，回传契约决定边界上传什么；没有契约的并行子 Agent 会把父上下文的注意力预算和污染控制同时击穿。

### 关键点

1. 回传体积是硬约束：数个子 Agent 的全量轨迹回传会同时消耗父上下文的 token 预算和注意力预算，污染不随窗口大小消失。
2. 蒸馏发生在子 Agent 侧（它有完整上下文），父侧截断只会得到半截结论——蒸馏位置本身就是契约的一部分。
3. 失败与部分完成必须是一等状态：failed 折叠成空结果会让编排器把"没查到"误当"不存在"。
4. 引用锚点是可验证性的前提：没有来源 ID 的结论在父层无法下钻核对，也无法做消融评测。
5. 中间工具输出、失败尝试的原始内容默认不回传，需要时提供下钻句柄（如 evidence_id）而不是整段搬运。

### 常见误区

1. **全量轨迹回传"信息更全"**：实际上父上下文会被中间细节稀释注意力，综合质量下降；完整轨迹应留在子 Agent 的可回取存储里，而不是上下文里。
2. **子 Agent 失败静默吞掉**：父层只看到少了一个结果，无法区分"任务无产出"与"执行失败"，重试与降级决策都会失真。
3. **把回传契约当成框架自动行为**：多数框架只把子 Agent 的最终文本消息拼回父上下文，schema、体积上限、失败三态都要在编排层显式实现，不是框架送的。

### 追问

**追问：多个子 Agent 的结果汇总本身也要占预算，怎么办？**
要点：三档做法——(1) 聚合者模式：由一个专门上下文（或另一层子 Agent）负责合并，主 Agent 只接聚合结论；(2) schema 压缩：回传强制结构化字段，天然比叙述省；(3) 分批消化：编排器按阶段拉取，未进入决策视野的结果放外部存储用句柄引用。核心判断是"父上下文此刻要为哪些信息付出注意力"，与写入侧准入（2026-11-19 S01）是同一预算观的两个方向。

## S01 · AI Agent 真实研发场景题

**题目 ID**：Q-20261124-S01　**一级类型**：AI 安全与治理（兼属工具与互操作协议）　**二级主题**：写路径隐式副作用与嵌套信任域（配置 v10 新增项首次出题）　**核心考点**：成功即触发、禁用自动行为而非逐点修补、校验对象延伸到嵌套信任域　**难度**：场景题（高）　**标签**：AI 安全、git、隐式副作用、嵌套信任域、按类收敛

### 题目

你负责一个代码助手平台：内部 Agent 通过自建的 git 工具服务对托管仓库执行 `merge`、`checkout` 等写操作。平台已上线三类防线——路径限制（`--repository` 校验）、只读/写操作分级、统一网关审计打点。

安全团队连续报告三类事故：

1. 某 Agent 执行 `merge` 成功返回后，工具服务器上出现一个计划外进程：仓库自带的 `gc.recentObjectsHook` 配置指向的脚本被执行（维护钩子在 merge 成功后自动触发 gc）。
2. 另一类：merge/checkout 写入了来自外部贡献者的 `.gitattributes`（含 filter / merge driver 声明），之后一次冲突 `abort` 时这些驱动文件被执行。
3. 第三类：仓库包含子模块与 promisor remote，子仓库自带的 `diff.external` / `textconv` 配置、promisor remote 的 `uploadpack` / `core.sshCommand` 配置，全部绕过了父仓库层面的路径与命令校验。

系统规模：约 1.2 万个托管仓库，日均 3 万次写操作，其中约 8% 来自不可信外部贡献者。工具服务器按仓库隔离程度分为共享池与隔离池两档。

目标：给出治理方案，说明为什么"逐点修补漏洞"在这类问题上连续失效，以及写路径的副作用清单应该怎么建。

限制：不能禁掉所有 merge/checkout（核心业务）；隔离池容量有限，不能把全部流量迁入；合规要求保留所有写操作的审计记录。

### 先思考

1. 三类事故的共同结构是什么？第一类的触发时机是"merge 成功之后"，第二类是"写入了配置、之后某条命令执行了它"，第三类是"执行点在嵌套仓库里"。它们和"只读工具被仓库配置劫持"（2026-11-17 S01）是同一类问题吗？
2. "校验对象必须等于生效对象"——在第三类里，父仓库校验的对象和实际执行配置的对象分别是谁？
3. 逐点修补：给 gc 钩子打补丁、给 .gitattributes 过滤、给子模块加校验——为什么每一轮修复后总有下一轮新 GHSA？按类收敛的"类"是什么？
4. 修复取向为什么是"禁用自动行为"而不是"校验配置内容"？`maintenance.auto=false`、`GIT_NO_LAZY_FETCH` 各关掉什么？
5. 审计要记录什么才能在事故后回答"这个写操作触发了哪些自动行为"？

### 参考答案

**结论：三类事故同属"写操作成功路径上的隐式副作用"与"嵌套信任域的配置执行"两个类——成功写入会触发仓库自带配置指向的自动行为，且间接引用机制会在嵌套仓库中再生。修复取向是禁用自动行为（`maintenance.auto=false`、`GIT_NO_LAZY_FETCH`、禁用/白名单 external diff 与 textconv），并让路径与命令校验覆盖嵌套信任域，而不是逐点修补。**

问题拆解。三层防线（路径限制、读写分级、网关审计）防的是"Agent 发起了什么调用"，三类事故的执行通道全是"仓库数据自带的配置在调用成功后做了什么"——校验对象（Agent 的命令与参数）不等于生效对象（git 在执行链上读取的配置）。这与 2026-11-17 S01 的"只读声明失效"同源但方向不同：那里是"读操作触发执行"，这里是"写操作的成功本身就是触发器"——merge 成功返回的那一刻，自动维护行为才开始跑。

核心方案，按类收敛为四条防线：

1. **禁用自动行为类**：工具服务进程级设置 `maintenance.auto=false`（关闭写后自动维护）、`GIT_NO_LAZY_FETCH=1`（禁止 promisor remote 的懒拉取执行远端命令）、禁用或白名单 `diff.external` / `textconv` / filter / merge driver。原则：这类配置的合法价值在交互式开发者手里，在服务端无人审批的自动执行链上只有风险，直接禁用比"校验内容是否安全"可靠——内容校验防不住嵌套引入与时机组合。
2. **嵌套信任域类**：路径与命令校验必须在每个仓库对象的完整配置面上运行，覆盖子模块（`.gitmodules` + 子仓库自己的 config）、linked worktree 与 promisor remote；"校验对象等于生效对象"要延伸到"配置解析范围 = 执行时会读配置的范围"。实现上可以在 checkout/merge 前枚举嵌套仓库清单，对其配置面执行与父仓库相同的检查，或干脆在服务端拒绝读取嵌套仓库的本地配置（用环境变量与命令行参数固定行为）。
3. **分级与降级类**：来源信任级 × 操作类型二维判定。不可信贡献者的写操作进隔离池（失败则 fail-closed，排队或拒绝，并给申诉 SLA），不因隔离池满而自动降级到共享池——自动降级会把攻击者流量挤进弱隔离档。写路径的 expand 型变更（如新增 driver 声明）单独标记，随写操作的审计记录。
4. **审计与观测类**：审计三元组之外，为每次写操作记录"该操作在当前配置面下可能触发的自动行为清单"（merge → maintenance hook；checkout of new attrs → driver 注册）；对计划外进程执行（fork 自 git 子进程树）做告警。红队回归用已知 GHSA（h2g3 / 9vjp / 8wv7 / 87qg）作测试集。

方案取舍：禁用自动行为会损失服务端自动 gc 等运维便利——改由平台侧定时任务统一执行维护（配置面由平台控制，不由仓库数据控制），这是把"隐式"变成"显式排队"的代价，可接受。全面迁移隔离池则受容量限制，按信任级分流是现实解。

失败路径与边界条件：配置面枚举可能漏掉动态引入的嵌套仓库（子模块随 checkout 新增）——所以嵌套检查挂在"写操作后新增仓库对象"这个事件上，而不是只在任务开始时做一次；超时上，禁用自动行为后写操作本身变快，隔离池排队超时走向显式失败而非共享池降级；重试与幂等由操作指纹承担（与 2026-11-16 S01 的 MCP Tasks 结论一致），失败重试不得重复执行已成功的 merge。

三层能力归属：模型概率能力——选择工具与参数，不承担安全判断；Agent 编排能力——任务分派、信任级路由、审批与 fail-closed 决策；git 配置语义与进程执行——确定性机制，防线必须落在这一层（禁用开关、环境变量、隔离进程），提示词或工具描述里的"只读/安全"声明不构成边界。

验证指标：已知 GHSA 回归集通过率（应 100%）、计划外进程执行告警数（目标 0）、共享池流量占比、写操作 p99 时延（禁用自动行为后的对比）、隔离池排队拒绝率与申诉处理时长。

**能力归属声明**：防线的有效性来自 git 进程配置与操作系统的确定性机制；模型与编排层只负责路由与拒绝，不负责"理解配置是否安全"。

### 关键点

1. "成功即触发"：写操作的成功返回不是执行的终点，成功路径上的自动维护与后续行为必须纳入副作用清单。
2. 逐点修补在这类问题上连续失效（同类 GHSA 四轮重现），因为漏洞面是"领域自带的间接引用机制"这个类，不是具体点位；修复按类收敛。
3. "校验对象必须等于生效对象"延伸到嵌套信任域：子模块、promisor remote、linked worktree 各自有配置面，父仓库校验不自动覆盖。
4. 修复取向是禁用自动行为而非校验配置内容：内容校验防不住嵌套引入与执行时机组合，开关与环境变量是确定性边界。
5. 与只读副作用（2026-11-17 S01）统一为同一个判断：信任域内的数据不等于可信代码，接口声明（只读/写、路径限制）都不是执行保证。

### 常见误区

1. **"merge 返回成功就万事大吉"**：成功恰是隐式副作用的触发时刻；审计只记"写操作成功"而不知道触发了什么，事故后无法归因。
2. **给每个 hook/driver 单独打补丁**：每轮 GHSA 都会带来新点位（本轮是 gc 钩子与 abort 路径驱动），点位是无穷的，类是有限的。
3. **认为父仓库的 `--repository` 校验覆盖子模块**：嵌套仓库有自己的 config 与执行配置，父层校验对象与生效对象再次脱节。
4. **隔离池满了自动降级到共享池**：降级路径把攻击者流量送进弱隔离档，应 fail-closed 加申诉。

### 追问

**追问 1：为什么"逐点修补"在这类问题上连续四轮失效，判断标准是什么？**
要点：失效的判据是"同一结构在不同路径上重现"——TOCTOU 类在 write/read/move 三路径重现（v9 时期），隐式副作用在 merge/abort 路径重现（本轮）。当一类缺陷的根因是机制层面（领域自带的间接引用机制），点位修补只改变出现位置；判断标准是问"下一个重现点能不能被现有防线覆盖"，回答是"不能"时就转向按类收敛。

**追问 2：嵌套信任域怎么系统性枚举，而不是靠事故驱动？**
要点：枚举的锚点是"git 会在哪些仓库对象上读配置"——主仓库 config、`.gitmodules` 指向的每个子仓库、linked worktree 共享的 common config、promisor remote 的按 remote 配置。工程做法：写操作前枚举嵌套仓库清单并对每个配置面跑同一组检查；对 checkout 会新引入的子模块单独拦截；把"配置面枚举"做成与 GHSA 回归集同级的测试项。事故驱动的对偶是"枚举驱动的攻击面清单"，与 2026-10-26 S01 的攻击面评审方法论一致。

**追问 3：这套防线和 2026-11-17 的"只读工具副作用"防线怎么统一，平台级还剩什么独有风险？**
要点：统一在"声明（只读/写/路径限制）不是保证，边界必须落在机制层"与"按类收敛"两条原则上；差异在触发时机（读时触发 vs 成功后触发）决定观测点不同。独有风险：写操作会**改变**后续的配置面（写入 .gitattributes 影响下一次操作），即"本操作的副作用成为下一操作的输入"——跨操作的配置演化是只读场景没有的，需要版本化记录每次写后的配置面 diff 并纳入变更门禁。

### 小型实践

对一个测试仓库完成一次"自动触发面审计"（30–60 分钟）：
1. `git config --show-origin --list` 遍历主仓库与所有子模块的配置，标出所有可执行项：`core.fsmonitor`、`gc.*.hook`、`diff.external`、`textconv`、filter 定义、merge driver、remote.*.uploadpack、`core.sshCommand`。
2. 对照 git 文档确认每一项的触发时机（哪条命令、哪个成功路径）。
3. 写一份服务端禁用清单（环境变量 + 配置项），在测试仓库上验证：merge 后无自动维护进程、子模块 fetch 不执行远端命令。
4. 产出：一页"写路径副作用清单"（操作 × 触发点 × 禁用方式），作为审计模板。

## S02 · 非 Agent 真实研发场景题

**题目 ID**：Q-20261124-S02　**一级类型**：数据库与存储（兼属分布式系统）　**二级主题**：热点行更新与行锁排队　**核心考点**：单行 UPDATE 的串行化、CPU 不高 TPS 低的现象解释、库存拆行与批量合并、预扣与对账兜底　**难度**：场景题（高）　**标签**：数据库、热点行、行锁、秒杀、幂等

### 题目

电商平台做限时秒杀：单个爆款 SKU 共 50,000 件库存，存为订单库（PostgreSQL）中一行 `inventory` 记录。扣减逻辑是一条事务内 `UPDATE inventory SET stock = stock - ? WHERE sku = ? AND stock >= ?` 加一条扣减流水 INSERT。

压测数据：入口目标 5,000 QPS；实际测得数据库 CPU 只有约 30%，内存与 I/O 正常，但扣减 TPS 稳定在 300 左右，锁等待超时占请求的 92%，应用侧大量 `canceling statement due to statement timeout`。

目标：把扣减能力提到支撑 5,000 QPS 的水平，同时保证不超卖是硬指标、已扣未支付的库存要能回补。

限制：不改整体架构为全新的库存服务（时间不够）；入口可以增加限流与排队；允许引入 Redis 但要求可回退；数据团队要求所有扣减留有可对账的流水。

### 先思考

1. CPU 30% 却 TPS 只有 300：瓶颈不在算力在哪？单行 `UPDATE` 上，行级锁让同一行的修改串行化——排队发生在哪条队列上？
2. `stock >= ?` 的条件更新防住了超卖，但防不住"等锁"。哪些手段能减少同一行的争用：拆行？合并更新？把扣减挪到 DB 之外？
3. 拆成 N 行后"剩余库存总数"怎么读？扣减时怎么选中一行？
4. 引入 Redis 预扣：预扣成功后 DB 落库失败怎么办？支付超时的回补怎么做？Redis 与 DB 的不一致窗口由什么决定？
5. 不超卖的最终防线放在哪一层？Redis 挂掉时怎么回退？

### 参考答案

**结论：瓶颈是单行的行锁串行化——所有扣减在同一个元组上排队，CPU 空闲只说明瓶颈不是算力而是锁等待。方案按层拆解：入口削峰 + Redis 原子预扣 + DB 侧拆行与批量合并 + 唯一流水约束作超卖最终防线 + 异步对账回补。**

问题拆解。PostgreSQL 对 `UPDATE` 目标行加行级锁，5,000 个并发事务在同一元组上串行，单行扣减虽快（毫秒级），吞吐上限也只有约 1/单次占用时长；其余事务全部处于锁等待，大量触发 statement timeout——这正是"CPU 30% 但 TPS 300"的原因：等待不消耗 CPU。92% 的锁超时意味着有效吞吐远低于入口压力，且超时重试进一步放大争用（与 2026-10-23 S02 的重试放大同族，但争用源不同：那里是锁顺序成环，这里是单点串行）。

核心方案，四层：

1. **入口削峰**：按 SKU 令牌桶限流到略高于实际可支撑水位，超出部分快速失败（"已抢完"而非排队），把无谓重试挡在门外。秒杀流量本身重尾，公平排队意义有限，快速失败体验更好且保护下游。
2. **Redis 原子预扣**：库存数预载入 Redis，Lua 脚本原子执行 `DECR`（库存不足直接拒绝）。预扣成功的请求才进 DB 落库链路，DB 承受的实际写入降到数百 QPS。预扣幂等键 = user_id + sku + 场次，防重放。可回退性：Redis 故障时降级为"纯 DB + 更低限流阈值"，功能正确只是容量下降。
3. **DB 侧拆行与批量合并**：单行拆为 N 行（如 10 行，每行 5,000 件），扣减按 `sku, bucket = hash(order_id) % N` 或随机选行，行内条件更新；剩余总数由聚合查询或计数表给出（容忍毫秒级误差，展示场景足够）。进一步提升吞吐可在应用侧把 1 秒内的扣减**合并成一次批量 UPDATE**（一次锁占用完成多件扣减），把锁的串行成本摊薄——这是热点行优化的两个标准手段：拆（并行化）与合（摊销）。
4. **最终防线与对账**：超卖硬指标由 DB 条件更新（`stock >= ?`）+ 扣减流水表的唯一约束（user_id+sku+场次唯一）兜底——即使 Redis 与 DB 出现不一致，DB 层也不可能出现负库存或重复扣减。已扣未支付：预扣记录带状态与 TTL，支付超时回补走异步任务（对 Redis `INCR` 回补 + 流水标记），回补幂等按流水 ID。对账任务比对 Redis 余量、DB 分行余量与流水聚合三方，差异率与超卖次数是上线硬指标。

方案取舍：Redis 预扣换吞吐，代价是引入不一致窗口（预扣成功到 DB 落库之间 Redis 是"承诺"而非事实）——因此正确性锚点放在 DB 条件更新，Redis 只承担准入，不承担事实。全部留在 DB 拆行是最保守方案（无新组件），但 5,000 QPS 下单行即使拆 10 行，单行仍要承担约 500 QPS 的串行扣减，余量不足；合并不拆则在峰值时单次 UPDATE 体积变大、延迟上升。组合使用，并将 Redis 作为可回退组件满足限制条件。

失败路径与边界：Redis 不可用→限流降级模式（已述）；DB 扣减失败而 Redis 已扣→按流水补偿回补，补偿失败进对账扫描（漏补靠对账而非实时链路，与 2026-10-21 S02 的漏执行兜底思路一致）；应用崩溃在预扣与落库之间→流水表只有预扣无扣减记录，由超时回补统一处理；扣减事务超时→整事务重试或按唯一约束幂等返回，锁等待不重试。

性能、可用性与验证指标：扣减链路 p99 < 100 ms（预扣路径）；DB 有效扣减 TPS ≥ 5,000 的实际落库需求（约数百 QPS）；锁等待超时占比从 92% 降至 <1%；对账差异率 < 0.01% 且小时级收敛；超卖次数 = 0（硬指标）；Redis 故障演练下系统退化为低速正确模式而非错误模式。压测方法：阶梯加压验证拆行数与合并窗口的乘积上限，观测点在锁等待而非 CPU。

**能力归属说明**：本题不涉及模型；确定性能力（限流、Lua 原子性、DB 条件更新与唯一约束、对账）承担全部正确性，这是非 Agent 场景的常态。

### 关键点

1. 热点行的本质是行级锁串行化：吞吐上限 ≈ 1/单次锁占用时长，CPU 利用率与瓶颈无关，观测点应放在锁等待（`pg_locks`、等待事件）。
2. 拆行（并行化）与批量合并（摊销锁成本）是两个正交手段，乘积决定上限。
3. Redis 预扣承担准入、DB 条件更新承担事实：正确性锚点只能有一个，且在确定性层。
4. 超卖最终防线 = 行内条件更新 + 扣减流水唯一约束；回补、漏补、崩溃恢复全部由流水 + 对账兜底。
5. 外部组件（Redis）必须可回退：降级模式是"低速但正确"，不是"错误但快速"。

### 常见误区

1. **"CPU 没满就该扩容数据库"**：加机器不解决单行串行，新副本反而带来复制延迟问题；先看锁等待事件再定方向。
2. **把超卖防线放在 Redis**：Redis 是缓存与准入层，崩溃或主从切换（2026-11-12 S02）都可丢失最近写入；条件更新在 DB 才是硬约束。
3. **对"抢不到"无限重试**：重试流量放大行锁争用（92% 超时里相当部分是重试贡献的），入口快速失败优于排队。
4. **拆行后把"剩余总数"当实时精确值用于扣减判断**：聚合值有毫秒级误差，判断进不进扣减用 Redis 预扣，DB 行内条件才是事实。

### 追问

**追问 1：为什么 CPU 只有 30% 而 TPS 卡在 300？给你一张只有 CPU 和 TPS 的监控图，你会先查什么？**
要点：单行 UPDATE 的吞吐上限由锁占用时长决定而非算力；CPU 空闲 + 锁超时高是"串行化瓶颈"的签名。先查 `pg_stat_activity` 的等待事件分布（LWLock/lock 占比）、行锁等待队列长度与 statement timeout 率，再查单次 UPDATE 的实际耗时。监控上应给"锁等待占比"独立面板。

**追问 2：拆行后热点转移了吗？怎么定行数与合并窗口？**
要点：拆行把争用摊到 N 行，但每行仍有串行上限（约 1/占用时长），N 行上限 ≈ N×单行上限；行数过少余量不足，过多则聚合查询与库存可视化管理成本上升。合并窗口把 K 次扣减摊进一次锁占用，窗口越长延迟越高——用阶梯压测找"行数 × 窗口"在目标 QPS 下的延迟拐点，而不是拍一个数。

**追问 3：Redis 预扣成功但 DB 长时间落不进去（DB 过载），库存会被"占住"吗？**
要点：会——预扣承诺与 DB 事实之间是有界不一致窗口，必须由流水状态机管理：预扣记录带 TTL 与状态（reserved/paid/refunded），TTL 到期由异步回补释放；DB 持续过载时应反向收紧 Redis 预扣速率（背压传导），而不是让预扣继续积累承诺。漏补与对账兜底是最后防线，实时链路只保证"快"，不保证"全"。

## L01 · LeetCode

**题目 ID**：Q-20261124-L01　**一级类型**：栈与队列（嵌套结构解析）　**难度**：medium

### 题目

**LeetCode 394 · 字符串解码（Decode String）**，难度 medium。
官方链接：https://leetcode.cn/problems/decode-string/ （已核验：题目描述、4 个示例、约束均取自官方页面；官方页难度标签在本轮未直接渲染，medium 按标准分类记录。）

给定一个经过编码的字符串，返回解码后的字符串。编码规则为 `k[encoded_string]`，表示方括号内的字符串正好重复 k 次（k 保证为正整数）。输入保证合法：无额外空格、方括号符合格式、原文不含数字（所有数字只表示重复次数），且嵌套可以出现（如 `3[a2[c]]`）。

**输入**：字符串 `s`。**输出**：解码后的字符串。

**约束**：`1 <= s.length <= 30`；`s` 由小写英文字母、数字和 `'['`、`']'` 组成；输入保证有效；`s` 中所有整数取值范围 `[1, 300]`；测试用例保证输出长度不超过 10⁵。

**示例**：
- `"3[a]2[bc]"` → `"aaabcbc"`
- `"3[a2[c]]"` → `"accaccacc"`
- `"2[abc]3[cd]ef"` → `"abcabccdcdcdef"`
- `"abc3[cd]xyz"` → `"abccdcdcdxyz"`

### 先思考

1. 嵌套意味着什么：`3[a2[c]]` 中内层 `2[c]` 要先变成 `cc`，才能参与外层的重复——"先完成内层"是哪种数据结构的天然行为？
2. 扫描中遇到数字、字母、`[`、`]` 四类字符分别该做什么？`[` 出现时，必须先保存哪两样东西？
3. `]` 出现时要做"三件事拼装"：取出重复次数、复制当前段、接到哪一段前面？当前段的"工作区"应该重置为什么？
4. 多位数怎么处理（本题 k ≤ 300，可能出现 `300[...]`）？
5. 递归也能解（把 `[...]` 当子问题），栈和递归各对应什么实现？两者复杂度一样吗？

### 参考答案

**推荐解法：单遍扫描 + 显式栈。** 栈中每个元素保存"进入这层括号前的已完成前缀"与"当前的重复次数"；遇到 `]` 时弹出，用"前缀 + 当前段 × 次数"重建当前工作区。

解题思路推导：嵌套括号是后进先出结构——最内层最先完成，其结果成为外层的组成部分，天然映射到栈。维护两个工作变量：`cur`（当前层的已构建字符串）与 `num`（当前累积的重复次数）。逐字符扫描：

- 数字：`num = num * 10 + digit`（支持多位数）。
- 字母：`cur += c`。
- `[`：把 `(cur, num)` 压栈，然后**重置** `cur = ""`、`num = 0`，开始构建内层。
- `]`：弹出 `(prev, k)`，置 `cur = prev + cur * k`。

正确性说明：不变量是"任一时刻，栈中的每个 `(prev, k)` 恰好是尚未闭合的外层括号的前缀与次数，且按嵌套深度从底到顶排列"。`[` 入栈保存外层现场，`]` 出栈恢复现场并把内层成品重复后拼接——每对括号恰好入栈出栈一次，扫描结束后栈空且 `cur` 即完整解码结果。输入保证合法，无需处理不匹配。

时间复杂度：O(n × maxKⁿᵉˢᵗ) 上界（输出长度本身可达 10⁵，解码复制与输出同阶），对本题约束内即 O(输出长度 + 输入长度)。空间复杂度：O(输出长度)（栈与工作串的总字符量）。

Python 参考代码：

```python
class Solution:
    def decodeString(self, s: str) -> str:
        stack = []          # 每层: (外层前缀 cur_prev, 重复次数 k)
        cur = ""
        num = 0
        for c in s:
            if c.isdigit():
                num = num * 10 + ord(c) - ord("0")
            elif c.isalpha():
                cur += c
            elif c == "[":
                stack.append((cur, num))
                cur = ""
                num = 0
            else:  # "]"
                prev, k = stack.pop()
                cur = prev + cur * k
        return cur
```

边界情况与测试用例：

1. 无括号纯字母：`"abc"` → `"abc"`。
2. 单层：`"3[a]"` → `"aaa"`。
3. 深嵌套：`"2[3[a]b]"` → `"aaabaaab"`（内层先完成再乘外层）。
4. 多位数：`"12[a]"` → `"aaaaaaaaaaaa"`（两位数累积）。
5. 前后缀混合：`"abc3[cd]xyz"` → `"abccdcdcdxyz"`（前缀保留、后缀在栈清空后继续追加）。

```python
def test():
    sol = Solution()
    assert sol.decodeString("3[a]2[bc]") == "aaabcbc"
    assert sol.decodeString("3[a2[c]]") == "accaccacc"
    assert sol.decodeString("abc3[cd]xyz") == "abccdcdcdxyz"
    assert sol.decodeString("abc") == "abc"
    assert sol.decodeString("2[3[a]b]") == "aaabaaab"
    assert sol.decodeString("12[a]") == "a" * 12
```

**可迁移能力**：嵌套/递归结构的线性解析模式——用栈把"递归定义的语法"转为单遍扫描，`[` 保存现场、`]` 恢复现场并合并。这一模式直接迁移到 JSON/公式/标记语言解析。与 AI Agent 工程的自然联系：工具返回的嵌套结构化文本（如带嵌套引用的引用块）解析用同一模式——仅在存在自然联系时提及。
### 关键点

1. `[` 时必须同时保存两样：外层前缀与重复次数，且立即重置工作区；漏掉重置会把内层内容拼进外层前缀。
2. `]` 的拼装顺序是"前缀 + 当前段 × k"，乘法作用在**当前层**，前缀不重复。
3. 多位数累积用 `num = num * 10 + d`，不能只读一位。
4. 每对括号恰好入栈出栈一次，输入合法保证栈最终为空——这是正确性论证的锚点。
5. 输出长度可达 10⁵ 而输入只有 30 字符：复杂度必须按输出长度计，勿按输入长度声称 O(n) 线性于输入。

### 常见误区

1. **只在栈里存数字不存前缀**：`]` 时无法把内层结果接回外层，需要额外结构恢复现场；存 `(prev, k)` 二元组是最简形态。
2. **乘法重复外层前缀**：写成 `cur = (prev + cur) * k` 会把未重复的内层也卷进乘法，顺序错即结果错。
3. **用 `if` 处理 `]` 的连续弹出**：本题单字符扫描每步最多遇一个 `]`，无此问题；但若改写成"栈顶仍是 `]` 场景"的变体题（如 946 类连续弹出），`if` 会漏——注意本模式与栈贪心模拟的边界差异。
