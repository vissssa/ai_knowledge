## B01 字符串长度到底是谁的：字节、码点与字素

**题目 ID**：Q-20261125-B01 ｜ 一级类型：编程语言与运行时 ｜ 二级主题：字符串与编码（UTF-8、长度语义、Unicode 规范化）｜ 标签：UTF-8、Unicode、规范化

### 题目

面试官问：计费系统按"字符数"给短信和文案计价，运营反馈同一段话在不同渠道统计出的字数不一样；数据组发现同一个邮箱在唯一索引里出现了两行，肉眼看完全相同；还有一次服务把日志行按前 100 个字节截断后，下游解析直接报错。请解释这三个现象背后字符串的哪些语义在起作用，并说明你在工程上如何给出统一的判定标准。

### 先思考

1. 先拆"长度"：同一段文本，按字节、按码点、按人眼可见字符（字素簇）计数，结果分别是什么？什么时候三者一致？
2. 邮箱唯一索引撞车的两个"相同"字符串，想一想 Unicode 规范化：同一个视觉字符可以有几种码点序列？
3. 截断报错：字节截断切在多字节字符中间会发生什么？为什么 UTF-8 的设计让这件事"可判定"而不是随机出错？

### 参考答案

**定义**：UTF-8 是对 Unicode 码点的变长编码，ASCII 1 字节、常用汉字 3 字节、emoji 可达 4 字节；"字符串长度"因此至少有三种互不相同的语义——**字节数**（存储与传输占用）、**码点数**（Python `len(str)` 返回的值）、**字素簇数**（用户感知的一个"字"，如家族 emoji 是多个码点）。三者只在纯 ASCII 文本上相等。

**适用边界**：只要文本含非 ASCII 字符或组合字符，就必须显式声明用哪种语义计数。计费与限长属业务语义，通常应对齐字素簇或产品口径；`Content-Length`、磁盘占用、网络传输一律是字节；数据库 `varchar(n)` 的 n 是字符（PG）还是别的语义要看具体实现。工程上的统一判定标准是：**在系统边界处固定一种语义并写进契约**，内部表示统一为一种规范化形式。

**示例**：`"café"` 有两种合法码点序列——NFC（`e` + 组合尖音符合成单码点 U+00E9）与 NFD（`e` + 独立组合尖音符 U+0301），两者字节不同、`==` 为 False、哈希不同，但在屏幕上完全一样。这就是"同一邮箱出现两行"的原因。对它做 NFKC 规范化后两种表示收敛为同一序列，唯一索引不再撞车。

**相近概念区别**：`str` 与 `bytes` 是表示层与编码层的分工——str 是码点序列，bytes 是编码后的字节序列，`len` 的语义随类型改变；编码（encoding）决定字节怎么存，排序规则（collation）决定字符串怎么比较，两者独立；`\u00e9` 这类转义只是字面表示法，不是又一种编码。另外 `bytes.decode` 遇到被切断的多字节序列会报 `UnicodeDecodeError`——这不是编码坏了，而是截断破坏了编码单元。

**典型应用**（通用工程）：传输与存储层（HTTP `Content-Length`、文件偏移）一律按字节；业务计费与展示限长按产品口径并显式声明；入库存前统一做规范化（通常 NFC）并放写入闸门；按字节截断后必须"截断到有效边界"再 decode。服务端读写文件时显式指定 `encoding="utf-8"`，不依赖 locale 默认值。

**面试现场回答**：这三个现象分别是三种长度语义、两种规范化形式和一次非法字节截断。核心结论是字符串没有天然的"长度"，只有你选定的语义；工程上的做法是边界处固定语义、入库前统一 NFC、按字节截断必须回到码点边界，并把这三条写进契约而不是依赖默认行为。

### 关键点

1. "长度"至少有字节、码点、字素簇三种语义，纯 ASCII 时才一致，任何计费/限长功能必须显式选边。
2. 规范化（NFC/NFD）不是格式化美化，而是唯一性与相等性的前提，必须在写入闸门统一。
3. 按字节截断可能切出无效 UTF-8，decode 报错是确定性行为而非随机损坏；正确做法是回到码点/字素边界。
4. `str`/`bytes` 的 `len` 语义不同；`Content-Length`、文件偏移永远按字节。
5. 编码管存储、collation 管比较，二者独立，唯一约束撞车优先查写入侧规范化。

### 常见误区

1. 用 `len(s)` 同时当作字节预算和字符配额——多字节文本下两者相差数倍，计费与限长会系统性偏差。
2. 认为"截断后 decode 报错是数据坏了"——错在截断操作破坏了编码单元，数据本身合法；修复点是截断逻辑而非数据修复。
3. 把规范化当可选优化——不做 NFC 的系统迟早在唯一索引、缓存键、去重集合上出现幽灵重复，且事后无法可靠合并。

### 延伸学习

1. Python 官方文档 *Unicode HOWTO*（编码、str/bytes、规范化 API 的权威入口）：https://docs.python.org/3/howto/unicode.html （官方文档，链接稳定；本轮未逐字核验正文）
2. Unicode 标准附录 *UAX #15: Unicode Normalization Forms*（NFC/NFD/NFKC/NFKD 的规范定义）：https://www.unicode.org/reports/tr15/ （官方规范；本轮未逐字核验正文）

### 追问

为什么唯一索引会允许两个"看起来一样"的值同时存在？——回答要点：唯一约束建立在码点序列（或其字节编码）上，NFC 与 NFD 是两个不同序列；比较用的 collation 若未做规范化也不会合并它们；所以规范化必须在写入侧完成，不能指望存储层兜底。

## B02 OpenTelemetry GenAI 语义约定：Agent 链路为什么要统一说法

**题目 ID**：Q-20261125-B02 ｜ 一级类型：Agent 评测与可观测性 ｜ 二级主题：OpenTelemetry GenAI 语义约定与 Agent、工具、MCP 调用链路 ｜ 标签：OpenTelemetry、语义约定、Trace、成本归因

### 题目

面试官问：你们的 Agent 平台要接第三方可观测性方案，团队成员各自在代码里打点，有人记 `model`、有人记 `llm_model`、有人把 token 数放进 span name。为什么 LLM/Agent 链路的可观测性需要一套专门的语义约定？这套约定解决了什么、目前处于什么状态、依赖它有哪些工程风险？

### 先思考

1. 先想通用 http span 记录了什么：状态码、耗时、URL——它回答不了哪些 LLM 特有问题？
2. 跨厂商比较（A 模型 vs B 模型的成本与质量）依赖什么？如果每个团队自己命名属性，聚合会发生什么？
3. "语义约定"和"强制 API"的区别是什么？约定处于 Development 状态意味着承诺强度有多高？

### 参考答案

**定义**：OpenTelemetry GenAI 语义约定（semantic conventions）是对 GenAI/Agent 链路遥测的**命名与取值约定**：规定 span 的种类与命名（如 agent、plan、execute_tool 等层次）、属性名与取值域（`gen_ai.system`、`gen_ai.request.model`、`gen_ai.request.max_tokens`、`gen_ai.usage.input_tokens` / `gen_ai.usage.output_tokens`、操作与错误属性等）。它让不同厂商、不同框架的模型与工具调用翻译成**同一套可聚合、可比较的字段**。

**适用边界**：约定不是强制 API，是互操作契约；整套 GenAI 约定目前处于 **Development 状态**（依据题库配置 v10 周维护核验记录：约定已迁至 open-telemetry/semantic-conventions-genai 仓库，`gen_ai.*` 属性为 Development，仅继承的少量通用属性为 Stable，仓库已出现首个 tagged release v0.1.0——本轮 GitHub 页面访问失败，状态以配置核验记录为准，标记为"未本轮直接核验"）。Development 意味着字段可能增改，采集侧必须容忍未知字段、不能把属性当强类型 API 依赖。

**示例**：一次 Agent 任务产生 span 链：`create_agent`（或 `invoke_agent`）→ `plan` → `execute_tool`（挂具体工具名与错误类型）→ 每次模型调用 span 带 `gen_ai.request.model="gpt-x"` 与 `gen_ai.usage.output_tokens=352`。聚合层即可按 `gen_ai.system + gen_ai.request.model + gen_ai.usage.*` 直接算出"每个任务、每个模型、每个工具步骤的 token 与成本"，无需自己再定义口径。

**相近概念区别**：通用 HTTP/RPC span 只知道"这次调用 200 OK、耗时 800ms"，不知道模型、token 与输入输出形态——这正是 GenAI 约定补的缺口；厂商私有 SDK 日志是各说各话的方言，聚合前要做昂贵的字段映射；语义约定与 MCP/A2A 等协议的追踪上下文传播（traceparent 经 `_meta`）互补：前者统一字段语义，后者统一链路上下文传递。

**典型应用**（Agent 系统中）：成本与延迟的按任务归因（task × model × tool 的最小维度集）、轨迹级评测（把评测事件对齐到 execute_tool span）、模型版本对比（`gen_ai.request.model` 作为分桶键）。自己打标的平台最终都会遇到"三个团队三种口径"的漂移，统一约定的价值正在于此。

**面试现场回答**：通用遥测记录不了 LLM 特有的 token、模型与工具语义，各团队自造字段则聚合必然漂移；GenAI 语义约定把 span 层次与 `gen_ai.*` 属性统一，使成本归因与轨迹评测有公共口径。它目前是 Development 状态的约定而非稳定 API，生产用法是采集层固定版本、业务通过映射层消费，把约定当数据契约而不是代码依赖。

### 关键点

1. 语义约定解决的是**口径统一**：跨厂商、跨团队的属性命名与取值域，聚合与对比才成立。
2. span 层次（agent → plan → execute_tool）是成本与错误归因的骨架，工具 span 不挂在 agent 链下会导致归因断裂。
3. `gen_ai.usage.*` 来自模型响应回传，是实测值而非估算，token 计费归因应以此为准。
4. GenAI 约定整体处于 Development，字段可能变化——容忍未知字段、版本固定、映射层隔离。
5. 与通用 http span 的关系是补充而非替代；与协议层追踪上下文传播（traceparent）互补。

### 常见误区

1. 把语义约定当稳定 API 直接强依赖——Development 状态下字段增改会静默破坏下游；正确姿势是映射层隔离。
2. 自造属性名以为"反正是自己的数据"——聚合口径漂移是隐性税，等发现时历史数据已不可比。
3. span 层级随手建——工具调用不挂到对应 agent/plan span 之下，按任务归因和轨迹评测的 join 就断了。

### 延伸学习

1. OpenTelemetry GenAI 语义约定仓库（状态与 span 定义的一手来源）：https://github.com/open-telemetry/semantic-conventions-genai （本轮页面访问失败未直接核验；Development 状态依据题库配置 v10 于 2026-11-23 的周维护核验记录）
2. OpenTelemetry 语义约定总文档（约定状态机与 Stability 定义）：https://opentelemetry.io/docs/specs/semconv/ （官方文档，链接稳定；本轮未逐字核验正文）

### 追问

约定还在 Development，生产环境该不该用？——回答要点：该用，但要隔离风险：采集侧 pin 采集器/SDK 版本、为约定字段加一层内部映射（别让下游直接消费 `gen_ai.*` 原始键）、升级走灰度并 diff 属性集合；把它看作"低成本的口径对齐投资"，而不是"可长期承诺的 API"。

## S01 把内部 RPC 包装成 Agent 工具：粒度、截断与错误语义的契约适配

**题目 ID**：Q-20261125-S01 ｜ 一级类型：工具与互操作协议（兼属软件工程与平台工程、AI Agent 核心）｜ 二级主题：外部 API 和企业系统集成——工具契约适配 ｜ 标签：工具设计、契约适配、截断、错误语义

### 题目

一家电商公司要给客服 Agent 接入订单中台：中台有 40 个内部 RPC（`get_order`、`list_orders`、`refund`、`update_address`……），最初的做法是把 RPC 签名直接透传成工具。上线两周出现三个问题：① 模型调用 `list_orders` 拉到 500 条记录，网关截断到前 50 条但没有告知模型，模型在截断集上断言"查无此订单"并转人工，投诉量上涨；② 有团队把 40 个 RPC 拆成 80 个细粒度工具想"更灵活"，单任务平均步数从 4 涨到 19，P95 延迟 40 秒；③ 一次 `refund` 因网络抖动实际成功但返回超时，模型重试导致重复退款。系统规模：客服 Agent 日均 6 万次会话、中台 RPC P99 120ms。要求：给出工具契约的重新设计方案，说明粒度怎么定、截断与分页怎么进契约、错误语义怎么翻译，并明确指出哪些能力属于模型、哪些属于编排层、哪些属于传统确定性系统。

### 先思考

1. 三个故障分别对应契约的哪个缺口：数据完整性（截断）、调用面复杂度（粒度）、副作用安全性（错误语义与幂等）？
2. 工具粒度的"任务动词"视角：模型面向任务（查订单并退款），RPC 面向资源 CRUD——两者之间的映射单位应该是什么？
3. 错误语义：上游"超时"和"明确拒绝"对模型意味着完全不同的下一步，翻译层该输出什么结构？

### 参考答案

**结论**：把内部 RPC 透传成 Agent 工具是把面向确定性调用方的契约直接暴露给概率调用方，必然在数据完整性、调用面复杂度和副作用安全三处失配。重新设计的核心是：**工具按任务动词聚合粒度、截断与分页显式进契约、错误翻译为结构化分类、写工具独立成层并强制幂等**。

**问题拆解**：① 截断未声明 = 契约缺少数据完整性信号，模型把不完整视图当全集推理；② 步数膨胀 = 粒度过细，模型承担了本应由接口设计承担的组合负担，且每步都是一次模型推理的延迟与成本；③ 重复退款 = 超时被当作失败重试，副作用边界没有落在工具层。

**核心方案**：工具粒度按"客服任务动词"聚合——不是 `get_order`/`list_orders`/`get_logistics`/`get_payment` 四个 CRUD，而是一个 `lookup_order_context(order_id_or_phone)` 返回任务所需的结构化聚合视图；对真正开放性的检索场景提供带分页契约的 `search_orders(query, next_cursor)`。契约四要素强制进 schema：`has_more` + `next_cursor`（分页）、`truncated` + `truncation_reason`（截断显式声明）、`error_class` + `retryable`（错误翻译）、写工具的 `idempotency_key` 参数。

**执行流程**：模型调用 → 工具网关（唯一执行点）做参数校验与租户权限检查 → 适配层调 RPC 并做聚合/裁剪 → 响应封装为带完整性信号的结构化结果 → 若 `truncated=true`，结果中同时给出 `next_cursor` 与"不得基于截断集下断言"的系统指引（写进响应结构而非 system prompt）。写路径：`refund` 之类写工具不直接透传 RPC，走"提案—执行"分离：适配层生成业务幂等键（会话 ID + 操作指纹），执行层以幂等键对中台做条件提交，中台无幂等支持时在适配层落幂等表（唯一约束）补位。

**技术选型与依据**：聚合工具 + 分页下钻（选它：步数与延迟可控，模型选择负担小；备选：全细粒度自由组合——灵活但步数爆炸、选择失败率随工具数上升，已被 ② 证伪；另一备选：全粗粒度"大而全"工具——把组合逻辑塞进服务端硬编码，长尾任务无法覆盖）。错误翻译选 `error_class ∈ {timeout, not_found, rejected, upstream_error}` + `retryable` 布尔，替代裸 500 透传。

**方案取舍**：核心权衡是**灵活性与可控性**——细粒度把控制权交给模型（灵活、步数与不可预测性上升），任务级聚合把控制权收回接口设计（可控、脆弱于长尾）。取舍判据：高频路径固化成聚合工具（可评测、可缓存），低频长尾保留少量带分页契约的检索工具；**准确率与延迟**的权衡落在聚合视图的宽度上，视图越宽单次调用信息越全但上游 RPC 串联越多。

**失败路径与边界条件**：上游超时——预算传导（Agent 任务 deadline 减去已耗时是本次调用超时上限），`timeout` 标记为 `retryable=true` 但仅读工具自动重试，写工具超时必须走幂等键重放而非盲目重试；截断——显式 `truncated` 字段，评测中把"截断集上断言全局结论"列为失败模式；空结果与"查无"分离为两个不同的响应形态，避免模型把异常当业务结论。**恢复**：任务失败后凭幂等键重放，已成功的子步骤幂等返回原结果。**重试**：读工具指数退避 + 抖动 + 会话级重试预算；写工具仅幂等重放。**幂等**：幂等键由适配层生成并对齐业务操作指纹，中台不支持时以适配层幂等表（唯一约束 + 状态字段）兜底。**安全**：租户令牌下推到每次 RPC 调用、写工具白名单按角色分级、审计记录归一化后的生效参数（不是模型原始输出）。

**成本、延迟与可靠性**：任务级聚合使单任务步数回到 4-6 步，P95 延迟从 40 秒回到 8 秒以内；token 成本随步数线性下降；可靠性收益来自截断显式化（错误升级率下降）与写路径幂等（重复退款归零）。

**验证指标与观测**：工具选择正确率（轨迹级评测）、截断感知率（`truncated=true` 且模型继续下结论的比例，目标 0）、单任务步数分布与 P95 延迟、写工具重复执行率（幂等键命中率）、`error_class` 分布看板；上线后以投诉率与人工升级率作为业务侧校验。

**能力归属**：模型承担任务理解与参数抽取（概率性）；编排与工具网关承担执行点、权限、预算与重试策略（Agent 编排能力）；幂等表、唯一约束、审计与 RPC 本身是传统确定性系统——**重复退款问题的最终防线是确定性幂等，不是把提示词写得更恳切**。

### 关键点

1. 工具是面向概率调用方的契约重设计，RPC 签名透传会在数据完整性、调用面、副作用三处失配。
2. 截断必须显式进契约（`truncated` + `next_cursor`），完整性信号缺失会让模型把部分视图当全集。
3. 粒度按任务动词聚合，高频路径固化、长尾保留带分页的检索工具；步数是延迟与成本的乘数。
4. 错误翻译为 `error_class + retryable` 结构，写工具超时只能幂等重放；幂等键生成在适配层、判重靠唯一约束。
5. 三个故障的三条防线分属三层能力：prompt 降概率、编排层做执行点与预算、确定性幂等保正确性。

### 常见误区

1. 把"模型聪明"当作截断的解药——模型对"数据不完整"的敏感度是概率性的，契约缺失必然出现全集断言。
2. 以"更灵活"为由持续加细粒度工具——工具数上升使选择退化为检索、步数成本线性放大，灵活性与可控性必须显式取舍。
3. 用重试解决写工具超时——超时不等于未执行，无幂等键的重试就是重复副作用；正确路径是幂等重放或人工确认。

### 追问

1. 为什么不在 system prompt 里写"如果结果被截断请继续翻页"？——要点：提示词是指引层不是约束层，概率不等于保证；截断感知必须是结构化契约（`truncated` 字段）+ 网关侧拦截（检测到截断集上的全局断言模式可拒绝）双层实现，prompt 只降低概率。
2. 80 个细粒度工具错在哪里，什么时候细粒度是对的？——要点：错在选择面与步数成本，且多数细粒度调用只是聚合视图的一角；细粒度在"需要模型真正组合推理的开放任务"（如数据分析 Agent 自由探索）才合理，判据是调用序列能否预知。
3. 中台不支持幂等键怎么办？——要点：适配层补位（幂等表 + 唯一约束 + 状态机），把"执行前登记、执行后确认"做成两阶段；长期方向是推动中台原生幂等，因为适配层幂等只覆盖经过它的调用，绕过适配层的直调仍是裸奔。

## S02 磁盘 95% 触发只读锁之后：保护机制触发时的恢复路径

**题目 ID**：Q-20261125-S02 ｜ 一级类型：数据库与存储（兼属软件工程与平台工程）｜ 二级主题：向量数据库和全文检索——磁盘水位保护与只读块恢复 ｜ 标签：Elasticsearch、磁盘水位、只读块、容量治理

### 题目

检索平台承载全文检索与向量化日志检索，Elasticsearch 8.x 集群 12 个数据节点，日志类索引占总磁盘约 70%。某天上午起业务写入开始批量报错 `cluster_block_exception`，排查发现多个节点磁盘使用率触及 95%，Elasticsearch 对落在这些节点上的所有索引触发了只读块。值班同学的第一反应是把 `cluster.routing.allocation.disk.watermark.flood_stage` 调高到 99% 让集群"解锁"，随后另一个节点磁盘到达 100%，节点进程假死。系统约束：日志保留策略名义上 30 天但从未自动执行；写入 QPS 峰值 8000；检索 P95 要求 500ms。请给出止血与根治方案，说明水位机制的准确语义、恢复的先后顺序，以及这类"保护机制"在设计上要吸取什么教训。

### 先思考

1. 先读机制：85% / 90% / 95% 三条水位各触发什么行为？只读块为什么是 `read_only_allow_delete` 而不是完全只读——这个"允许删除"暗示了什么恢复路径？
2. 止血顺序：调高阈值、删数据、迁 shard——哪条是设计内的路径？调高阈值在什么前提下才安全？
3. 根治：为什么"30 天保留策略从未自动执行"？保护机制触发说明监控与自动化链条在哪里断了？

### 参考答案

**结论**：磁盘水位是存储引擎的自我保护，触发的正确恢复路径是**释放空间直到磁盘降到 high 水位以下**，而不是调高阈值绕过保护；`read_only_allow_delete` 中的"允许删除"就是设计者留下的止血通道。调高 flood_stage 到 99% 是在移除最后一道防线，直接导致了节点磁盘打满的更严重故障。

**机制语义（官方文档已核验）**：三条默认水位——low **85%**（不再向该节点分配新 shard）、high **90%**（把 shard 从该节点迁走）、flood_stage **95%**（对落有 shard 的所有索引强制 `index.blocks.read_only_allow_delete` 只读块，这是防止磁盘写满的最后手段）。只读块在磁盘使用率降回 high 水位以下时**自动解除**；`cluster.routing.allocation.disk.threshold_enabled` 默认开启，磁盘检查间隔 `cluster.info.update.interval` 默认 30 秒；百分比与绝对字节值不得在三条水位间混用。另有两个易错点：所有节点都超过 low 水位时，任何 shard 迁移都无法发生（没有可去的地方），必须先删数据；单数据节点集群不受水位豁免（早期版本的豁免行为已在 8.0 移除）。

**问题拆解**：① 止血——恢复写入需要目标节点磁盘降到 90% 以下；② 误操作纠正——撤回 99% 的阈值改动；③ 根治——保留策略落地与容量治理，防止复发。

**核心方案（止血）**：按"删除优先于迁移"排序：第一步撤回 flood_stage 修改（恢复 95%）；第二步找出占用最大的日志索引，按业务确认的保留窗口删除过期索引——DELETE 被只读块允许，且删除释放空间最直接；第三步若删除后仍超 90%，把 shard 迁移到有空间的节点（`_cluster/reroute` 或临时把新索引指到低水位节点）；磁盘降到 90% 以下后只读块自动解除，无需手动删 block（若需手动解锁必须先确保空间已释放，否则解除后立即重新触发并可能写满磁盘）。**根治**：ILM（索引生命周期管理）按 30 天自动删除或降冷到廉价存储；写入侧按索引模板设分片大小目标（单 shard 20-50GB 量级）；磁盘水位 P95 纳入告警，80% 即预警，给迁移留出窗口。

**执行流程**：告警触发 → 值班确认水位与受影响索引 → 撤回错误阈值改动 → 删除过期索引（业务确认保留窗口）→ 观察自动解锁 → 复盘 ILM 缺失原因 → 上线保留策略自动化 + 80% 预警。

**技术选型与依据**：保留策略选 ILM 自动删除（依据：人工执行 30 天策略已被证明不可持续；备选：定时脚本调 DELETE API——可行但缺少状态机与失败重试，需自建台账；另一备选：扩容磁盘——只解决本轮不解决增长斜率）。止血顺序选"删除优先"（依据：删除同时释放空间与减少 shard，迁移只在还有低水位节点可用时才可行）。

**方案取舍**：核心权衡是**保留时长与磁盘成本**——30 天全量保留的磁盘斜率决定了水位触发的必然性，降冷（frozen 层、可搜索快照）用查询延迟换空间；**副本数与空间**——日志类索引副本从 1 降到 0 可省 1/3 空间但牺牲单节点故障容忍，可对可重建索引（可从原始日志重放）采用 0 副本 + 快照兜底。

**失败路径、超时、重试、幂等与恢复**：删除操作本身要防误删——按索引名模式 + 创建时间双条件过滤，删除前列表留档（可恢复性依赖快照，删除前对不确定索引先 snapshot）；迁移期间集群带宽与检索延迟波动，限速执行；自动化脚本与 30 秒磁盘检查间隔存在竞态——脚本判断"已低于水位"后引擎可能仍在异步解除块，脚本不应假设即时生效，应轮询 `_settings` 确认块消失。**幂等**：删除按索引名幂等（重复执行安全）；ILM 状态机保证同一索引不会重复进入删除阶段。**恢复**：全程以"磁盘 < 90% 且受影响索引块清零"为完成判据，写回业务流量前先灰度一部分写入。

**安全、成本、延迟与可靠性**：删除是最危险的常规操作，必须走业务确认 + 留档 + 快照三道闸；成本上降冷与 0 副本可把日志存储成本压降约一半量级（依集群形态）；检索 P95 在 shard 迁移期间需观测抖动，限速迁移；可靠性上，水位保护的价值正在于它宁可让写入失败也不让磁盘写满导致节点假死——本次 100% 打满造成的假死正说明绕过保护的代价。

**验证指标**：各节点磁盘使用率 P95 与最大值、处于只读块的索引数（应为 0 告警）、ILM 每日实际删除量与保留窗口偏差、写入错误率、检索 P95；上线后连续两周观察磁盘增长斜率是否与 ILM 预期一致。

### 关键点

1. 三条水位的行为分工：85% 停止分配、90% 迁走、95% 只读块；只读块低于 90% 自动解除。
2. 恢复路径是释放空间，不是调高阈值；`allow_delete` 就是设计内的止血通道。
3. 全员超 low 时迁移机制失效——容量问题必须靠删除或扩容打破，这是结构性死锁。
4. 水位是最后防线而非调节旋钮：绕过它的代价是磁盘 100% 与节点假死，比写入失败严重得多。
5. 保护机制触发说明上游自动化（ILM）与监控预警（80%）早已失效；修复对象是链条而非水位本身。

### 常见误区

1. 把保护阈值当配置项调高"解锁"——移除最后防线后磁盘写满是必然，节点假死比写入报错严重一个量级。
2. 手动删除 `read_only_allow_delete` 块而未先释放空间——块解除后写入立即恢复，磁盘被迅速写满，触发更严重的故障甚至文件系统损坏。
3. 以为保留策略"配置了就会执行"——策略与执行之间的自动化断裂（ILM 未启用、脚本未部署、告警未触发）才是根因，水位触发只是迟到的症状。

### 延伸学习

1. Elasticsearch 官方文档 *Disk-based shard allocation settings*（三条水位、只读块与自动解除语义，本轮已核验）：https://www.elastic.co/guide/en/elasticsearch/reference/current/disk-allocator.html
2. Elasticsearch 官方文档 *ILM: Manage the index lifecycle*（保留策略自动化的标准机制）：https://www.elastic.co/guide/en/elasticsearch/reference/current/index-lifecycle-management.html （官方文档；本轮未逐字核验正文）

### 追问

1. 为什么把 flood_stage 调高是错误方向？什么情况下调阈值是合理的？——要点：flood_stage 是最后防线，越过它之后没有任何机制阻止磁盘 100%；调高只在"有明确计划在阈值窗口内释放空间"且确认其余节点健康时作为临时窗口使用，且必须设回滚提醒。
2. 为什么所有节点都超过 low 水位时集群会"卡死"在水位机制里？——要点：迁移需要有低水位目标节点，全员超 low 则无合法目标，shard 移不动、只读块解不了；这是容量问题的结构性信号，只能靠删除或扩容打破。
3. 只读块为什么设计成 `read_only_allow_delete` 而不是完全只读？——要点：删除是唯一既能被用户执行又能释放空间的操作，设计者预期恢复路径就是删数据；这也是"恢复路径写在保护机制的语义里"的案例。

### 小型实践

用 Docker 起 3 节点 ES 集群，创建一个测试索引写入 bulk 数据，把该节点磁盘水位临时调低（如 `low: 1mb / high: 1mb / flood_stage: 1mb` 绝对字节值）人为触发只读块，依次验证：① 只读块存在时 DELETE 索引仍可用；② 手动删块但磁盘仍超限后的行为；③ 删除数据降到 high 以下后块自动解除。全程记录三个水位的实际触发时序，写成一页 runbook。

## L01 LeetCode 8. 字符串转换整数 (atoi)

**题目 ID**：Q-20261125-L01 ｜ LeetCode 题号：8 ｜ 中文名：字符串转换整数 (atoi) ｜ 英文名：String to Integer (atoi) ｜ 难度：medium ｜ 一级类型：字符串解析与状态机 ｜ 标签：状态机、溢出钳制、一次遍历

### 题目

**官方链接（已核验）**：https://leetcode.cn/problems/string-to-integer-atoi/ （题目描述、5 个示例与约束均于本轮从官方页面核验；页面难度标签未渲染，medium 按官方分类记录）

实现 `myAtoi(string s)`，将字符串转换为 32 位有符号整数。算法规则（依官方描述）：

1. **空格**：读入并丢弃前导空格（`' '`）；
2. **符号**：检查下一个字符是否为 `'-'` 或 `'+'`，两者都不存在则假定结果为正；
3. **转换**：读入数字字符直到遇到非数字或字符串结尾；没有读到数字则结果为 0；
4. **舍入**：结果超出 32 位有符号整数范围 `[-2^31, 2^31 - 1]` 时，向下取 `-2^31`、向上取 `2^31 - 1`。

**输入**：字符串 `s`。**输出**：32 位有符号整数。

**约束**：`0 <= s.length <= 200`；`s` 由英文字母（大小写）、数字、`' '`、`'+'`、`'-'` 和 `'.'` 组成。

**示例（官方，已核验）**：`"42"` → `42`；`" -042"` → `-42`；`"1337c0d3"` → `1337`；`"0-1"` → `0`；`"words and 987"` → `0`。

### 先思考

1. 规则是严格顺序的：空格之后符号只能出现一次、数字之前，任何阶段遇到不合法字符就停止——尝试把流程画成一次遍历的状态推进，而不是多次扫描。
2. 溢出：Python 整数不会溢出，但钳制判断要在累积前做——想一想把 `num * 10 + d > INT_MAX` 改写成不产生中间大数的等价形式。
3. 边界：全空格、只有符号、符号后无数字、数字后跟字母——每一步"停在哪个阶段"决定返回什么。

### 参考答案

**解题思路（推荐解法：一次遍历 + 累积前钳制）**：用索引 `i` 一次遍历，三个阶段顺序执行——跳过空格；可选读一个符号位；循环读数字并在**累积前**检查是否越界，越界直接返回对应极值。不做第二次扫描、不先用大整数算完再钳制，而是在每步累积前判定，这与 C/C++ 实现中"中间值也不能溢出"的要求同构，也是面试想看的写法。

**正确性说明**：阶段顺序与官方规则一一对应——空格只在数字前有效（`"0-1"` 中 `-` 到来时已在数字阶段，停止，返回 0）；符号只允许一个（`"+-2"` 停在符号阶段返回 0）；钳制判定 `num > (INT_MAX - d) // 10` 等价于 `num * 10 + d > INT_MAX` 但不产生大中间值。对符号为负的情形，真实值恰好为 `-2^31`（即 num = 2147483648）时会被钳制返回 `-2^31`——结果数值正确，因为该值本身就是合法下界。

**复杂度**：时间 O(n)，每字符最多处理一次；空间 O(1)。

**Python 参考代码**：

```python
class Solution:
    def myAtoi(self, s: str) -> int:
        INT_MAX, INT_MIN = 2**31 - 1, -2**31
        i, n = 0, len(s)

        # 阶段 1：跳过前导空格
        while i < n and s[i] == ' ':
            i += 1

        # 阶段 2：可选符号，只允许一个
        sign = 1
        if i < n and s[i] in '+-':
            if s[i] == '-':
                sign = -1
            i += 1

        # 阶段 3：读数字，累积前钳制
        num = 0
        while i < n and '0' <= s[i] <= '9':
            d = ord(s[i]) - ord('0')
            if num > (INT_MAX - d) // 10:
                return INT_MAX if sign == 1 else INT_MIN
            num = num * 10 + d
            i += 1

        return sign * num
```

**关键边界情况**：全空格或空串 → 0；只有 `"+"` / `"-"` → 0（符号后无数字）；`" +-2"` → 0（空格后遇到非数字）；`"-91283472332"` → `-2147483648`（下界钳制，官方经典用例）；`"20000000000000000000"` → `2147483647`（上界钳制）；`"3.14159"` → `3`（`.` 属非数字，停止）；`"  +0 123"` → `0`（数字阶段遇到空格停止）。数字判别用 `'0' <= c <= '9'` 而非 `str.isdigit()`——后者对 `'²'` 等非 ASCII 数字返回 True，本题约束虽限定了字符集，但这一习惯在真实工程（外部输入解析）中是必需的防御。

**测试用例（3 个）**：

1. `myAtoi(" -042")` → `-42`（前导空格 + 负号 + 前导零，官方示例 2）
2. `myAtoi("-91283472332")` → `-2147483648`（负向下界钳制；注意与正数钳制值不同：`2^31 - 1` 与 `-2^31` 不对称）
3. `myAtoi("  +0 123")` → `0`（数字阶段遇空格停止，且 `sign * 0 = 0` 不受符号影响）

**可迁移解题能力**：顺序敏感的解析问题统一用"单次遍历 + 阶段状态推进"而非多遍扫描；溢出类问题把"先算后判"改为"累积前判定"；以及"钳制值不对称"（INT_MAX 与 INT_MIN 相差 1）这类细节意识。

### 关键点

1. 规则是严格顺序的：空格 → 符号 → 数字，任何阶段遇到不合法字符即停止，停在哪个阶段决定返回值。
2. 钳制必须在累积前判定，改写为 `num > (INT_MAX - d) // 10` 避免大中间值，与 C/C++ 实现约束同构。
3. 钳制值不对称：上界 `2^31 - 1`、下界 `-2^31`，负数恰为 `-2147483648` 时钳制返回值与真实值相同。
4. 数字判别用显式范围 `'0' <= c <= '9'`，`str.isdigit()` 对非 ASCII 数字返回 True 是解析外部输入的隐患。
5. 空串与"只有符号"返回 0 是"没有读到数字"规则的直接推论，不是特判。

### 常见误区

1. 先用 Python 大整数算完再钳制——思路可接受但失去了"中间值不可溢出"这一与工程实现同构的训练点，面试中被视为回避核心。
2. 把 `"0-1"` 处理成 `-1`——`-` 出现在数字阶段属于"遇到非数字字符"，必须停止，不能回头当符号。
3. 用 `s.lstrip()` + 正则一行流当作正解——能过但暴露的是"依赖运行时宽容"而不是边界分析，追问溢出与字符集契约时通常失守。
