## B01 浮点数与数值精度：`0.1 + 0.2 != 0.3` 之后的账目问题

- 题目 ID：`Q-20261117-B01`
- 编号：B01（非 AI Agent 基础题）
- 一级类型：编程语言与运行时；二级主题：数值表示与浮点精度（IEEE 754）
- 难度：基础题（中高）
- 考察点：二进制浮点的表示模型与不可精确表示的来源；舍入规则与误差在运算中的传播；运算顺序对结果的影响与灾难性抵消；特殊值 NaN / Inf 的传播语义；金额与累计量的工程处理方案。

### 题目

面试官问："在 Python 里 `0.1 + 0.2 == 0.3` 返回 False，很多人知道。但请不要停在'浮点误差'四个字——解释 IEEE 754 双精度为什么会这样，误差在什么运算模式下会从表示级放大到业务级，以及一个计费系统为什么不能靠'加个精度阈值'解决问题。"

### 先思考

- 为什么 0.1 在二进制下是无限循环小数？四舍五入到 52 位尾数后，存的到底是哪个数？
- 两个浮点数相加要经历哪几步？对齐指数时，较小的那个数会损失什么？
- 一万个 0.1 逐个累加，和一次乘以 10000，结果一样吗？为什么顺序会影响总和？
- `inf - inf`、`nan == nan`、`nan != nan` 各返回什么？这些行为对控制流意味着什么？
- 如果误差不可避免，正确性应该建立在哪种表示上：更长的尾数、十进制浮点，还是整数最小单位？

### 参考答案

**定义与表示边界**：IEEE 754 双精度用 1 位符号 + 11 位指数 + 52 位尾数表示二进制浮点数，形式为 `(-1)^s × 1.f × 2^e`。0.1 的十进制值对应二进制下的无限循环小数，存储时按最近舍入（round to nearest, ties to even）截断，因此内存里的 0.1 是一个比 0.1 略大（或略小）的近似值——这是表示级误差，与运算实现无关，任何遵守 IEEE 754 的语言（Python float、Java double、Go float64）行为一致。适用边界：浮点适合表示连续量（测量值、概率、权重、金额的**统计汇总**），不适合作为**需要精确相等判断**的量的存储。

**示例**：`0.1 + 0.2` 的实际运算是：两个近似值对齐指数（0.2 的指数比 0.1 大 1，0.1 的尾数右移一位再损失一位精度）、尾数相加、结果再舍入一次——所以误差不止来自表示，还来自每次运算的舍入。最终结果 `0.30000000000000004` 打印出来正好是舍入后的最短十进制表示。

**相近概念区别**：与"精度阈值比较"（`abs(a-b) < eps`）不是同一层——阈值只处理"判定"，不消除"累积"；与 `decimal.Decimal`（十进制浮点，0.1 可精确表示，但 `1/3` 仍不精确且速度慢数量级）的分工是精确十进制语义 vs 性能；与整数最小单位（以"分"存储金额）是彻底消除舍入的最稳方案，但要注意乘法（费率 × 金额）仍会引入除法舍入问题，需明确舍入方向。另注意与"灾难性抵消"区分：两个相近数相减会把两个数各自的相对误差放大成结果的巨大相对误差（有效位大量丢失），这是误差**放大**机制而非表示缺陷本身。

**典型应用**：通用工程中，账务、计费、库存、配额等"必须可精确对账"的量用整数最小单位或 Decimal 存储，浮点只用于报表聚合与模型计算；科学计算与 ML 中接受浮点但须控制求和顺序（分块求和、Kahan 补偿、配对求和）。NaN 的传播语义（任何比较返回 False、参与运算持续扩散）意味着它不能用于控制流分支——Python 里 `math.isnan` 是唯一的可靠判定；inf 由溢出和除零产生，`inf - inf = nan` 会在不可预期处出现。

**面试现场回答**：浮点误差的根因是 0.1 在二进制下不可精确表示，存储值已经是近似值；每次运算再叠加一次舍入，误差会沿着加法累积、被灾难性抵消放大。工程结论是：不能靠 epsilon 比较修复正确性——正确性要从表示层解决，对账类数据用整数最小单位或 Decimal，浮点只留给统计与近似计算；同时警惕 NaN 不可比较的特性对控制流的破坏。

### 关键点

- 误差是表示级的：IEEE 754 遵守者行为一致，与语言、优化器无关；换语言不解决问题。
- 每次运算都舍入一次：误差累积与运算顺序相关，`sum` 逐项累加与分块求和结果不同。
- 灾难性抵消：相近数相减放大相对误差，是"误差放大"而非"表示不准"，两者要分开说。
- NaN 参与一切比较都为 False，等值判断 `x == x` 可检测 NaN；它不能驱动 if 分支。
- 金额正确性建立在整数最小单位或 Decimal 上，舍入方向（银行家舍入 vs 四舍五入）是业务决策。

### 常见误区

- "换成更长的类型（float128 / long double）就精确了"——错误：二进制下 0.1 仍不可表示，只是误差更小，累积问题依旧。
- "用 `abs(a-b) < 1e-9` 就能修复"——错误：这只改判定不改累积，阈值选择本身依赖量纲与规模，且大量累积后误差可能超过任何先验阈值。
- "Decimal 万能"——不完整：Decimal 精确表示十进制输入，但除法仍产生舍入，且性能差一个数量级；高频路径应整数化，Decimal 留给边界交互。

### 延伸学习

- Python 官方教程第 15 章 Floating Point Arithmetic: Issues and Limitations（docs.python.org/3/tutorial/floatingpoint.html）：官方对表示误差、求和顺序与 Decimal 分工的说明。
- David Goldberg, "What Every Computer Scientist Should Know About Floating-Point Arithmetic"（ACM Computing Surveys, 1991）：表示模型、舍入与抵消的标准参考文献。

### 追问

**追问：为什么" Decimal 处理 0.1 精确"不能推出"Decimal 处理一切精确"？**
回答要点：Decimal 是十进制浮点——0.1 可精确表示，但 1/3 这样的无限小数在有限位下仍需舍入；它消除的是"十进制输入被二进制扭曲"这一层，不是消除舍入本身；金额场景靠"整数最小单位 + 明确舍入方向"双保险，而不是裸用 Decimal。

## B02 上下文退化及其归因（Context Rot）：128K 窗口的"有效预算"与标称上限

- 题目 ID：`Q-20261117-B02`
- 编号：B02（AI Agent 基础题）
- 一级类型：上下文工程与能力封装；二级主题：上下文退化及其归因
- 难度：基础题（中高）
- 考察点：上下文退化的定义与"窗口 = 上限 ≠ 均匀预算"；退化非均匀性的三个实测因素；归因方法论（单一变量对照、位置控制、focused vs full）；退化与上下文工程三手段（选择、压缩、隔离）的因果关系。

### 题目

面试官问："模型标称 128K 上下文。团队把所有工具输出、历史轨迹、检索结果全部塞进上下文，效果反而比精挑 20K 时更差。请解释'上下文退化'是什么、退化为什么非均匀，以及你会用什么方法把线上退化归因到具体原因。"

### 先思考

- "窗口装得下"和"模型用得好"是同一个承诺吗？退化是均匀下降还是分场景突变？
- 如果只改变输入长度、保持任务不变，测出来的是哪个变量的影响？
- needle 与问题的语义相似度、干扰项数量、语料结构，哪个因素在实验里影响最大？
- 一个反直觉的实验发现：把语料句子打乱、去掉逻辑连贯，性能反而更好——这说明模型对上下文做了什么假设？
- 这些发现如何转化为 Agent 上下文组装时的确定性规则？

### 参考答案

**定义**：上下文退化（context rot）指随输入 token 数增长，模型在同一任务上的表现变得不可靠，且退化方式**非均匀**——即使任务复杂度完全不变。它修正了"处理第 10000 个 token 与第 100 个 token 一样可靠"的隐含假设：标称窗口是上限，不是均匀可用的预算。适用边界：退化规律来自受控实验，外部效度有限，具体到某模型某任务必须自测，不能拿论文结论替代分桶评测。

**简洁示例**：Chroma 2025-07 的研究报告在 18 个模型上控制单一变量（只改输入长度）实验：needle 与问题的语义相似度越低，退化越快；干扰项（distractor）从 0 到 4 个持续损害性能且各干扰项影响不均；LongMemEval 中仅含相关内容的约 300 token 输入显著优于含无关内容的约 113K 完整输入；最反直觉的是，打乱语料句子顺序、去掉逻辑连贯性反而让所有模型表现更好——模型对"连贯文本"做了更多整体性假设，检索场景中这反而制造干扰。

**相近概念区别**：与"上下文窗口上限"（硬截断，超了报错）不同，退化是软性质量衰减，不报错、难察觉；与"lost in the middle"（位置偏差）不同，位置只是退化因素之一，且位置效应分模型、并不总在中间最差；与注意力机制的原理性解释（softmax 分摊、注意力稀释）不同，报告刻意不解释内在机制，只给出可复现的现象规律——面试时把"现象"和"机制假说"分开说，是加分项。

**在 Agent 系统中的应用**：退化是上下文工程三手段（选择、压缩、隔离）的实证依据——选择（组装期决定放什么）直接降低干扰项数量；压缩（事后裁剪）减少无关内容；隔离（子 Agent 拆分）把各干一团上下文限制在独立窗口。归因方法落到工程上是四步：控制长度单一变量做离线对照、按输入长度分桶看线上成功率、needle-question 相似度分层复现、focused vs full 消融对比；结论用于设定"有效上下文预算"，而非依赖标称窗口。

**面试现场回答**：上下文退化是输入越长、同一任务表现越不可靠的现象，且非均匀——受语义相似度、干扰项、语料结构影响，位置只是因素之一。窗口标称值是上限不是有效预算。归因靠控制变量：只变长度的对照实验、线上按长度分桶、相似度分层、消融对比。Agent 工程上这就是选择优先于压缩、压缩优先于隔离的依据——减少无关内容比事后补救便宜。

### 关键点

- 窗口 = 上限 ≠ 均匀预算；退化在"最简单任务"上也会发生。
- 非均匀性三因素：needle-question 语义相似度（越低退化越快）、干扰项数量、haystack 结构（连贯反而更差）。
- 归因必须控制单一变量：长度、位置、相似度、干扰项逐个隔离，否则结论混叠。
- 退化无报错信号，只能靠分桶指标发现；评测集须覆盖长输入场景。
- "信息在上下文中的呈现方式比信息是否存在更重要"——这是选择 / 压缩 / 隔离三手段的实证锚点。

### 常见误区

- "模型够新、窗口够大，塞满就行"——错误：18 个模型一致退化，包括 2025 年最新的前沿模型；增大窗口不消除退化。
- "把退化归因于 lost in the middle 一个因素"——不完整：位置效应分模型且非总在中间，只按位置优化会漏掉相似度与干扰项这两个更强的因素。
- "退化是模型问题，工程无法干预"——错误：focused 300 token 优于 full 113K 正是工程可干预的证据；干预点是组装期选择，不是事后祈祷。

### 延伸学习

- Chroma Research, "Context Rot: How Increasing Input Tokens Impacts LLM Performance"（research.trychroma.com/context-rot，2025-07-14）：18 模型、四组控制实验与 LongMemEval 的结论来源（本轮已核验页面）。
- 在自己的评测集上按输入长度分桶重跑一次回归，观察自家场景的退化曲线形状（实践方向）。

### 追问

**追问：既然结构连贯反而有害，是不是检索系统应该把文档打散成互不连贯的片段？**
回答要点：不能直接推——该发现来自检索式任务（needle 查找），而摘要、推理类任务依赖结构连贯性；正确做法是按任务类型选择呈现方式，检索块独立成段、推理链保持连贯，并把"结构 vs 打散"作为评测变量而非信念。

## S01 只读工具的副作用边界：仓库自带配置把"只读"变成任意命令执行

- 题目 ID：`Q-20261117-S01`
- 编号：S01（AI Agent 场景题）
- 一级类型：AI 安全与治理（兼属工具与互操作协议）；二级主题：只读工具的副作用边界（数据作为执行通道）
- 难度：场景题（高）
- 考察点："只读"是接口声明而非执行保证；信任域内的数据文件可作为命令执行通道；安全边界必须落在机制层（隔离与出网控制）而非声明层；与网络类攻击面（跨站 / SSRF / TOCTOU）区分的新一类；治理与审计如何覆盖"数据驱动的执行"。

### 题目

**业务背景**：公司为内部研发团队部署了代码问答 Agent，接入一个基于 MCP 官方参考实现（git 服务器）的 Git 工具服务。工具权限模型按接口声明分级：`git_status`、`git_log`、`git_diff` 等只读工具免审批，`git_commit`、`git_push` 等写工具需人工审批。

**系统规模与架构**：约 300 名工程师使用，日均 2 万次工具调用；Agent 通过统一工具网关调用 Git MCP 服务，服务运行在共享的容器池中，容器对内网 Git 仓库有读权限、对少量构建系统有写权限；处理对象包括外部贡献者提交的 PR 仓库镜像。

**故障现象**：安全团队在审计中发现，某个处理外部 PR 的 Agent 会话中，`git_status` 的执行导致了一条从仓库配置注入的命令被执行，命令试图回连外部地址拉取脚本。事后排查确认是 MCP 官方参考服务器已披露的漏洞模式（GHSA-6hqx-gqrx-c5r2，v2.4.0 修复）：仓库自带的 `.git/config` 中 `core.fsmonitor` 可指向任意命令，git 的只读操作（如 status）会触发 fsmonitor 钩子执行该命令。

**目标与限制**：保持只读工具免审批的体验（全审批会毁掉产品价值）；不改 Agent 编排框架；修复必须在工具服务与容器层落地，两周内完成。

**需要取舍的问题**：权限分级继续以接口声明为依据（升级成本最低，但声明被击穿的先例已出现），还是转为以运行时隔离强度为依据（更安全，但只读工具也要进沙箱，成本与延迟上升）？

### 先思考

- "只读"声明约束的是调用者（Agent / 用户），还是被调用进程的执行行为？这两个对象一样吗？
- git 为什么会在只读操作里执行用户可配置的命令？这类"领域自带的间接执行机制"还有哪些同构物？
- 防御应该加在声明层（工具分级表）、校验层（检查 config 内容），还是机制层（沙箱与出网）？各层能防住什么、防不住什么？
- 校验 `.git/config` 的内容可行吗？如果仓库里有别的可执行钩子（hooks、attributes、alternates）呢——逐点修补的收敛终点在哪里？
- 审计链如何回答"这条命令是谁的意志：Agent、用户还是仓库内容"？

### 参考答案

**结论**：只读分级可以保留，但只读的保证必须从接口声明迁移到执行机制——凡处理不可信仓库的会话，只读工具也要在隔离运行时（无出网、文件系统最小挂载）中执行；声明层只作为路由与体验分级，不作为安全边界。

**问题拆解**：第一步，明确漏洞类别——这不是网络类攻击面（跨站、SSRF、TOCTOU 已在既往治理覆盖），而是"数据即执行通道"：仓库是数据，但 git 这个领域自带把配置文件提升为可执行机制的间接引用（core.fsmonitor、hooks、attributes filter、alternates）。信任域内的输入数据不等于可信代码。第二步，划定修复层：声明层（分级表）无法防，因为它约束的是调用者意图而非执行行为；内容校验层（扫描 config）只能逐点堵，git 的间接执行机制面还在扩大（本类漏洞已在 write、read、move 三条路径反复出现），按类收敛优于逐点修补；机制层（沙箱 + 出网控制）是唯一与执行行为对齐的边界。第三步，落地分级：处理内部可信仓库的会话保持现有体验；处理外部 PR 镜像的会话强制进强隔离池。

**核心方案**：① 工具网关按"仓库来源信任级"路由到两个执行池：内部池（现有容器，禁写仍审批）与外部池（强隔离：无出网、tmpfs 挂载仓库镜像、进程级权限最小化）。② 镜像化落地：外部仓库先在隔离的镜像步骤克隆并剥离或重写可执行配置（fsmonitor、hooks、proxy），再供工具服务读取——执行与配置注入分离。③ 出网默认拒绝：外部池所有工具进程 egress 全禁，fsmonitor 即使被触发也无法回连。④ 升级 pin 到修复版 v2.4.0 并纳入供应链台账（版本 + 权限面 diff 门禁）。

**执行流程**：PR 进入 → 镜像步骤（隔离环境克隆 + 配置剥离 + 剥离记录入审计）→ 外部池会话（只读工具直接执行、写工具走审批）→ 会话结束镜像销毁。

**技术选型与依据**：隔离运行时选 gVisor 类系统调用过滤而非裸容器（裸容器共享内核，fsmonitor 触发的命令仍在同一内核跑）；不选"内容扫描 config"为主防线（漏报不可证明，仅作为纵深一层）；不选全量审批（体验归零且审批疲劳会反过来降低审批质量）。

**方案取舍**：镜像化引入镜像时延（秒级）与存储成本，换取执行与配置注入的结构性分离；两池架构增加路由复杂度，换取内部体验不变；按类收敛（拦"配置可执行"这一类）而非逐点修补，用一次性机制成本终止反复出现的三路径重现。

**失败路径与边界条件**：镜像步骤自身失败时 fail-closed（外部 PR 会话拒绝启动而非降级到不可信池）；剥离清单之外的未知执行机制（如未来 git 新增配置项）依赖 egress 全禁兜底——即使执行发生也无法外联或回传；镜像剥离不能修复被 Agent 读取后进入上下文的恶意内容（prompt injection 路径），那条线由内容层闸门另行处理，不在本题范围内但须明确声明边界。

**超时 / 重试 / 幂等 / 恢复**：镜像步骤超时（60s）后 fail-closed 并留审计；重试幂等键为仓库 commit SHA + 剥离配置版本；隔离池崩溃按会话重启，无跨会话状态。

**安全 / 权限 / 成本 / 延迟 / 可靠性**：权限模型从"接口声明分级"升级为"来源信任级 × 接口声明分级"二维；审计须记录镜像剥离动作、剥离前后配置 diff 与会话使用的池级，使"谁注入了配置、执行发生在哪个边界内"可回答；成本为隔离池实例（约 30% 容器开销）与镜像存储；延迟增加秒级镜像步骤，只读工具本身的响应时延不变；可靠性上 egress 全禁使被注入命令最多浪费 CPU，不构成外联通道。

**评测指标与观测**：上线前用 GHSA-6hqx 的复现仓库做红队回归（fsmonitor 注入、hooks 注入、attributes filter 注入三类用例全部被阻断）；上线后观测隔离池 CPU 异常消耗（被注入命令的痕迹）、镜像剥离命中率（发现被剥离配置的比例反映攻击面真实存在率）、外部池会话的工具错误率（确认隔离未破坏正常只读能力）。

**三层能力归属**：模型层只负责生成工具调用参数（且其输入已被仓库内容污染，不可信任其判断）；Agent 编排层负责会话路由与审批流；安全保证完全由传统软件层提供（隔离运行时、egress 控制、镜像剥离）——这正是"授权边界应置于模型之外"的具体落点。

### 关键点

- "只读"约束的是调用者意图，不约束实现内部执行行为——接口声明不能作为安全边界。
- 仓库是数据也是执行通道：领域自带的间接执行机制（fsmonitor / hooks / attributes / alternates）使校验清单不可穷尽，须按类收敛。
- 防线对齐执行行为：隔离运行时 + egress 全禁是唯一可证明的边界，内容扫描只能作纵深一层。
- 来源信任级与接口分级正交：外部 PR 与接受外部依赖的内部仓库都可能注入配置，信任级按内容来源动态判定。
- 镜像剥离 fail-closed、egress 兜底、审计记录剥离 diff 与池级——修复可验证、注入可回答。

### 追问

**追问 1：为什么"扫描 .git/config 内容"不能作为主防线？**
回答要点：逐点修补已被实践证伪——同一 TOCTOU 类在 write、read、move 三条路径连续三轮重现；git 的间接执行机制清单不可穷尽（fsmonitor、hooks、attributes、alternates、proxy……），扫描器漏报无法证明安全；机制层与执行行为对齐，是唯一可证明的边界。

**追问 2：内部可信仓库就不会有同样问题吗？什么时候内部仓库也会变成不可信源？**
回答要点：内部仓库在依赖投毒、供应链攻击或离职员工场景下同样可注入配置；信任级不应按"内外网"静态划分，而按仓库内容来源动态判定——引入外部依赖、接受外部 PR 的内部仓库也应进入镜像化路径；这是"信任域内输入数据不等于可信代码"的完整推论。

**追问 3：如果业务要求外部池也能执行构建脚本（不能全禁出网），方案怎么改？**
回答要点：从"全禁"退到"代理出网"——隔离池所有出网经 egress 代理按域名白名单与协议白名单放行，fsmonitor 类回连因目标不在白名单而失败；同时把执行分为"读仓库"与"跑构建"两个阶段，构建阶段用声明过的构建定义（非仓库自带脚本）驱动，仓库内容永远不直接进入执行路径。

### 小型实践（30–60 分钟）

在本地建一个 git 仓库，把 `.git/config` 设置 `core.fsmonitor = echo pwned`，然后用 `git status` 观察命令是否被执行（Linux/macOS 本地即可复现）；随后把仓库目录挂进一个无网络的容器再跑 `git status`，对比两层的实际防御差异，并写一份 200 字的"声明层 / 校验层 / 机制层各自能防住什么"的总结。

### 常见误区

- "只读工具不产生副作用，所以不需要隔离"——错误：只读声明约束的是接口语义，不约束工具实现内部的命令执行；fsmonitor 证明只读操作可以执行任意命令。
- "扫描并清理恶意配置即可"——错误：间接执行机制清单不可穷尽，逐点修补在该漏洞类上已三轮重现；按类收敛 + 机制兜底才是可证明方案。
- "这是 MCP 的 bug，升级就好"——不完整：升级修复的是这一个实现；"数据即执行通道"是领域自带的模式，任何接 git、包管理器、构建系统的工具服务都存在同构面，治理必须落在运行机制层。

## S02 TCP keepalive 与中间设备空闲超时：凌晨批量任务的偶发 connection reset

- 题目 ID：`Q-20261117-S02`
- 编号：S02（非 AI Agent 场景题）
- 一级类型：操作系统与网络；二级主题：长连接空闲超时、TCP keepalive 与连接存活判定
- 难度：场景题（高）
- 考察点：TCP keepalive 三参数与默认值的时间线；连接"可用"是三方共识而非两端事实（NAT / LB 连接跟踪表）；keepalive 只证明"对端有响应"不证明"服务活着"；应用层心跳与幂等重连的取舍；恢复路径上的幂等设计。

### 题目

**业务背景**：支付渠道接入网关与上游渠道系统之间维持 HTTP keep-alive 长连接池（连接复用率约 85%），每日凌晨 2 点有一个批量对账任务集中发起约 3 万笔查询。链路上有云平台 NAT 网关与一个四层负载均衡，其中 NAT 的连接跟踪表空闲超时为 350 秒，四层 LB 的空闲超时为 900 秒。

**系统规模与数据流**：网关 4 个实例，每个实例维护每渠道约 40 条长连接；上游服务为有状态会话网关，新建连接需 3 次 TLS 握手，成本高，因此连接池策略偏保守（空闲连接保留 1 小时才回收）。

**故障现象**：每天凌晨批量任务开始后约 2–5 分钟，出现 30–80 笔查询以两种形态失败：其一，客户端发出请求后立刻收到 RST（connection reset）；其二，请求发出后挂起 30 秒超时。日间流量几乎无此现象。重启连接池后短时间内恢复正常，次日复发。

**目标与限制**：失败率压到 0.01% 以下；不增加上游容量；改动范围限于网关与连接池层；批量任务的重试必须安全（查询本身幂等，但同一批次内有严格时限，单笔重试预算 10 秒）。

**需要取舍的问题**：靠调大 TCP keepalive 频率让连接"过 NAT 检查"（探测成本与 NAT 表污染），靠应用层心跳主动保活（请求量与复杂度上升），还是接受空闲连接会被掐断的事实、把工程重点放在"发现死连接的速度 + 重连的成本 + 重试的幂等"上？

### 先思考

- 批量任务前连接池里的连接已经空闲多久？这个时长与 350 秒、900 秒、7200 秒三个超时有什么关系？
- 连接被 NAT 掐断时，两端各自知道吗？谁会先发现，通过什么信号（RST / 超时）？
- TCP keepalive 默认为什么几乎不触发？它的探测语义能证明什么、不能证明什么？
- "发出请求立刻收到 RST"和"挂起 30 秒超时"分别对应哪种掐断形态？两者的恢复策略相同吗？
- 如果接受连接随时可能死，系统的正确性应该建立在连接上还是请求上？

### 参考答案

**结论**：根因是空闲连接存活时间超过了链路上最短的第三方空闲超时（NAT 350 秒），凌晨批量任务在"长时间空闲的假活连接"上发起第一笔请求，被中间设备静默掐断的连接分别以 RST 或挂起超时两种形态失败。修复的主线不是"保活"，而是缩短有效空闲窗口（池内闲置连接按 300 秒主动回收或预热）+ 请求级快速失败重试 + 幂等重发，keepalive 只作为快速探测死连接的辅助手段。

**问题拆解**：其一，时间线核对：日间流量持续，连接空闲时间短于 350 秒，NAT 表项始终新鲜；凌晨任务前的低峰期连接空闲可达 30 分钟以上，NAT/LB 连接跟踪表项早已过期，中间设备对后续报文的行为（丢弃或发 RST）因设备而异——这正是两种失败形态。其二，两端视角不对称：服务端连接仍是 ESTABLISHED，客户端发第一个包才撞上失效表项；keepalive 默认 7200 秒空闲才探测，远大于 NAT 超时，因此从未起过作用。其三，失败形态分化：收到 RST 是中间设备主动重置，可立即重试新连接；挂起 30 秒是报文被静默丢弃，等待超时浪费重试预算——需要分层超时（连接借用前先做毫秒级探测或首字节超时收紧到 3 秒）把第二种形态快速转化为可重试失败。

**核心方案**：① 池管理改为"空闲 300 秒主动回收 + 批量任务前预热"：批量任务调度器提前 60 秒触发池预热（按目标并发预建连接），任务期间池不回收；② 借用检查：从池中取连接时若空闲超过 300 秒，丢弃重建（重建成本 3 次 TLS 握手约 200ms，远低于 30 秒挂起）；③ 请求级快速失败：写请求首字节超时收紧到 3 秒，触发即弃连接重试，读请求天然幂等、写请求带请求 ID 幂等重发；④ 可选 keepalive 辅助：对池内连接启用 `SO_KEEPALIVE` 并按连接覆盖参数（`TCP_KEEPIDLE=240, TCP_KEEPINTVL=30, TCP_KEEPCNT=3`），使死连接在被借用前就被内核标记错误、从池中剔除——注意这是探测加速，不是存活的证明。

**执行流程**：任务调度 → 预热连接（新连接进池，表项新鲜）→ 请求借用（空闲检查）→ 失败分类（RST 立即重建重试；首字节超时弃连重建重试）→ 重试预算 10 秒内最多 2 次 → 超预算标记该渠道连接异常并告警。

**技术选型与依据**：选池层空闲回收 + 借用检查为主（改动集中在网关，行为可预测），不选单纯调 keepalive（7200 秒默认与 NAT 350 秒差 20 倍，且 keepalive 探测报文自身会刷新 NAT 表项、可能掩盖真实的池回收需求）；不选应用层心跳为主（每连接心跳请求量与上游会话网关压力上升，且心跳证明的是传输层活着，不证明服务逻辑可用）；幂等重发依赖请求 ID + 上游查询接口天然幂等。

**方案取舍**：主动回收牺牲部分连接复用率（85% → 预计 78%），换取"池内连接永远新鲜于最短第三方超时"这一不变量；预热引入 60 秒提前调度依赖，换取任务窗口内的失败归零；keepalive 参数按连接覆盖而非改系统默认（`/proc/sys/net/ipv4` 全局值影响其他服务）。

**失败路径、边界条件与恢复**：预热失败（上游不可达）时任务按现有连接降级执行并提高重试预算；RST 重试须防"上游真的崩了导致重试风暴"——按渠道做重试熔断（连续 20 次 RST 则暂停借用并告警，而非无限重建）；挂起超时的 30 秒兜底超时保留，作为 3 秒首字节超时的第二层；连接池上限保护重建风暴不耗尽文件描述符。

**幂等与重试**：查询请求幂等，重试直接重发；批量任务整体按批次 ID 去重（调度器重复触发安全）；重试预算（10 秒 / 2 次）在任务级共享，避免单笔重试挤占批次时限。

**性能、可用性与验证指标**：新连接重建成本可控（预热摊平）；可用性目标即 0.01% 失败率，分形态统计（RST 型 / 超时型）验证修复对两种形态分别生效；上线后观测池内连接空闲时长分布与 NAT 表项对齐性、批量窗口失败笔数、重建 QPS 与文件描述符水位。验证方法：压测环境模拟 350 秒空闲后发请求，确认两条失败路径均被借用检查与首字节超时拦截。

### 关键点

- ESTABLISHED 是两端本地视图，不是可用性证明；链路上最短的第三方空闲超时（350s）才是实际约束。
- keepalive 默认 7200s 远大于 NAT 超时且只证明协议栈有响应——它只是死连接的探测加速器，不是保活方案。
- 失败形态分化：RST 可立即重建重试，静默丢弃须用首字节短超时把未知态压缩为显式失败。
- 不变量设计：池内连接空闲时间恒小于最短第三方超时（300s 回收 + 任务前预热），正确性建立在请求级幂等之上而非连接上。
- 重试须防风暴：按渠道熔断（连续 RST 暂停重建）、重试预算共享、连接池上限保护 fd。

### 追问

**追问 1：keepalive 探测成功是否证明上游服务可用？为什么还要首字节超时？**
回答要点：不能——keepalive 探测由内核 TCP 栈应答，只证明对端主机 TCP 协议栈有响应，应用进程可能已挂死或阻塞；首字节超时检测的是"请求得到应用层处理"这一真实承诺，两者作用在不同层、不可互相替代。

**追问 2：为什么 RST 和挂起超时要用不同的恢复策略？**
回答要点：RST 是显式失败信号，连接状态明确，可立即重建重试（快速失败路径）；挂起意味着报文被静默丢弃，连接生死未知，继续等只浪费预算，策略是收紧首字节超时把未知态尽快转化为显式失败——本质是把"三态未知"压缩为可判定的失败，这与工具调用超时语义的处理是同构的。

**追问 3：如果上游会话网关是有状态的（连接绑定会话），重建连接的成本和数据一致性问题怎么处理？**
回答要点：有状态会话使"重建"从握手升级为会话恢复——需在上游提供会话令牌（连接断开时会话可按令牌恢复而非重建）；同时请求 ID 幂等重发要覆盖会话恢复期间的重复投递；若上游无法支持会话恢复，则连接池退化为"请求内连接"（不复用），用吞吐损失换一致性确定性——取舍必须显式做出而非默认。

### 小型实践（30–60 分钟）

在本机用 `python3 -c` 起一个 TCP echo 服务，用 `nc` 建立连接后挂起超过 75 秒观察默认行为；随后用 Python socket 设置 `setsockopt(SOL_SOCKET, SO_KEEPALIVE, 1)` 并通过 `TCP_KEEPIDLE/TCP_KEEPINTVL/TCP_KEEPCNT` 把探测压到 10 秒内，用 `tcpdump` 观察 keepalive 探测报文；再用 `iptables` 模拟 DROP（静默丢弃）与 REJECT（RST）两种掐断，记录两种形态下客户端的失败信号差异。

### 常见误区

- "连接是 ESTABLISHED 就是可用的"——错误：TCP 状态是两端本地视图，NAT / LB 连接跟踪表是隐含的第三方状态，表项过期后 ESTABLISHED 连接是假活。
- "调大 keepalive 就能防掐断"——不完整：默认 7200 秒远大于常见 NAT 超时，即使调小，keepalive 也只探测传输层，不证明应用可用；它只能作为死连接的探测加速器。
- "失败就重试，不用区分失败形态"——错误：RST 与静默丢包的可判定性不同，统一用长超时会把批量任务的重试预算耗在等待上；分层超时 + 分类恢复是必要的。

## L01 LeetCode 94. 二叉树的中序遍历

- 题目 ID：`Q-20261117-L01`
- 编号：L01
- 题号：94；中文名：二叉树的中序遍历；英文名：Binary Tree Inorder Traversal；难度：easy（官方页难度标签本轮未渲染，按标准分类记录 easy，未直接核验）
- 官方链接：https://leetcode.cn/problems/binary-tree-inorder-traversal/（已核验）
- 一级类型（索引口径）：二叉树（迭代遍历 + 栈）

### 题目

给定二叉树的根节点 `root`，返回它的**中序**遍历结果（左 → 根 → 右 的顺序）。

**输入 / 输出**：输入为二叉树根节点；输出为节点值组成的数组，顺序为中序。

**约束**：节点数范围 `[0, 100]`；`-100 <= Node.val <= 100`。

**示例**（官方三例，已核验）：
- `root = [1,null,2,3]` → 输出 `[1,3,2]`
- `root = []` → 输出 `[]`
- `root = [1]` → 输出 `[1]`

**进阶**：递归算法很简单，你可以通过迭代算法完成吗？

### 先思考

- 递归中序的执行顺序是"一路向左 → 回溯 → 输出 → 转右"。回溯发生时，"下一个该处理的节点"存在哪里？
- 迭代实现里，`cur` 指针和栈各承担什么职责？什么时候入栈、什么时候出栈、什么时候输出？
- 循环的继续条件为什么是 `cur != null || stack 非空` 两个条件，缺一不可？
- 输出时机在弹栈后——为什么不能在入栈时输出（对比前序遍历的差别）？

### 参考答案

**解题思路（推荐：迭代 + 显式栈）**：用一个 `cur` 指针模拟"一路向左"的下探，用一个栈记录下探路径上的祖先节点。`cur` 非空就入栈并左移；`cur` 为空说明左子树处理完毕，弹栈顶节点输出（它就是当前最左未输出的节点），然后转向其右子树。循环继续条件是 `cur != null or 栈非空`：栈非空说明还有祖先待输出，`cur` 非空说明还有未下探的左子树。

**正确性说明**：栈中保存的是"输出过左子树但尚未输出自身"的节点集合，`cur` 表示下一个待下探的子树根。任意时刻，下一个中序输出节点要么是 `cur` 最左链的末端（对应入栈后弹出），要么是栈顶祖先——两个条件恰好覆盖所有情况，每个节点恰好入栈、出栈、输出各一次，顺序与递归定义的中序一致。

**复杂度**：时间 O(n)——每节点入栈出栈各一次；空间 O(h)，h 为树高，最坏（单链）O(n)，平衡树 O(log n)。

**Python 参考代码**（已通过官方 3 示例 + 3 自建用例 + 3000 组随机对拍，对照递归中序独立实现）：

```python
# Definition for a binary tree node.
# class TreeNode:
#     def __init__(self, val=0, left=None, right=None):
#         self.val = val
#         self.left = left
#         self.right = right
from typing import Optional, List

class Solution:
    def inorderTraversal(self, root: Optional[TreeNode]) -> List[int]:
        res, stack, cur = [], [], root
        while cur or stack:
            while cur:                # 一路向左，路径祖先全部入栈
                stack.append(cur)
                cur = cur.left
            cur = stack.pop()         # 左子树处理完毕，弹栈输出
            res.append(cur.val)
            cur = cur.right           # 转向右子树
        return res
```

**边界情况**：空树（`root = None`，循环一次不进，返回 `[]`）；单节点；全左链（栈深达 n）；全右链（`cur` 转右后持续下探）；中序与"值排序"无关——本题是普通二叉树不是 BST，勿按大小假设（如 `[1,2]` 输出 `[2,1]`）。

**测试用例**：
1. `[1,null,2,3]` → `[1,3,2]`（官方示例，右子树的左孩子先输出）
2. `[]` → `[]`（空树）
3. `[1,2]` → `[2,1]`（全左链：先输出左孩子再输出根）
4. `[3,1,null,null,2]` → `[1,2,3]`（左孩子的右子树穿插在根之前）

**进阶追问方向**：Morris 遍历 O(1) 空间——利用叶节点空的右指针临时指回中序后继，输出后恢复，代价是修改指针需还原且实现复杂。

**可迁移的解题能力**：把递归的隐式调用栈显式化——识别"回溯点在哪里、状态存哪里"两个问题；这套"指针 + 显式栈"的框架直接迁移到 BST 迭代器（LC 173）、中序后继（LC 285）、迭代遍历家族（94 / 144 / 145）。与 AI Agent 工程的自然联系（仅顺带一提）：递归转迭代同构于"把隐式计划变成显式状态机"，栈对应 Agent 的待办状态，可检查点持久化——本题在此不展开。

### 追问

**追问：同样的栈框架怎么改成前序和后序？后序的难点在哪？**
回答要点：前序只需把输出移到入栈时、弹栈后先压右再压左；后序输出时机在两次访问之后，直接套框架无法区分"右子树是否已处理"——两个标准解法：前序（根右左）结果整体反转，或在栈中记录"上次输出的节点"，弹栈后若上次输出是当前节点右孩子则输出自身。难点本质：中序/前序的"输出时机"与"访问时机"可以合并，后序必须显式区分两次经过。

### 关键点

- 循环条件 `cur != null or 栈非空` 缺一不可：只看 `cur` 会漏掉回溯，只看栈会漏掉右子树下探。
- 输出发生在弹栈后：入栈节点尚未"轮到"，这是中序与前序在框架上的唯一差别。
- 空间是树高 O(h) 而非 O(n)——除非树退化为单链。
- 本题与 BST 无关：中序 ≠ 排序输出，勿加值序假设。

### 常见误区

- 把输出写进入栈分支（`stack.append(cur)` 时 `res.append`）——那是前序；中序必须弹栈后输出，否则顺序错。
- 循环条件只写 `cur != null`——处理完根转右后 `cur` 会变 None，但栈里还有祖先待输出，提前退出漏节点。
- 手算期望值时按 BST 排序直觉（如把 `[3,1,null,null,2]` 算成 `[1,3,2]`）——中序由结构决定，本题正确输出是 `[1,2,3]`，手算必须跟指针走。
