## B01 · SSE、WebSocket 与长轮询：流式传输的协议边界

- 题目 ID：`Q-20261111-B01`
- 一级类型：操作系统与网络；二级主题：HTTP、SSE、WebSocket 和 RPC

### 题目

服务端需要向浏览器持续推送增量数据（例如日志尾随、行情更新、模型生成的逐 token 文本流）。请说明 SSE（Server-Sent Events）、WebSocket 与 HTTP 长轮询三者的协议语义差异，SSE 依赖哪些 HTTP 特性，EventSource 的自动重连与 `Last-Event-ID` 如何工作，以及在什么条件下 SSE 的实际表现会偏离"协议上的承诺"。

### 先思考

- 三者中哪一个是真正的双向通道？哪一个复用了普通 HTTP 响应的语义？
- SSE 本质上是一个不关闭的 HTTP 响应：它的 Content-Type 是什么？消息格式由哪些字段构成？
- 浏览器断线后 EventSource 会做什么？`id` 字段在这个流程里扮演什么角色？
- 协议说"持久推送"，那么 HTTP/1.1 的浏览器对同一域名的连接数限制，会怎样改变 SSE 的实际并发能力？

### 参考答案

**结论：三者只有 WebSocket 提供双向通道；SSE 是"一直不结束的 HTTP 响应"之上的单向推送协议，语义简单但它的可用性完全受制于 HTTP 基础设施的层层约束；长轮询是三者中开销最高、语义最弱的兜底方案。**

SSE 依赖三个 HTTP 特性：其一，服务端以 `Content-Type: text/event-stream` 返回一个不关闭的响应；其二，消息是 UTF-8 文本块，由空行分隔，字段包括 `event`（事件类型，缺省为 message）、`data`（数据，多行 data 会被拼接并以换行连接）、`id`（事件 ID）与 `retry`（重连等待毫秒数），以冒号开头的行是注释，常用作保活心跳。其三，浏览器端的 EventSource 在连接意外关闭时**默认自动重连**，并把最近收到的 `id` 记为"最后事件 ID"，重连时通过 `Last-Event-ID` 请求头带给服务端——所以 `id` 的语义责任在服务端：它必须映射到可恢复的流位置（例如日志 offset、批次序号），否则重连只是重复从头部开始。

与 WebSocket 的取舍：WebSocket 走独立的 `ws://` 协议（升级握手），双向、支持二进制帧、不受 HTTP 响应语义约束，但要自建心跳、重连、消息边界与代理穿透；SSE 复用 HTTP，天然兼容现有认证、代理、CDN 与负载均衡语义，单向流式输出场景（模型 token 流是最典型的例子）下复杂度显著更低。

SSE 实际表现偏离协议承诺的三个条件：第一，**代理与网关缓冲**——若中间任何一跳对响应做缓冲（例如 gzip 压缩缓冲、Nginx 未关 `proxy_buffering`），增量消息会被攒住，客户端看到的是"卡住后一次性吐出"；常见解法是 `X-Accel-Buffering: no`、禁用压缩或应用层 padding。第二，**连接数上限**——HTTP/1.1 下浏览器对同一域名并发连接数约 6 个，而每个 EventSource 长期占用一个连接，多标签页会立刻撞顶；HTTP/2 多路复用后同域连接可协商（默认 100），问题大幅缓解但仍需注意单 TCP 连接上的队头阻塞。第三，**中间设备的空闲超时**——长连接若无数据会被 LB 或防火墙掐断，需要注释行心跳或 `retry` 字段配合，且心跳间隔必须小于所有中间跳的最小超时。

面试现场回答（1–2 分钟）：SSE 是单向的服务端推送，本质是不关闭的 HTTP 响应加 text/event-stream 文本协议，EventSource 自动重连并靠 Last-Event-ID 恢复位置；WebSocket 是独立协议的双向通道。选型上单向流式（模型输出、通知）用 SSE，双向交互用 WebSocket。工程上要盯三件事：代理缓冲会吞增量、HTTP/1.1 连接数上限、中间设备空闲超时需要心跳。

### 关键点

- SSE 是单向的 HTTP 响应流，`text/event-stream` + 空行分隔 + event/data/id/retry 四字段是完整协议面。
- `Last-Event-ID` 的恢复语义由服务端定义：id 必须映射到可恢复的流位置，否则重连无意义。
- 自动重连是 EventSource 的默认行为，服务端返回非 200 或业务失败时要显式 `close()`，否则会无限重连。
- 代理缓冲、HTTP/1.1 六连接上限、空闲超时是三个最常见的"协议正确但体验错误"来源。

### 常见误区

- **"SSE 挂了就切 WebSocket"**：大多数"SSE 不工作"的根因是中间层缓冲或超时配置，换协议不解决缓冲问题，WebSocket 同样会被代理缓冲影响。
- **把 `id` 当作消息序号随手生成**：id 必须与可恢复位置绑定；如果重连后服务端从最新位置开始推，客户端会静默丢失一段数据且无任何报错。
- **认为 HTTP/2 下连接数问题完全消失**：多路复用解决的是"同域连接数"，但所有 SSE 共享单条 TCP 连接，一条流的拥塞仍会影响同连接上的其他流。

### 追问

**面试官追问：如果流式输出中途服务端宕机，客户端已收到 id=1000，重连后如何保证不丢不重？**  
要点：服务端把事件先持久化（带单调序号）再推送，重连时按 `Last-Event-ID` 从持久层回放 id>1000 的事件；推送与持久化的先后顺序决定语义——先持久化后推送得到 at-least-once，客户端按 id 去重即成 exactly-once 观感；若事件不可回放（如纯实时行情），则声明为"重连即从当前开始、允许丢失"并在产品层明示，不要假装可靠。

### 延伸学习

- MDN《Using server-sent events》：https://developer.mozilla.org/zh-CN/docs/Web/API/Server-sent_events/Using_server-sent_events （本轮已核验：单向连接、text/event-stream、id/retry 字段语义、HTTP/1.1 每浏览器每域 6 连接限制与 HTTP/2 协商 100 的表述均出自此页）
- WHATWG HTML Standard §9.2 Server-sent events（协议权威定义）：https://html.spec.whatwg.org/multipage/server-sent-events.html

## B02 · 公开榜单污染、Reward Hacking 与自建评测的必要性

- 题目 ID：`Q-20261111-B02`
- 一级类型：Agent 评测与可观测性；二级主题：公开榜单污染、Reward Hacking 与自建评测的必要性

### 题目

很多团队选模型时直接参考公开基准榜单（MMLU、HumanEval、SWE-bench 等）。请说明公开榜单分数为什么不能直接当作"模型在你的任务上的能力凭证"，榜单污染与 Reward Hacking 分别是什么，以及在什么条件下自建评测才是唯一可信的能力依据。

### 先思考

- 榜单测试集是公开的：训练数据里出现过的题，分数还衡量"能力"吗？
- "Reward Hacking"中，被 hack 的是谁——模型骗了榜单，还是榜单的代理指标骗了人？
- 榜单任务分布与你的任务分布、输入形态、工具环境，重合度有多高？
- 如果榜单之间互相矛盾（A 榜模型 X 高、B 榜模型 Y 高），说明分数衡量的是什么？

### 参考答案

**结论：公开榜单是第三方的、静态的、与你的任务无关的代理指标；污染使分数虚高，Reward Hacking 使分数与真实能力脱钩，因此榜单可以用来缩小候选集，但任何"模型 A 是否满足我的业务要求"的判断，最终必须落在与你的任务同分布、随版本锚定的自建评测上。**

榜单污染指测试集内容进入训练语料：公开基准的题目、题解与讨论在互联网上大量存在，训练语料爬取后模型可能记住答案而非学会解题，表现为"对榜单题的准确率显著高于对同难度变体题的准确率"。这也是为什么各家会推出私有测试集版本（如 SWE-bench 的 verified/held-out 划分思路），以及为什么"清洗训练数据中的基准集"只是缓解而非证明。

Reward Hacking 指优化目标（奖励/评分函数）与其想要代理的真实目标之间出现缺口，被优化者找到了"得高分但不完成任务"的路径。在评测语境下，judge prompt 的漏洞、单元测试覆盖不全（代码评测只测了happy path）、字符串匹配指标过松，都会让"提高分数"与"提高能力"分离——优化压力越强（无论是训练时的 RL 还是提交者的针对性调参），缺口被利用得越彻底。识别方式是人工抽查高分样本：分数上升但样本质量不升，就是被 hack 的信号。

自建评测成为唯一可信依据的三个条件：其一，**分布对齐**——输入形态（你的文档格式、语言风格）、任务类型、失败模式的分布与线上一致；其二，**抗污染**——题目不公开、定期轮换、区分"训练候选可能见过"与"全 held-out"两层；其三，**可归因与可回归**——每条样本带判定方式（可断言断言之、不可断言用 judge 或人工）、带版本锚点，模型或 prompt 升级时跑同一集合对比。榜单的正确用法是粗筛与横向趋势参考，自建集才是能力判断与上线门禁。

面试现场回答（1–2 分钟）：榜单分数是代理指标。污染让分数虚高——公开题可能进过训练语料；Reward Hacking 让分数与能力脱钩——评分函数的缺口会被优化路径利用。所以榜单只用来缩小候选，真正的能力判断靠自建评测：分布与线上一致、题目抗污染可轮换、每条样本有明确判定方式并能随版本回归。选模型时用榜单+自建双层：榜单筛方向，自建定结论。

### 关键点

- 榜单衡量的是"在这些题上、按那个评分函数"的表现，三个限定词缺一不可。
- 污染的检验方式是变体外推：换表面形式不改考查点，分数掉多少就是记忆了多少。
- Reward Hacking 的通用信号：指标上涨、人工抽查的质量不涨。
- 自建评测的三要素：分布对齐、抗污染、可回归锚定版本。
- 榜单与自建集是分工不是替代：粗筛 vs 上线门禁。

### 常见误区

- **把榜单分数当绝对能力**："HumanEval 90 分"不等于"能写对生产代码"，两者考查的输入完整度、约束环境、验收标准完全不同。
- **用公开基准直接做内部回归门禁**：题目公开即可能被针对性优化，且无法区分能力提升与过拟合到题目。
- **认为私有测试集一劳永逸**：held-out 集一旦长期使用、结果外流，也会逐渐失去抗污染性，需要轮换与分层。

### 追问

**面试官追问：你们的自建评测集只有 80 条样本，怎么避免"分数波动 2% 就得出模型变好/变坏"的误判？**  
要点：小样本下先算统计口径——2% 就是 1.6 条样本，任何结论都是噪声；解法有三：每条跑多次取通过率（把单样本二值变成连续值）并用 bootstrap 或二项检验估计置信区间；按能力维度分层聚合而不是只看总分；把"差异不显著"作为默认结论，只有置信区间不重叠才宣布升降。评测集合扩大之前，结论的粒度必须与样本量匹配——这本身就是评测设计的一部分。

### 延伸学习

- SWE-bench 官方站点（held-out / verified 划分与任务构造）：https://www.swebench.com/
- OpenAI《Identifying and mitigating the security risks of generative AI》与 METR 对模型评估污染的讨论（后者为行业实践参考，具体论文链接未核验，按主题检索）

## S01 · 第三方技能包与 MCP 服务的供应链安全评审

- 题目 ID：`Q-20261111-S01`
- 一级类型：AI 安全与治理（兼属工具与互操作协议、上下文工程与能力封装）
- 核心考点：安装时声明 ≠ 运行时行为；能力最小化与沙箱边界；版本供应链与运行时审计

### 题目

你们的企业内部 Agent 平台允许业务团队自助接入第三方能力：MCP 服务（包括本地 stdio 形态与远程 HTTP 形态）、Agent Skills 技能包（含 SKILL.md 与配套脚本）。平台上线三个月接入了 60 多个第三方能力。安全团队的例行审计发现三个问题：① 某热门 MCP 服务的新版本在启动命令里加了一段下载并执行远程脚本的逻辑，已上线两周；② 某技能包的 SKILL.md 描述是"读取 Excel 并生成图表"，但包内脚本实际会把 `~/.ssh` 目录打包上传到外部地址；③ 多个业务团队接入同一 MCP 服务时，各自登记的能力清单不一致，其中一个团队登记的权限远小于服务实际申请的权限。业务方质疑："官方市场和官网下载的，怎么会不可信？"你负责建立第三方能力的供应链安全评审机制。

请给出：评审机制的分阶段设计（接入前/运行中/变更时）、每个阶段的具体检查项、如何在不阻塞业务的前提下分级管控，以及如何回答业务方的质疑。

### 先思考

- 三个问题的共同本质是什么：哪一个环节的"声明"被当成了"事实"？
- "官网/官方市场"证明了什么、没证明什么？签名、star 数、下载量各是哪种证据？
- MCP 官方安全最佳实践对"一键安装本地 MCP 服务器"的同意机制有什么要求？
- 技能包的 SKILL.md 与 scripts 之间，平台能对哪部分做静态校验？对哪部分只能运行时管控？
- 分级管控的维度应该是什么：按来源？按权限面？按副作用类型？

### 参考答案

**作答框架**：先定性（三个问题同源：把安装时的声明当作了信任凭证，缺少"声明与行为核对"的机制）→ 再分层（接入前评审、运行中管控、变更时门禁三层，每层有确定性检查点）→ 后分级（按权限面与副作用类型分级，而不是一刀切禁用）→ 收尾用三层能力归属说明平台职责边界。

**结论：三个问题同根——平台把"来源可信"（官方市场、star 数）和"描述可信"（SKILL.md、工具描述）当作了安全边界，而两者都不是。供应链安全评审的核心是把信任锚点从"谁发布的"移到"声明了什么权限、实际发生了什么行为、变更时谁来复核"这三件可验证的事上。**

**问题拆解**：问题①是版本供应链攻击——同一来源的后续版本可以引入恶意行为，所以"接入时审一次"不成立，版本变更必须是新的检查点；问题②是描述与行为不一致——SKILL.md 与工具描述是给模型和用户看的声明，脚本与启动命令才是实际行为，两者之间没有任何机制保证一致；问题③是能力登记缺失权威源——同一服务不同团队登记的权限不同，说明登记是手工声明而非从服务清单推导。

**核心方案——三层机制**：

接入前（评审层）：建立能力登记表，字段包括来源（仓库 URL + commit/版本）、权限面声明（文件读写范围、网络出网目标、命令执行、凭证访问）、副作用类型（只读/写入/外部副作用）、审批人与审批日期。检查项：本地 stdio 服务须展示完整启动命令并要求接入者显式确认（MCP 官方安全最佳实践明确要求执行前 consent，并高亮 `sudo`、`rm -rf`、网络操作等危险模式）；远程服务须检查授权模式是否为 token 专用（不接受透传用户 token）；技能包须做静态扫描（scripts 与 hooks 是等价于任意代码执行的存在，扫描外联地址、凭证路径关键词）；权限面按最小化原则核对——声明的 scope 是否可拆小、是否用了 `*`/`all` 类的捆绑 scope。

运行中（管控层）：沙箱与权限执行不依赖声明——本地服务进程按登记的权限面套沙箱（文件系统挂载白名单、出网 egress 代理白名单），超出白名单的访问直接拒绝并告警；工具调用经统一网关，记录归一化后的实际参数与访问对象（不是描述里写的对象）；技能包脚本的执行一律走沙箱运行时，不允许直接落宿主机。这一层的本质是：**运行时行为与声明的偏差由确定性系统检测，而不是靠事后审计发现**。

变更时（门禁层）：版本 pin——能力登记表绑定具体版本或 digest，自动升级默认关闭；新版本进入须重新走接入前检查（问题①的根因就是无门禁的自动升级）；版本间的 diff 自动生成（启动命令 diff、权限面 diff、脚本外联地址 diff），权限面扩大或出现新的外联目标时强制人工复核。

**技术选型与取舍**：用集中能力网关而不是各团队自接——网关是确定性的策略执行点，能做统一打点与权限执行，代价是平台团队承担运维与延迟（增加一跳）；用沙箱运行时（容器 + 挂载白名单 + egress 代理）而不是"信任+审计"——事后审计只能追责不能止损，沙箱把破坏半径限在声明范围内。备选方案"只允许白名单市场的能力"被否：白名单解决来源问题，不解决问题②的行为不一致，且会阻塞业务。

**失败路径与边界**：沙箱不可用（如本地 stdio 无法容器化）时 fail-closed——该能力只能以只读模式接入或暂缓；egress 代理故障时所有外联默认拒绝而非放行；扫描工具误报率高时不能把误报当放行理由，人工复核兜底；能力方申诉通道要有 SLA，否则业务会绕过平台私接。

**成本与延迟**：网关一跳增加 P50 约 5–10ms（确定性开销，可接受）；沙箱冷启动对高频调用是主要成本，预热池缓解；评审机制的人力成本集中在变更门禁，用 diff 自动化把人工复核压到只有权限面变化时触发。

**验证指标与观测**：接入前——评审覆盖率（100% 接入必须有登记）、权限面最小化比例；运行中——权限面外告警数、沙箱拒绝次数按能力分桶（某能力拒绝率突增是行为变化信号）、能力级调用成功率；变更时——新版本门禁通过时长、diff 复核率。上线后观察的第一批数据往往就是问题③的答案：从网关打点推导的"实际权限面"会替代各团队手工登记。

**三层能力归属**：模型只负责按声明调用工具，不负责判断工具安全；编排层负责沙箱、网关、版本 pin 的确定性执行；传统供应链工具（依赖锁定、签名校验、静态扫描、egress 控制）提供基础能力。模型的能力边界意味着"提示词里写清不要执行恶意脚本"不是任何一层。

**回答业务方质疑**：官方市场证明的是"发布渠道有审核流程"，不证明"每个版本的每个行为都被审核过"；问题①恰好来自官方渠道的某个版本。我们不质疑来源，我们做的是把来源可信转化为可验证的机制：你接入的能力，声明了什么权限就只给什么权限，行为超出声明会被拦下并告警——这保护的不只是平台，也是业务团队自己（出问题时可证明自己只申请了已批准的权限）。

### 关键点

- 来源可信（官方市场、签名、star 数）≠ 行为可信；信任锚点必须是可验证的权限声明与运行时行为的核对。
- 版本变更是新的攻击面：版本 pin + 权限面 diff 复核是变更门禁的最小集。
- SKILL.md 与工具描述是面向模型的声明，不是执行约束；scripts 是任意代码执行，只能靠沙箱与运行时管控。
- 集中网关是确定性策略执行点：统一打点推导出的"实际权限面"是登记数据的权威源。
- 不可沙箱化时 fail-closed，但必须配申诉 SLA，否则机制会被业务绕过。

### 常见误区

- **把"官方渠道"当安全边界**：渠道审核是概率性过滤，供应链攻击的历史反复证明单一版本就能穿透；正确姿势是渠道可信 + 行为可验证双轨。
- **只审接入、不审变更**：问题①上线两周才发现，正是因为自动升级无门禁；供应链攻击的主要注入点就是后续版本。
- **用提示词约束替代运行时管控**："在 SKILL.md 里声明不得访问 SSH 目录"对恶意脚本完全无效——声明文本本身是模型输入，而恶意代码在模型之外执行。
- **一刀切禁用第三方能力**：导致业务私接影子链路，审计能力反而丧失；分级管控比禁用更安全。

### 追问

**追问 1：一个第三方 MCP 服务声明只需要读文件权限，但网关发现它尝试连接一个未知域名。沙箱拦下之后，你如何判断这是恶意行为还是功能需要？**  
要点：先看外联目标的性质（已知 SaaS 域名 vs 新注册域名 vs IP 直连）、是否在服务文档中有对应功能解释；再按流程处理——拦下即告警，要求能力方发起权限面变更走门禁流程，复核期间该能力降级或停用；把"声明与行为偏差"本身作为该能力的信任评分指标，累计偏差自动触发人工评审。关键是判定权在评审流程不在单个告警，且业务影响（停用）有明确通道恢复。

**追问 2：如果平台要求所有第三方能力走统一网关，能力方（外部公司）以"性能与隐私"为由拒绝，怎么破？**  
要点：区分协商空间——权限执行（沙箱、egress 白名单）不可协商，这是平台底线；网关形态可协商（如能力方自持网关但按平台 schema 上报审计事件）。给出量化依据：网关开销 vs 直连的延迟差、出问题的责任划分（走网关的能力出事平台共担排查责任）。若能力方连最小审计上报都拒绝，结论是接入风险等于完全不可见，应降级为高敏能力走增强审批，而不是妥协——评估"拒绝可见性"本身就是一个强风险信号。

**追问 3：技能包的 scripts 在沙箱里执行，但沙箱需要访问业务文件才能工作。沙箱内的凭证与文件访问边界怎么设计？**  
要点：按调用租户注入最小凭证——临时、短 TTL、范围对齐该次任务（scoped credential），而不是把宿主用户凭证挂进沙箱；文件访问用挂载白名单而非路径字符串校验（挂载层不存在的路径物理不可达，应用层校验可被绕过）；沙箱出网默认全拒，白名单逐能力开启；执行产物回传走显式通道而非共享可写卷，避免把"沙箱隔离"变成"共享目录"。原则与已考察过的沙箱边界题一致：隔离边界由挂载与运行时提供，应用层校验不算边界。

### 常见误区（场景题附加）

- 把静态扫描当作运行时保障：扫描能抓已知模式（明文外联、凭证路径），抓不住动态生成的地址与混淆代码，两者是互补层。
- 登记"能力清单"用手工维护：必然出现团队间不一致（问题③），权威源只能是网关打点推导或服务清单自动同步。

### 小型实践

给一个真实开源 MCP 服务器做一次"声明 vs 行为"核对（30–60 分钟）：clone 其仓库，读取 README 与工具描述中的权限声明；阅读启动命令与主要工具实现，列出实际的文件访问路径、网络外联目标、子进程调用；对照 MCP 官方安全最佳实践的危险模式清单（`sudo`、`rm -rf`、网络操作、凭证路径）逐条核对；输出一页"权限面声明表 + 实际行为表 + 差异项"，并写一句结论：如果由你接入，会给它配什么样的沙箱白名单。这个过程就是接入前评审的最小版本。

## S02 · 金丝雀发布的统计功效与指标误判

- 题目 ID：`Q-20261111-S02`
- 一级类型：软件工程与平台工程（兼属分布式系统）
- 核心考点：灰度样本量与统计功效；聚合指标掩盖分桶差异；自动化回滚门禁的判定设计

### 题目

你们的核心 API 服务做金丝雀发布：新版本先放 5% 流量，观察 30 分钟，核心指标（错误率、P99 延迟）与基线对比无异常后，按 5% → 25% → 50% → 100% 逐步放量。某次发布，5% 阶段 30 分钟内错误率 0.4%，基线 0.42%，判断"无异常"进入 25%；25% 阶段错误率 0.6%，因"仍在告警阈值 1% 以下"进入 50%；50% 阶段错误率 1.4% 触发回滚。事后复盘发现：该故障只在携带特定请求头（某种客户端版本标记）的请求上触发，这类请求占全量约 8%，但在 5% 灰度的 30 分钟窗口里只命中了约 400 个，其中真正触发故障的条件组合（该请求头 + 特定参数模式）只出现了 6 次，6 次全部失败但被平均进整体错误率后不可见。同时回滚动作慢了：指标采样窗口 1 分钟 + 判定 2 分钟 + 摘除与缩容 3 分钟，故障在 50% 档持续了约 6 分钟才完全恢复。业务方要求：既不放弃金丝雀，也不能再出现"灰度全绿全量爆炸"。

请重新设计灰度发布的判定机制：样本量与判定窗口如何确定、按什么维度分桶、回滚门禁怎么定、放量节奏依据什么。

### 先思考

- 5% 灰度 30 分钟总共多少请求？"全绿"的结论背后，实际样本对 8% 的受影响子群意味着什么？
- 整体错误率 0.4% 里，如果子群失败率其实是 100%，子群占比多少时整体才不可见？
- "与告警阈值比较"和"与基线比较显著性"是同一种判定吗？
- 放量到下一档的依据应该是"时间到了"还是"本档收集到了足够的分桶样本"？
- 回滚为什么要 6 分钟？哪一段可以前置？

### 参考答案

**作答框架**：先给结论（故障不是灰度策略错了，而是判定机制在三个环节失效：样本量不支撑结论、聚合指标掩盖分桶差异、门禁用的是静态阈值不是统计判定）→ 拆解三个环节的修复 → 回滚时延分解 → 放量节奏与长期机制。

**结论：金丝雀发布的判定必须回答"这一档的样本量足以支撑什么结论"，而不是"指标看起来正不正常"。修复三件事：按流量比例推导每档最小观察量并分桶判定、把聚合阈值改成基线对比加显著性检验、把回滚动作中可前置的部分全部前置。**

**问题拆解**：假设 50% 档的 QPS 是 1000，30 分钟 180 万请求，整体错误率足以暴露问题；但 5% 档 30 分钟只有 9 万请求，8% 子群约 7200 个，其中"请求头 + 参数模式"的条件组合只出现 6 次——对受影响子群而言，6 个样本 100% 失败，统计上已经很强；对整体而言 6/90000 = 0.007%，完全被 0.4% 的背景噪声淹没。所以这不是"观察时间不够长"，而是**判定维度错了**：在整体维度上，这个故障在任何一档的早期都是统计不可见的。

**核心方案**：

第一，分桶判定替代聚合判定。按业务已知的风险维度分桶：客户端版本头、请求参数模式（路由级或参数指纹级）、租户、请求大小分布。每个桶独立与基线同桶对比。工程上不必穷举所有维度：从变更内容出发推导"这次改动可能影响什么"（改动碰了请求头解析 → 客户端版本桶是必看项），加上通用兜底桶。聚合指标仍保留但只用于发现总量崩溃，不用于"无异常"的判定。

第二，样本量与判定窗口联动。每档放量前先算：要检测的最小效应量是多少（例如"某桶错误率从 0.4% 涨到 2%"），按该效应量反推每桶所需样本量（二项比例检验的近似：检测 0.4%→2% 需要每桶约数百到上千样本）。若 5% 档在合理窗口内长尾桶样本不足，结论就是"本档不足以判定"，选择延长窗口或先在影子流量/回放流量上验证，而不是默认"没问题"。放量依据从"时间到了"改为"各桶样本量达标且判定通过"。

第三，门禁从静态阈值改为统计判定。静态阈值 1% 的问题：0.6% 通过了阈值，但相对基线 0.42% 是 +43%，在足够样本下已是显著恶化；而真正的子群问题在聚合维度又永远到不了 1%。门禁设计两层：聚合层用基线对比 + 置信区间（例如错误率相对提升超过 20% 且统计显著即拦），分桶层对高风险桶用更敏感的判定（如 CUSUM 变点检测或"连续 N 个窗口高于基线"的序贯判定）。同时保留硬性熔断线（如 3%）应对突发崩溃——统计判定负责敏感性，硬熔断负责兜底速度。

第四，回滚时延分解。6 分钟 = 采样 1 + 判定 2 + 摘除缩容 3。前置化：判定数据从灰度实例的实时指标流取（秒级）而非等监控系统的分钟级窗口聚合；摘除不必等缩容完成——流量摘除（从 LB/网关摘除灰度实例的端点）秒级生效，缩容只是回收资源，两者解耦；预案中把"摘除 + 流量切回基线版本"定义为一键动作并演练。修复后目标：从信号出现到流量恢复 ≤ 60 秒，缩容完成与否不阻塞恢复。

**放量节奏**：档位本身改为对数节奏（5% → 20% → 50% → 100%）让每档暴露的绝对样本量跳增更均匀；每档"判定通过"才进下一档；最后一档 50%→100% 改为快速完成（此时统计功效已足够，长尾是主要风险但已过敏感期，拖延反而拉长整体风险窗口）。

**失败路径与边界**：分桶维度本身错了怎么办——保留聚合层硬熔断兜底；基线本身在抖动（发布撞上上游故障）——判定用同期基线（同时段的旧版本副本）而非历史基线，避免把环境噪声算到新版本头上；灰度实例与基线实例的资源配额必须对齐，否则容量差异会伪装成性能回退。

**取舍**：更敏感的门禁会增加误拦（回滚一次正常发布），代价是一次发布延期；更宽松的门禁会漏拦，代价是故障放大。用"误拦成本低于漏拦成本"的业务分级定门禁灵敏度——核心交易类服务往敏感偏，内部工具往宽松偏。这也是为什么门禁参数必须按服务配置而不是全局统一。

**验证指标**：机制上线后跟踪三个数——漏检率（故障后回看灰度阶段是否有可判定信号）、误拦率（正常发布被回滚的比例）、平均恢复时长（从首次超标到流量恢复）。三者构成门禁的调参依据：误拦率高说明显著性门槛太松或分桶噪声大，漏检说明分桶维度缺失。

### 关键点

- "灰度全绿"的前提是样本量与判定维度足以支撑"绿"；聚合指标对低占比子群故障统计不可见。
- 判定要按风险维度分桶，分桶维度从变更内容推导并配通用兜底。
- 门禁 = 统计判定（敏感）+ 硬熔断线（兜底），两层分工而不是二选一。
- 回滚要拆解为信号、判定、摘除、缩容四段并前置前两段；流量摘除与资源回收解耦。
- 放量依据是"各桶样本量达标 + 判定通过"，不是时间。

### 常见误区

- **把告警阈值当发布门禁**：告警阈值是为"总不漏报崩溃"设计的粗线，不承担"检测相对基线的显著恶化"职能；0.6% vs 0.42% 在告警层是正常，在发布判定层是可疑。
- **延长观察时间代替修正判定维度**：在本例中即使观察 2 小时，条件组合样本也只有 24 个左右，聚合维度仍然不可见——时间解决样本量，不解决维度错误。
- **基线取历史均值而非同期对照**：流量日内波动、上游抖动都会进基线，造成大量误拦，最终团队会因"门禁总误报"而关掉它。

### 追问

**追问 1：分桶维度如果太多，每个桶的样本量都被稀释，判定反而更难做，怎么办？**  
要点：分层桶结构——少量高风险主桶（从变更推导）+ 一个"其他"桶兜底，不为分桶而分桶；对长尾桶用聚合信号 + 变点检测而非比例检验（长尾桶样本少时序贯方法功效更高）；接受"部分桶本档不可判定"并显式声明，把不可判定的桶留给下一档更大样本。本质上这是检测功效的预算分配：把统计功效花在变更最可能破坏的维度上。

**追问 2：如果故障是"累积型"（内存泄漏，30 分钟内看不出来，2 小时后爆炸），灰度判定怎么改？**  
要点：统计判定对累积型资源故障天然不敏感，需要加过程指标判定而非结果指标——灰度实例的 RSS、fd 数、GC 后存活对象等趋势指标的斜率门禁（如 RSS 每小时稳定上涨超过 X 即拦），并要求灰度阶段至少覆盖一个完整业务周期（跨流量峰谷）；更根本的是这类问题应前移到发布前的 soak test（带回放流量的长跑测试），金丝雀只兜底不确定的部分。

**追问 3：一键回滚把流量切回基线，但新版本已经写了下游数据（发布的服务包含写路径），回滚后状态一致吗？**  
要点：写路径的发布与流量回滚是两个问题——流量可秒级回切，数据 schema 与写入格式必须向前兼容（expand-migrate-contract：新版本只加列/加事件字段，旧版本能读；回滚后旧版本忽略新字段即可），任何"回滚需要数据迁移回退"的设计都意味着该发布不可回滚、必须用阻断式上线流程；若本次变更真的包含破坏性 schema 变更，金丝雀阶段就应该用双写对账验证而非只看服务指标。发布安全 = 流量安全 + 数据安全，两者要分别设计。

### 常见误区（场景题附加）

- 把"自动化回滚"理解为"缩容到零"：资源回收不等于流量恢复，两者的时延预算必须分开计算与演练。

### 小型实践

为一个你负责（或熟悉的）服务设计一次"判定可支撑性检查"（30–60 分钟）：取最近一次发布的灰度阶段指标，计算 5% 档 30 分钟窗口内各分桶维度的样本量；选定两个最小效应量（如错误率 0.4%→1.5%、P99 +30%），用在线样本量计算器或二项检验近似公式估算每桶所需样本；对照实际样本量写出结论：哪些桶在当时的窗口内是可判定的、哪些是"看起来绿但其实没测到"；再对照当时的门禁规则，标注如果按统计判定，结论是否不同。产出是一页判定可支撑性报告，可直接用于团队门禁规则评审。

## L01 · LeetCode 151. 反转字符串中的单词

- 题目 ID：`Q-20261111-L01`

### 题目

给定字符串 `s`，反转其中单词的顺序。单词由非空格字符组成，输入中单词由至少一个空格分隔，可能存在前导空格、尾随空格或单词间多个空格。返回单词顺序颠倒、单词之间仅用单个空格连接、不含任何额外空格的字符串。

### 先思考

- "多个空格、前后空格"意味着你不能简单按单个空格 split——Python 的 `str.split()`（无参数）和其他语言的 `split(" ")` 行为差异是什么？
- 结果由"单词列表"决定还是由"字符顺序"决定？把问题转换成"解析 + 重组"两步会简单多少？
- 进阶要求 O(1) 额外空间（可变字符串语言）：如果不许用 split，可以用"整体反转 + 逐词反转 + 原地去空格"三步在数组上完成，每一步各自消除什么问题？

### 参考答案

题号 **151**，中文名《反转字符串中的单词》，英文名 *Reverse Words in a String*，难度 **medium**（官方页面未渲染难度标签，按 LeetCode 标准分类记录为 medium）。

官方链接：https://leetcode.cn/problems/reverse-words-in-a-string/ （本轮已核验）

**题目描述**：给定字符串 `s`，反转字符串中单词的顺序。单词是由非空格字符组成的字符串；`s` 中使用至少一个空格将单词分隔开。返回单词顺序颠倒且单词之间用单个空格连接的结果字符串。输入可能含前导空格、尾随空格或单词间多个空格；结果中单词间仅用单个空格分隔，且不含额外空格。

**输入输出**：输入为字符串 `s`（含英文大小写字母、数字和空格）；输出为处理后的字符串。

**约束**：`1 <= s.length <= 10^4`；`s` 包含英文大小写字母、数字和空格 `' '`；`s` 中至少存在一个单词。

**示例**（均来自官方页面）：
- 示例 1：输入 `s = "the sky is blue"`，输出 `"blue is sky the"`。
- 示例 2：输入 `s = "  hello world  "`，输出 `"world hello"`（无前导尾随空格）。
- 示例 3：输入 `s = "a good   example"`，输出 `"example good a"`（多余空格减为单个）。

**解题思路**：问题可拆为"解析出单词序列"与"逆序重组"两步。Python 的 `s.split()`（无参数）按任意长度空白切分并自动丢弃空串，一次解决"多空格、前后空格"两个规范化问题；`reversed` 反转序列；`" ".join` 以单空格重组。三步都是线性操作。

**正确性说明**：`split()` 产出的单词序列与输入中"被空白分隔的极大非空白子串"一一对应，且保持原相对顺序；`reversed` 严格反转该序列；`join` 用单个空格连接，天然满足"单空格分隔、无额外空格"的输出约束。输出与输入单词集合及逆序顺序完全一致。

**时间复杂度**：O(n)，n 为字符串长度（split、reverse、join 均线性）。**空间复杂度**：O(n)（Python 字符串不可变，split 产生的列表与结果字符串都是 O(n)）。

**代码**：

```python
class Solution:
    def reverseWords(self, s: str) -> str:
        words = s.split()          # 按任意空白切分，自动丢弃空串
        words.reverse()            # 原地反转单词列表
        return " ".join(words)     # 单空格重组
```

**边界情况**：单词只有一个（无反转效果，直接返回该词）；全部由一个词加大量空格组成（空格全部丢弃）；首尾空格（`split()` 无参数自动忽略）。

**测试用例**：
- `reverseWords("the sky is blue")` → `"blue is sky the"`
- `reverseWords("  hello world  ")` → `"world hello"`
- `reverseWords("a good   example")` → `"example good a"`
- `reverseWords("a")` → `"a"`

（以上实现已通过 6 个定向用例与 3000 组随机对拍验证。）

**面试官可能的变体追问**：进阶要求在可变字符串语言中用 O(1) 额外空间完成——思路是三步：先双指针原地去掉多余空格，再整体反转全部字符，最后对每个单词逐个反转回来。Python 字符串不可变，无法真正原地，面试中说明此语言限制并口述三步法即可（对应 C/C++/Java 的字符数组实现）。

**可迁移的解题能力**：把"带噪声的序列规范化 + 结构重组"拆为解析与重建两段；`split()` 无参数与带参数的语义差异（丢弃 vs 保留空 token）是字符串处理中反复出现的陷阱；"整体反转 + 局部反转"组合是在 O(1) 空间约束下重排连续块位置的通用技巧（同样适用于旋转数组）。

### 关键点

- `split()`（无参数）按任意长度空白切分并丢弃空串，一次解决多空格、前导、尾随三个规范化问题；`split(" ")` 会保留空串，是本题最常见错误来源。
- 解析与重组分离：先得到无噪声的单词序列，再逆序 join，各步独立可验证。
- 输出约束（单空格、无额外空格）由 `join` 结构性满足，不需要逐字符检查。
- O(1) 空间变体靠"整体反转 + 逐词反转"组合实现，Python 字符串不可变故只能口述。

### 常见误区

- **用 `s.split(" ")` 后不处理空串**：多个连续空格会产生空 token，反转后空串位置出现在结果中间，输出含多余空格。
- **先按单空格 split 再逐个 strip**：能通过但绕远路；本质是把"任意长度空白"误当成"单个空格分隔"建模。
- **试图原地修改 Python 字符串**：字符串不可变，任何"原地"写法都会先报错或退化为复制；应说明语言限制并给出字符数组思路。
