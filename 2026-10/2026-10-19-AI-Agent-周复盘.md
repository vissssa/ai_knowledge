### C01（改编自 Q-20261012-B02，精选题到期复习）

**题目**：线上结构化输出解析失败率从 0.3% 涨到 4%，同时 P95 延迟从 1.8 s 涨到 4.6 s。团队已经在解析层加了"修复式重试"（失败后用原始输出回灌模型重写一次）。请给出分层归因顺序与每一层的判定指标，并说明为什么"修复式重试"会让延迟指标恶化。

**判定要点**：

1. 归因顺序应为：模型层（是否 strict 模式、schema 是否被改动、模型版本是否切换）→ 输出层（是否被截断，看 `finish_reason`）→ 校验层（校验器是否变严）→ 重试层（重试率与重试耗时占比）。**不要**一上来就改提示词。
2. 判定指标：`schema_valid_rate` 按模型版本与 schema 版本分桶；`finish_reason = length` 的占比（区分"没输出完"与"输出了但不合规"）；`retry_rate` 与重试耗时在总延迟中的占比。
3. 延迟恶化的机制：修复式重试是**串行追加**的一次完整模型调用，失败率 4% 意味着约 4% 的请求多付一次完整往返，且这些请求往往是输出最长、最容易触发截断的那批（相关性放大了影响）。因此 P95 恶化幅度远大于失败率本身的 4%。
4. 处置顺序：先止血（限制重试预算、对超长输出走截断续写而非整体重写），再定位根因（schema/模型/截断三者分离），最后把重试改为有预算、有幂等、有降级的结构化失败路径。

**与原题的角度差异**：原题考"定义与边界"，本题考"故障定位与指标设计"。

### C02（改编自 Q-20261015-B01）

**题目**：两个并发事务在默认隔离级别下执行：`T1` 读 `SELECT count(*) FROM oncall WHERE shift='night'`，得到 1；`T2` 也读同样的查询，得到 1；随后 `T1` 插入一条 `shift='night'` 并提交，`T2` 也插入一条并提交。业务不变量是"night 班次至少 2 人"。请回答：在读已提交、可重复读、可串行化三种级别下分别会发生什么？如果改用"先查后插"加锁能否解决？

**判定要点**：

1. 这是**写偏斜（write skew）**：两个事务读同一份快照，各自写入不同行，**不存在写-写冲突**，因此行锁与快照隔离都拦不住。
2. 读已提交：两者都成功，不变量被破坏。可重复读：在 PostgreSQL 中 RR 使用快照隔离，**仍允许序列化异常**，两个插入都会成功，不变量同样被破坏（这是最容易被答错的一点——"RR 不会有幻读"不等于"RR 不会有写偏斜"）。可串行化：`T2` 会被检测出读写依赖冲突而中止，返回 SQLSTATE `40001`，需要整事务重试。
3. "先查后插"加锁（`SELECT ... FOR UPDATE`）对本题**无效**，因为要锁的是"不存在的行"——`FOR UPDATE` 锁不到尚未插入的元组。可行方案是：唯一约束/排除约束、显式锁住聚合实体（如锁 `shift` 维度的父行）、或直接用可串行化并接受重试。
4. 结论：约束优先于隔离级别；隔离级别解决的是读写依赖检测，约束解决的是不变量本身。

### C03（改编自 Q-20261016-B03）

**题目**：团队为 RAG 引入了父子块检索：小块用于检索，命中后回传其所属大块用于生成。上线后召回指标没变，但生成端的引用准确率反而下降，且 token 成本上升 40%。请回答：父子块在什么前提下才生效？上述现象最可能的原因是什么？

**判定要点**：

1. 父子块生效的**前提**是：小块与大块的切分边界对齐语义单元，且"命中小块所属的大块"确实包含答案所需的完整上下文。如果原始文档本身结构混乱、或大块跨了无关主题，回传大块只会引入噪声。
2. 最可能的原因排序：大块过大导致**上下文稀释**（答案被无关内容淹没，模型倾向引用块内的显眼但无关句子）；大块内存在多个相似片段导致**引用定位漂移**（模型无法判断答案来自哪一句）；以及大块回传后**多条召回的大块高度重叠**，重复占用窗口。
3. 成本上升是必然的：回传大块把每条召回的 token 数放大了数倍。因此父子块必须配合回传条数下调，否则是纯成本增加。
4. 修正：限制回传大块的数量与总 token 预算；在大块内保留位置锚点并做去重；用"命中片段在大块中的位置"做高亮或裁剪，只回传命中片段的邻域而非整个大块。

### C04（改编自 Q-20261014-B01）

**题目**：一个 Agent 服务部署在 CPU 限额为 2 核的容器中。监控显示：CPU 使用率长期只有 30%，但 P99 延迟呈周期性锯齿状抖动（每 100 ms 出现一次尖峰）；`cpu.stat` 中 `nr_throttled` 持续增长，`throttled_time` 占比约 22%。请判断根因，并说明为什么"CPU 没用满"与"延迟抖动"可以同时成立。

**判定要点**：

1. 根因是 **CFS 带宽控制限流**：`quota/period` 约束的是**带宽（单位时间内的 CPU 时间上限）**，不是并行度。进程可以在极短时间内跑满配额，然后在剩余周期内被完全停止，等待下一个周期恢复——这正是周期性锯齿的来源。
2. "CPU 使用率 30%"是周期内的**平均值**，掩盖了"前 30 ms 跑满、后 70 ms 停住"的真实形态。因此使用率低与抖动大并不矛盾。
3. `nr_throttled` 增长与 `throttled_time` 占比是判定限流的直接证据；两者应作为一级告警，而不是只看 CPU 使用率。
4. 处置：确认 `period` 与 `quota` 的配置（默认 period 为 100 ms，与 100 ms 周期吻合）；若业务需要更强的突发能力，可在保持平均带宽不变的前提下调整 period（period 越长，突发能力越强，但单次暂停时间也更长），或提高配额；同时**必须把并发度按配额推导**，而不是按 `cpu_count()`——后者在容器中会读到宿主机核数。
5. 补充排查项：父级 cgroup 配额耗尽会连带限流子级，因此需要向上检查一层。

## 五、综合系统设计题 D01

**题目**：设计一个多租户 Agent 平台的**可观测与治理底座**。

**规模与约束**：

- 40 个企业租户，日均 120 万次任务，峰值 12 万次/小时；
- 每个任务平均 6 次模型调用、11 次工具调用，工具分布在 60 余个 MCP server（含 20 个第三方）；
- 合规要求：租户数据严格隔离，审计留存 365 天，任何一次数据访问必须可归因到具体身份；
- 现有痛点：成本按账号统计无法归因到任务；线上问题只能靠用户反馈发现；第三方能力无法快速撤销。

**要求**：给出链路模型、数据模型、关键执行流程、以及三个必须做的取舍。

**参考要点**：

1. **链路模型**：用户请求为 root span；每次模型调用与每次工具调用为子 span，工具调用 span 需要携带 server 版本与能力 ID。跨 MCP 边界用 `_meta` 传播 `traceparent`，保证 trace 不断裂；`baggage` 只放租户与实验分组等非敏感维度，出网前剥离。模型调用与工具调用必须是**同一 trace 下的兄弟 span**，不能各自成 trace。
2. **数据模型（三张核心表）**：
   - `task(id, tenant_id, user_id, agent_id, workflow_version, model_version, status, started_at, ended_at)`；
   - `span(id, trace_id, parent_span_id, kind, name, capability_id, server_version, started_at, duration_ms, status)`；
   - `cost_event(span_id, tenant_id, task_id, kind, input_tokens, output_tokens, cache_read_tokens, cache_creation_tokens, unit_cost)`。
   成本挂在 span 上、按 task 聚合，才能回答"某租户某类任务花了多少"。
3. **关键流程**：请求进入 → 生成 trace 并绑定租户与身份 → 编排层每步创建 span → 工具调用经网关（鉴权 + 参数策略 + 出口白名单 + 版本 pin）→ 网关写审计流 → span 结束时写 cost_event → 任务结束时聚合。审计走异步持久队列，写失败不阻断调用但上调风险等级。
4. **必须做的三个取舍**：
   - **采样 vs 全量**：成本与 trace 存储压力下必须采样，但采样要在入口做头部决策并保持全链路一致（`sampled` 标志传播），否则链路会残缺；错误与高风险链路应全采（尾部补充采样）。
   - **实时聚合 vs 事后批算**：实时聚合能支撑成本熔断与异常告警，但引入流处理复杂度；建议实时只算聚合指标，明细保留供事后下钻。
   - **审计完整性 vs 延迟**：审计写入必须异步并允许短暂缺失，缺失期间该能力风险等级上调；不要为了审计完整性把审计放进关键路径。
5. **验收指标**：按任务成本归因覆盖率（目标 100%）、trace 完整率（跨 MCP 边界不断裂的比例）、影响面反查耗时（给定能力 ID 查出依赖业务线）、MTTD、审计完整率、以及第三方能力熔断生效时长。
6. **不得忽略的失败路径**：网关不可用时的降级策略（按风险等级决定是否放行）、版本漂移检测、以及"审计缺失"本身要作为可观测指标而不是静默失败。

## 六、LeetCode 复习题 E01

**标记**：**LeetCode 复习题**
**原题**：146. LRU 缓存（`Q-20261010-L01`，首次出现日期 **2026-10-10**，medium，哈希表 + 双向链表）
**复习原因**：周复盘要求的间隔复习；该题是本周期第一道设计题，其核心结构（哈希表索引 + 链表维护顺序）是后续多道缓存类问题的母结构；本次**不重复原实现题**，改为三个变体角度。
**作答状态**：原状为 `generated`，无作答记录，因此本次复习不构成"已掌握"的证据。

**变体题目**：在 146 的基础上增加三项要求，请说明每一项会破坏原设计的哪个假设、以及需要怎么改。

1. **带 TTL**：每个条目有独立过期时间，过期后即使最近被访问也必须失效。
2. **并发安全**：多线程同时 `get` / `put`，要求读操作不阻塞其他读操作。
3. **按字节计费的容量**：容量上限不是条目数，而是条目 value 的字节总数，且不同条目大小差异可达三个数量级。

**参考要点**：

1. **TTL 破坏的是"链表顺序即淘汰顺序"这一假设**。原设计中链表尾部就是最该淘汰的项；引入 TTL 后，过期项可能位于链表中间。三种改法：惰性删除（访问时检查过期，简单但过期项会占着空间直到被访问或淘汰）、按过期时间的额外索引（小根堆或时间轮，主动清理，O(log n)）、以及混合（惰性为主 + 定期扫描少量候选）。要点是：**过期判定必须在读取时做，不能只依赖淘汰时检查**，否则会返回已过期数据。
2. **并发安全破坏的是"所有操作都是 O(1) 且无竞争"的假设**。读多写少的场景下应用读写锁：`get` 持读锁，但要命中后更新链表位置——这是写操作，因此要么把 LRU 顺序更新降级为近似（允许偶尔不精确，用分段或延迟更新），要么让 `get` 也持写锁（退化成串行）。工程上常见折中是把缓存分片（按 key 哈希到 N 个独立的 LRU），降低锁竞争而不需要复杂的无锁结构。
3. **按字节计费破坏的是"每个条目占 1 个单位容量"的假设**。淘汰时不能只看链尾一条，而要循环淘汰直到腾出足够空间；同时必须防止"一个超大条目把整个缓存清空"——需要设单条目上限，超过则拒绝写入而不是淘汰所有人。另外字节数计算本身要确定（序列化后的长度，而不是对象引用大小）。

**复杂度变化**：TTL + 堆为 O(log n)；分片后单次操作仍为 O(1) 但容量按片均分，命中率可能略降；按字节计费使单次 `put` 最坏退化为 O(k)（k 为被淘汰条目数），均摊仍为 O(1)。

## 七、迁移题 E02（同一算法思想的迁移）

**题目**：LRU 的结构是"哈希表提供 O(1) 定位 + 链表提供 O(1) 顺序维护"。现在把它迁移到 Agent 系统的**上下文条目缓存**上：一个长会话 Agent 需要缓存"工具调用结果"以节省 token 与延迟，但缓存条目有四种不同的失效语义。请设计淘汰策略，并说明哪些地方能直接复用 LRU 的结构，哪些地方必须改。

四种失效语义：

- A 类：会话级事实（如"用户的账号 ID"），只要会话在就必须保留；
- B 类：外部数据快照（如"某工单的当前状态"），有 TTL 且可能被外部修改；
- C 类：大体积工具结果（如"一次全文检索返回的 200 条记录"），占用空间大但复用率低；
- D 类：高频重复查询（如"同一个 SKU 的价格"），体积小但命中率高。

**参考要点**：

1. **可直接复用的部分**：哈希表按 key 定位、链表维护访问顺序、O(1) 提升到头部、O(1) 淘汰尾部——这些结构在原样场景下完全复用。
2. **必须改的部分一：单一顺序不够**。A 类不能被淘汰，因此它不能参与 LRU 排序，应放在独立的常驻区（并单独设容量上限，防止无限增长）；把 A 类放进同一条 LRU 链会导致"会话早期的关键事实在长会话中被挤掉"，这正是长会话 Agent 丢失硬约束的典型成因。
3. **必须改的部分二：容量维度不同**。C 类与 D 类的体积差三个数量级，按条目数的 LRU 会让几个 C 类条目挤掉大量 D 类条目，命中率崩塌。应改为按**字节容量**并限制单条目大小，或按体积分级到不同的 LRU 队列（类似分段 LRU）。
4. **必须改的部分三：新鲜度语义不同**。B 类有 TTL 且会被外部修改，纯 LRU 不知道"内容已变"。需要在条目上保存 provenance（来源、版本/ETag、写入时间），并在命中时区分"确定新鲜"与"可能过期"；对后者要么重新校验，要么返回时标记不确定，让模型知道这是旧数据。**绝不能把过期快照当作事实回灌给模型**。
5. **与 LRU 的本质差异**：LRU 假设"缓存未命中只是慢一点，重新计算即可"。Agent 场景下**缓存命中错误会污染模型的推理前提**，因此正确性优先级高于命中率；宁可多花一次工具调用，也不要返回一个自己都不确定是否新鲜的缓存值。
6. **可迁移的抽象**：把 LRU 抽象为"定位索引 + 顺序索引 + 容量策略 + 新鲜度策略"四个可替换组件，四种失效语义分别配置不同的策略组合，而不是为每类各写一套缓存。
